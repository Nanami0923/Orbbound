# Orbbound 双端局域网联机玩法与实现方案

整理日期：2026-10-15。审查基线：当前工作区 4.2.0，HEAD `de7728d`。

本文是玩法与开发方案，尚未实现联机、构建联机安装包或完成双设备实测。下文时长、网络阈值、攻击数值和工期均为建议初值，验收目标不代表已有测试结果。

**建议首发：两人「同图竞分」，Windows 与 Android 都能建房、加入和重连；用房主统一裁决游戏状态，以原生 TCP 传输操作和快照。随后推出「连锁对战」与「协作接力」。**

## 1. 产品范围与设计取舍

### 1.1 首发要解决的体验

两个人连接同一路由器或可互通的热点，打开游戏，不注册账号、不连接云服务器，就能在一分钟内建立房间，完成一局约三分钟的对决，结束后直接再来一局。

| 项目 | 首发决定 |
| --- | --- |
| 人数 | 2 人；只有一个房主和一个客人 |
| 平台 | Windows ↔ Android、Android ↔ Android、Windows ↔ Windows |
| 房主能力 | 两个平台均可建房，无需电脑作为固定服务器 |
| 网络 | 首先支持可互通的 IPv4 局域网；无需互联网 |
| 建房 | 昵称、房间名、难度、3 / 5 分钟；两端明确展示设置 |
| 加入 | 自动发现房间 + 手动输入 `IP:端口` |
| 核心玩法 | 同图竞分；独立棋盘、相同开局、同时开始 |
| 对局保障 | 就绪、版本检查、同步倒计时、结果确认、短时重连 |
| 记录 | 独立联机战绩，不进入单机最高分、星级或关卡解锁 |
| 下一阶段 | 连锁对战、协作接力、便捷邀请二维码 |

首发不做公网匹配、账号好友、语音聊天、四人局、观战席、房主迁移、跨进程续局或游戏内自动开启热点。浏览器开发预览提供模拟传输；正式局域网功能由安装版的原生桥接提供。

“同一 Wi-Fi”不是充分条件：访客网络、AP 客户端隔离、校园网隔离可能禁止设备互通。手动地址只能绕过发现失败，不能绕过隔离或防火墙。Android 热点作为房主的能力必须单独实测，不能根据普通 Wi-Fi 的成功推定。

### 1.2 为什么按这个顺序开发

| 模式 | 玩点 | 新增规则成本 | 顺序 |
| --- | --- | --- | --- |
| 同图竞分 | 同一开局，各自寻找更好的消除路线 | 较低；主要是会话、时间和结果裁决 | P0，首发 |
| 连锁对战 | 大掉落给对手压力，消除抵消攻击 | 中等；新增攻击队列、公平排序和防滚雪球 | P1，第二阶段 |
| 协作接力 | 共用一个棋盘，轮流拆解，共同过关 | 中等；新增回合、共享目标和协作关卡 | P1，第三阶段 |

这三种玩法分别覆盖“比操作”“互相干扰”“一起解题”。先验证跨端联机的稳定性，再把互动规则加到同一套会话框架里。

## 2. 现有代码能复用什么

| 已确认的基础 | 源码依据 | 联机用途 / 边界 |
| --- | --- | --- |
| 共用 TypeScript 规则、Phaser 展示 | [package.json](../../package.json)、[PlayScene.ts](../../src/game/PlayScene.ts) | 两端共用一套规则，不在 C#、Java 各重写一份 |
| 纯函数开局、消除、下压 | [engine.ts](../../src/core/engine.ts) 的 `createGameState`、`resolveShot`、`forceDescent` | 可在无场景对象的房主裁决器里计算双方状态 |
| 状态包含随机数状态、棋盘行偏移 | [types.ts](../../src/core/types.ts)、[rng.ts](../../src/core/rng.ts) | 可制作完整快照、复现操作；必须同步 `rngState`、`rowOffset` |
| 固定逻辑坐标和弹道 | [game-config.ts](../../src/content/game-config.ts)、[physics.ts](../../src/core/physics.ts) | 使用已有 640×760 逻辑空间，不使用手机屏幕像素计算落点 |
| 限时、清盘换波、压力下压 | [modes.ts](../../src/core/modes.ts)、[engine.ts](../../src/core/engine.ts) | 可借鉴逻辑；现有 `createRound` 只接受 5 / 10 分钟，不能直接拿来创建 3 分钟联机局 |
| Windows 原生外壳 | [Program.cs](../../windows/Program.cs)、[package-win.cjs](../../scripts/package-win.cjs) | 当前是 .NET Framework 4.8 / WinForms + WebView2；历史 Electron 不参与本次方案 |
| Android 原生插件入口 | [MainActivity.java](../../android/app/src/main/java/com/orbbound/game/MainActivity.java)、[GameFeedbackPlugin.java](../../android/app/src/main/java/com/orbbound/game/GameFeedbackPlugin.java) | 新增 Capacitor 插件提供网络能力 |
| 单机保存、排行、生命周期 | [main.ts](../../src/main.ts)、[history.ts](../../src/storage/history.ts) | 必须为联机分流，不能直接沿用退出、存档和结算路径 |

**当前没有房间、发现服务、网络连接、联机协议或远端玩家状态。现有确定性只保证相同状态和输入得到相同结果，并不等于已经支持联机。**

需要优先处理的耦合：

1. `PlayScene.launch()` 在发射瞬间就调用 `resolveShot()` 并持久化；飞行和掉落动画是之后的展示。联机必须把提交权交给房主裁决器。
2. 下一发能否发射目前受动画完成控制。联机必须改为统一的逻辑冷却，避免帧率、减少动态效果或掉帧影响发射频率。
3. `Date.now()`、单机暂停、计时下压混在场景中；联机时间必须来自房主会话时钟。
4. 当前切后台、Windows 宿主后台事件和 Android 返回键会回首页；联机必须进入独立的暂停 / 重连流程。
5. `GameState.status === 'WON'` 既可能是清盘，也可能是单机限时结束，不能直接解释成赢了对手。

## 3. 首发玩法：同图竞分

### 3.1 一局怎么玩

1. 房主选择难度和时长，默认普通、3 分钟；可选 5 分钟。
2. 双方确认设置并准备，资源加载、初始快照核验完成后显示同步的 3、2、1。
3. 双方在各自的大棋盘上操作；对手的分数、波次和缩略棋盘持续可见。
4. 使用现有三连消除、悬空掉落及基础计分。清空棋盘进入下一波，累计分数。
5. 到时停止接收新的发射，以房主确认的结果结算；双方均可选择再来一局。

建议显示文案：**「相同开局，自由拆解。时间结束时比较分数。」**

### 3.2 规则清单

| 规则 | 建议定义 |
| --- | --- |
| 难度 | 双方一致，首发使用现有简单 / 普通 / 困难配置 |
| 计分 | 沿用 `matchPoints`、`dropPoints`；比较基础分，不额外乘难度倍率 |
| 供球 | 保留有效颜色供球，不增加双方完全相同的固定球序 |
| 清盘 | 当前波得分计入总分，波次加一；进入下一张相同编号的种子棋盘 |
| 下压 | 保留发射压力下压；时间下压沿用现有限时节奏思路，按房主活动时间调度 |
| 清盘奖励 | 首发不额外加分，避免先引入未经验证的奖励平衡 |
| 触底 | 该玩家本局结束，保留分数并观看；另一方可以继续至截止或触底 |
| 提前结束 | 双方都触底则立即结算；不提供单方“结算本局”按钮 |
| 排名 | 总分高者胜；同分比较完成波次；仍相同则平局 |
| 胜负解释 | 这是竞分玩法，触底不直接判负；高分玩家提前触底仍可能获胜 |
| 系列赛 | 首发只做单局与再来一局，三局两胜作为后续选项 |

每人的时间下压在其逻辑冷却结束后应用；到期债务不能丢失或靠反复发射重置。同一时刻先处理已到期的时间下压：下移棋盘、清零 `danger`、更新 RNG 和 `boardRevision`，并从原计划时间推进下一次时间下压。随后才验证新发射；针对下压前旧修订的命令拒绝并要求同步重瞄。普通发射仅按现有压力规则累加，压力触发下压不重置独立的时间下压计划。不要在两个分支各自下压后再凭 UI 合并动画，这会隐藏真实规则差异。

清盘进入新波时保留总分、总发数、比赛剩余时间，重置该波压力与下压计划。首发不直接复用单机 `resetDescent()` 的任意重置行为。

### 3.3 同图公平的准确含义

现有 `chooseNextColor()` 依据当前棋盘的有效颜色抽球；两人的操作不同，棋盘和随机数消耗会分歧。因此只能承诺：

- 相同波次的初始棋盘和初始两球一致。
- 同一难度、同一逻辑坐标、同一弹道和供球算法、同一冷却规则。
- 相同状态与操作序列能复现相同结果。

新增并版本化 `deriveWaveSeed(matchSeed, waveIndex)`，用固定的无符号整数混合算法生成每波种子，配固定测试向量。不得拿某一玩家当前的 `rngState` 当下一波种子，否则双方同编号波次会不同。每个玩家的波内 RNG 独立推进。

不承诺键鼠与触控的操作效率完全一样。通过真实跨端对局记录胜率、发射速度和误操作，必要时后续加入回合玩法；首发不凭猜测给手机加分或调整命中判定。

### 3.4 截止、冷却和判定

房主裁决器在截止前接受并提交的合法发射立即计分，即使动画尚未播放完；到达截止时拒绝新发射。客户端点击时间只用于诊断，不决定有效性，也不允许补交“我刚才已经点击”的得分。

房主玩家也走同一个命令队列和合法性检查，不允许直接修改自己的棋盘。该方案能消除代码路径差异，但客人的网络往返仍会产生小幅延迟劣势；首发定位为朋友间休闲对局，以稳定低延迟局域网为目标，不声称赛事级公平。

新增纯函数 `shotTiming(trace, events, rules)` 生成 `readyAtMatchMs`。建议先以已有飞行时长公式加消除 / 掉落 / 下压的固定逻辑时间形成统一冷却；两端动画时长向它对齐，减少动态效果只改变视觉。冷却不能由客户端传入，也不能等待对方动画完成回包后才解除。

## 4. 后续玩法一：连锁对战

核心体验是“打出大掉落给对手施压，再用下一次消除化解来袭攻击”。保留双独立棋盘和相同开局，使用独立的 `lan-battle-v1` 规则包。

### 4.1 第一版攻击机制

只引入一种攻击：**额外下压一行**。不先加入遮挡屏幕、反转瞄准、随机换球等控制干扰，保证手机和电脑都能理解与应对。

设本次同色消除数为 `M`，悬空掉落数为 `D`：

```text
攻击值 A = min(3, floor(max(0, M - 3) / 3) + floor(D / 4))
抵消自己的待收攻击，再把剩余攻击值发送给对手。
4 点待收攻击值转换为一行额外下压。
```

例如：消除 6 个、掉落 8 个，产生 `1 + 2 = 3` 点。自己当前有 2 点待收攻击，先抵消，向对手发送剩余 1 点。这里的计数来自房主计算的事件，不能由客户端上报。

建议初值：预警 2 秒；额外下压之间至少间隔 4 秒；待收值上限 8 点，超出丢弃；不足 4 点保留，并可被后续消除抵消。每份攻击分别记录到达与生效时间，只有至少 4 点均完成预警才可兑现一行，不能让较早的 1 点带着刚到的 3 点立即下压。抵消从最早到达的攻击开始，不刷新其他攻击的预警计时。

### 4.2 防止不可挽回的连打

- 攻击仅在被攻击者下一次可以操作的边界执行，不在飞行中移动目标棋盘。
- 有到期完整攻击行时，先允许执行同批次的合法防御发射并抵消，再应用剩余攻击。规则与竞分下压顺序不同，必须独立定义。
- 同一 50 毫秒裁决批次中，先结算双方发射，再同时抵消、发送、应用攻击，最后统一判断触底，避免固定先处理房主。
- 连锁对战初版关闭额外的“时间下压”，保留发射压力下压；攻击下压与自然下压同批次重合时只执行一次自然下压，攻击值延后，不凭空消失。
- 清盘提供一小段保护期的想法先做试玩验证；若采用，明确保护时长及队列是否继续增长，不临时藏在 UI 中。

批次开始时锁定玩家是否处于可操作边界，在同一次原子结算中完成防御发射、抵消和剩余攻击，再统一提交状态与新的冷却。不能因为防御发射新设了冷却，就再次推迟本批已到期的攻击；展示按“原棋盘弹道 → 消除 / 抵消 → 下压”播放，逻辑冷却包含整个过程，不在飞行展示中途改变弹道目标。

### 4.3 胜负

首发该模式建议单局上限 5 分钟。仅一方触底，对方获胜；同一个裁决批次双方触底，平局。到时双方均存活则比较累计基础分，同分平局。截止与攻击执行冲突时，截止优先，丢弃未执行攻击。

为了避免接收攻击消耗掉本来用于供球的 RNG，后续把联机供球、自然补行和攻击补行拆成独立随机流，所有状态进入快照。不能简单反复调用当前 `forceDescent()`：它会清空 `danger` 并消耗同一个 RNG，需要新策略或提取更底层的下压原语。

以上数值只作为首次试玩配置。重点观察大掉落后胜率、首个攻击到触底的时间、连续无操作窗口；确认能翻盘后再开放更多攻击种类。

## 5. 后续玩法二：协作接力

双方共享一个棋盘，每人轮流发射两球，共同完成清盘或目标球任务。它适合朋友讨论解法，也能降低跨端输入速度差异的影响。

- 首轮由房主随机指定先手，之后按固定顺序轮换；每个回合携带 `turnId` 和 `activePlayerId`。
- 非当前玩家只能查看、发送短提示和标记建议落点；标记不会直接变成发射命令。
- 每回合建议 25 秒，只计算可操作阶段的思考时间；飞行动画和双方暂停不计入。超时自动交棒，连续两回合无人操作则进入等待状态。
- 保留共享的当前球与下一球；切换玩家不重抽球、不重置压力。
- 一个共享发数预算，完成目标共同胜利；预算用尽或触底共同失败。主动离开则结束协作，记录为中断。
- 设计独立的 6～10 个协作关卡，由浅到深覆盖反弹、切断支撑和交接布局。已有 30 关可作为素材参考，但不能未经校准直接换标题上线。
- 保存协作历史与共同最佳发数，不推进个人闯关星级和解锁。

无人操作进入等待后冻结团队和回合时钟；双方重新就绪后倒计时恢复，继续已经确定的下一位玩家，不重置剩余发数。最后一发同时完成目标且用尽预算时，目标成功优先，保持现有关卡的最后一发判定；等待中有人离开则中断。

这一模式先做回合接力。两人同时向一个棋盘发射会带来弹道竞争、供球归属及落点冲突，留到后续独立玩法再讨论。

## 6. 房间与双端界面

### 6.1 用户流程

```text
首页 → 局域网联机 → 创建房间 / 加入房间
                          ↓
       等待室：双方昵称、平台、规则、连接质量、准备
                          ↓
          加载并核验初始状态 → 同步倒计时
                          ↓
                 对局 → 双方结果页
                          ↓
             再来一局 / 回等待室 / 离开
```

首页新增一张与现有模式同级的「局域网联机」入口。第一次进入展示简短提示：“两台设备连接同一路由器或热点；一方创建，另一方加入。”不开局时不持续扫描网络。

| 页面 | 内容和行为 |
| --- | --- |
| 创建房间 | 昵称、房间名、模式、难度、时长；建好后显示可用本机地址和端口 |
| 加入房间 | 附近房间卡片、刷新、手动地址输入；显示 1/2 或 2/2、模式及兼容状态 |
| 等待室 | 双方头像色 / 昵称 / 平台、规则摘要、准备按钮；房主可开始、移除未开局客人 |
| 局内 | 自己棋盘、对手信息、比赛时钟、连接质量、联机菜单 |
| 结算 | 双方分数、完成波次、总发数、胜负原因；重开需要双方同意 |
| 故障页 | 明确区分未发现、连接超时、房间已满、版本不兼容、权限拒绝、房主退出 |

昵称最多 16 个可见字符，房间名最多 24 个；渲染按文本转义，控制字符拒绝。房主改变规则后双方准备状态清空。准备后仍需加载成功确认；资源未加载完不能仅因按钮点过“准备”就开始。

首发不显示可能误导的六位“联网房间号”。若后续加入短码，它只用于识别已经发现的房间；没有目录服务器时，单凭短码无法在任意网络定位房主。二维码应携带实际地址、端口、房间 ID 和协议版本，不等同公网邀请。

### 6.2 Windows

宽窗口以自己棋盘为主，侧栏放对手缩略棋盘、分差和连接状态；窄窗口退化成顶部信息条。双方棋盘使用同样的逻辑比例，不为了并排而改变自己的弹道空间。

保留鼠标、键盘、快转、快捷键设置。联机中把“结算本局 / 重新开始 / 存档并返回”替换为“对局菜单 / 请求暂停 / 离开房间”；全局快捷键同样分流，不能绕过菜单触发单机行为。Escape 关闭弹层，输入地址或昵称时不触发发射快捷键。

### 6.3 Android

竖屏保持自己棋盘的可操作尺寸，顶部紧凑显示双方分数、倒计时和网络状态，对手棋盘用小缩略图；横屏或平板再扩大侧栏。查看对手不得遮挡当前球、下一球和发射区域。

普通控制与沉浸控制继续可用。攻击预警用颜色、图标与可选轻震动，不能只靠颜色。系统返回打开联机菜单；双击返回不默默离房。输入法出现、导航栏变化和屏幕旋转不得改变会话身份或重建比赛。

## 7. 通信架构

### 7.1 主线：共用规则 + 原生传输

```text
客人：输入 / 本地瞄准 / 展示预测
        ↓ LanTransport
Android 插件 或 Windows 原生桥接
        ═══ 局域网 TCP ═══
房主原生连接服务
        ↓ 有限消息队列
房主 TS MatchAuthority：验证命令、计算双方状态、裁决胜负
        ↓
权威事件 + 状态快照 → 房主展示 与 客人展示
```

房主保存双方完整棋盘并裁决全部操作。原生层只处理网络、权限、发现、连接和生命周期信号，不计算消除、分数或胜负。房主的本地输入也经 `MatchAuthority` 处理。

权威逻辑从 Phaser 场景中抽出，建议使用固定频率的调度器处理事件，而不是绑定渲染帧。首发只承诺双方前台游玩；原生 socket 存活不代表 WebView 中的规则仍在运行，切后台统一冻结会话。

### 7.2 为什么选择原生 TCP

两端已有原生外壳，可分别使用 Windows `TcpListener/TcpClient` 与 Android `ServerSocket/Socket`。前者以 `NetworkStream` 传输数据，后者提供原生监听能力。[Microsoft TCP 说明](https://learn.microsoft.com/en-us/dotnet/fundamentals/networking/sockets/tcp-classes)、[Android ServerSocket 文档](https://developer.android.com/reference/java/net/ServerSocket)。

| 路线 | 判断 |
| --- | --- |
| 原生 TCP + 桥接 | 推荐；双方可建房，复用系统网络能力，消息量小，不必同步每帧画面 |
| 原生 WebSocket 服务 + 浏览器客户端 | 可替代；仍需 Android 服务端实现、依赖选择，以及 WebView 安全上下文验证 |
| WebRTC | 暂缓；需信令交换和更多连接状态，对两人同网段离散操作的收益有限 |
| 自建 UDP 可靠传输 | 不采用；需要额外处理重传、排序和拥塞，收益不足 |

使用原生 socket 后，页面不直接连接 `ws://局域网地址`，无需为了联机全局放宽 WebView 的混合内容策略。现有 Windows 虚拟主机页面及 Android Capacitor 页面加载方式保持可用。

### 7.3 房间发现与地址选择

首发用 UDP 查询、房主单播回复；只有发现使用 UDP，对局数据全部走 TCP。

建议约定 UDP 发现端口 `42170`，TCP 建房优先尝试 `42171`，冲突时由系统分配空闲端口并在回复中公布。它们是项目约定，不能宣称为官方分配端口。UDP 发现端口被占用时仍可创建 TCP 房间，提示“自动发现不可用，请通过地址加入”，不让建房整体失败。

1. 加入页每 2 秒向所选有效网卡的子网广播地址发送一次带随机查询 ID 的发现请求；不要只硬编码 `192.168.1.255`。
2. 房主返回查询 ID、房间 ID、名称、人数、TCP 端口、协议和规则标识；客户端使用实际数据包来源地址连接，不盲信载荷里的地址。
3. 发现消息不超过 1 KiB；匹配查询 ID、限速回复、房间 ID 去重；6 秒未刷新则标记失效。
4. 列表扫描失败仍可手动输入地址；保存最近成功地址，但重新连接前检查其是否仍指向目标房间。
5. 多网卡提供 Wi-Fi / 有线候选地址及简明选择，不把 VPN、虚拟网卡或回环地址当作唯一地址。只在选定局域网接口提供服务；若发现监听需要通配绑定，应过滤接口与来源。
6. 只在等待室发现或响应发现；离开页面停止扫描。游戏中的房间可停止发布，重连凭已知地址及令牌进行。

广播可能被路由器或机型过滤；Android 数据报 API 支持广播，但实际网络的投递仍需验证。[DatagramSocket 官方文档](https://developer.android.com/reference/java/net/DatagramSocket)。后续可给发现适配器加入 mDNS / DNS-SD；它也不能绕过客户端隔离。首发 IPv6-only 网络明确提示暂不支持，不把没有 IPv4 误报为未连接 Wi-Fi。

### 7.4 TCP 帧和资源边界

```text
4 字节无符号大端长度 N + N 字节 UTF-8 JSON
```

- 长度指 UTF-8 字节数，不能用字符串字符数。C# 与 Java 明确统一字节序。
- 每帧建议上限 64 KiB；拒绝零长度、超限、非法 UTF-8、非法 JSON、超深嵌套和未知必填字段类型。
- 处理半包、粘包、部分读取、EOF、连接中断和半包超时；一次 `Read` 不保证得到整条消息。
- 同一连接由单一写队列串行发送；缓冲区有上限，超过阈值断开并进入重连，不无限积压。
- 不发送逐帧坐标；只发送发射操作、裁决事件、规则状态和小棋盘快照。
- 探索 `TCP_NODELAY` 对小包延迟的影响，以实测决定；不把关闭 Nagle 当作所有延迟问题的解法。

## 8. 协议、同步与确定性

### 8.1 版本与身份

一次握手包含 `appVersion`、`protocolVersion`、`rulesetId`、`rulesHash`、`contentHash`。协议主要版本不兼容或规则 / 内容哈希不同就禁止准备。应用补丁版本可以不同，但只有已验收的兼容组合才能放行，不能只比较显示版本号。

分清以下标识：

- `roomId`：每次创建房间生成，销毁后不复用。
- `matchId`：每次“再来一局”更新，阻止上一局消息影响新局。
- `playerId`：由房主分配并绑定连接，不能信任客户端任意填值。
- `connectionEpoch`：重连后更新，拒绝旧连接迟到的数据。
- `clientSeq`：每玩家每局单调递增的命令号，重连时延续。
- `serverSeq`：房主裁决事件的全局序号。
- `boardRevision`：每名玩家棋盘的修订号，避免对手变化使自己的发射被误判过期。

### 8.2 最小消息集

| 消息 | 方向 | 用途 |
| --- | --- | --- |
| `HELLO / WELCOME / REJECT` | 双向 | 协议、身份、规则、加入状态与重连凭证 |
| `ROOM_STATE / SET_READY` | 双向 | 房间设置、玩家列表和准备状态 |
| `PREPARE_MATCH / LOADED` | 双向 | 初始快照、内容校验和加载屏障 |
| `START_AT` | 房主 → 双方 | 约定房主时间上的未来开局时刻 |
| `SHOT` | 玩家 → 房主 | 发射角度、命令号、自己的棋盘修订号 |
| `COMMAND_RESULT` | 房主 → 发起者 | 明确接受或拒绝及原因，携带对应命令号 |
| `STATE_COMMIT` | 房主 → 双方 | 裁决事件、双方状态、序号及逻辑冷却 |
| `PING / PONG` | 双向 | 连接心跳、往返时延与时钟偏移估计 |
| `RESYNC / SNAPSHOT` | 双向 | 修订不一致、重连后的全量恢复 |
| `PAUSE_REQUEST / PAUSE_STATE / RESUME_AT` | 双向 | 暂停请求、冻结状态和共同恢复 |
| `MATCH_RESULT / RESULT_ACK` | 双向 | 唯一最终结果及接收确认 |
| `REMATCH_READY / LEAVE / ROOM_CLOSED` | 双向 | 再来一局、主动退出和房间销毁 |

示例命令；字段是接口设计，不是当前源码已有类型：

```json
{
  "type": "SHOT",
  "protocolVersion": 1,
  "roomId": "room-opaque-id",
  "matchId": "match-opaque-id",
  "connectionEpoch": 2,
  "clientSeq": 18,
  "boardRevision": 35,
  "payload": { "angleMilliDeg": -32500 }
}
```

角度以千分之一度的整数表达，范围沿用当前 ±78°；双方转换成相同弧度再调用 `traceShot`。客户端可发送诊断哈希，但不上传可信的分数或落点。房主必须自行计算弹道，不能仅用“这个格子能贴球”来验证发射。

### 8.3 一次发射怎么同步

1. 客户端依据最近确认的状态本地瞄准，可以立即展示炮口、音效和预测弹道；最多存在一条未确认发射，不在等待确认期间继续推进随机数和保存得分。
2. 原生层收到命令，房主将其放入统一的有界队列。
3. 房主检查身份、局 ID、命令序号、棋盘修订、角度、状态、冷却、截止时间；无合法落点则拒绝，不罚负、不消耗球。
4. 房主使用固定逻辑几何调用 `traceShot`，再调用消除规则；提交分数、棋盘、RNG、下一球和下一次可发射时间。
5. 广播 `STATE_COMMIT`。客户端以该状态确认预测；若不同，取消旧动画、替换到权威棋盘并给出轻提示，不能重复累计得分。
6. 客户端落后或修订不符时先应用全量快照，再重新瞄准；不默默把针对旧棋盘的发射改到新棋盘执行。

在 TCP 连接内部无需再实现一套丢包重传协议，但业务命令仍需去重：房主缓存命令结果，重复的 `clientSeq` 返回相同结果，不再次执行。重连后先查最后处理序号和快照：已处理命令只取回原结果；房主尚未处理的旧命令标记取消，不在恢复后重放。玩家恢复操作后重新瞄准，用新的命令号发射，避免出现“回来就自动打一球”。

### 8.4 快照与时钟

首发棋盘只有 14×19，优先传完整快照，降低恢复复杂度；先测量带宽，再决定是否增加增量压缩。每次规则提交发送状态；无变化时每秒发送轻量时间 / 校验状态，按需请求全量快照。

快照至少包含：房间 / 局身份、规则标识、裁决序号、双方 `GameState`、累计分、波次、独立 RNG、棋盘修订、剩余活动时间、下一次自然下压时间、逻辑冷却、最后处理命令号、暂停原因；后续模式再加入攻击队列或回合信息。不能只保存 `board + score`。

校验哈希基于固定字段顺序的规范序列化，排除 UI、音效、本地昵称显示状态等非规则数据；它用于检测分歧，不作为身份认证。跨 JS 引擎数学细节导致预测差异时，仍以房主快照为准；黄金操作集必须在真实 Android WebView 与 Windows WebView2 都跑过。

比赛使用单调时钟和“已活动时长”，不用两台设备的系统日期差决定输赢。首次交换多次 `PING/PONG` 估计偏移，之后平滑校正显示；同步倒计时约定至少 3 秒后的开局时刻。客户端没收到可确认的开局状态则保持不可操作，不自行开始计时。

建议以 50 毫秒为一次权威处理批次，规则变化后立即广播。一般优先级为：终局 / 暂停门禁 → 截止检查 → 已到期规则事件 → 合法发射 → 模式结算；连锁对战的同批次防御与攻击按第 4 节单独排序。调度严重停顿时冻结恢复，禁止一次补跑全部后台期间的下压。

## 9. 暂停、后台、断线与退出

### 9.1 房间状态机

```text
IDLE → DISCOVERING 或 HOSTING → LOBBY → PREPARING → COUNTDOWN → PLAYING
PLAYING → PAUSED → COUNTDOWN → PLAYING
PLAYING / PAUSED → RECONNECTING → 快照恢复 → COUNTDOWN → PLAYING
PLAYING → FINISHED → LOBBY
任意活动状态 → CLOSED
```

玩家还有独立的 `connected / ready / eliminated` 状态，不能把一人触底误当房间关闭。

### 9.2 行为规则

| 场景 | 建议行为 |
| --- | --- |
| 打开音量等小设置 | 遮罩不暂停整个比赛；不允许重启棋盘、导入备份或切换规则 |
| 主动请求暂停 | 对方同意后房主广播冻结；每人每局 1 次，最长 30 秒，双方提前就绪可恢复 |
| Android 切后台、Windows 最小化 / 锁屏 | 尽可能先通知房主，双方冻结比赛；进入短时恢复，不回单机首页 |
| Windows 普通失焦 | 清除按键和音频焦点；是否触发冻结依前台策略统一处理，避免每个小弹层误判后台 |
| 短暂断网 | 心跳异常后停用新输入，显示正在重连，保留当前画面 |
| 主动离房 | 显示“离开将结束本局”；竞分 / 对战记录退出方认输，协作记录中断 |
| 房主正常退出 | 尽力发送 `ROOM_CLOSED`；比赛结束，双方回联机入口 |
| 房主进程崩溃 / 被杀 | 无房主迁移；无法在时限内恢复则记为中断，不猜测胜者 |
| 客人断线超时 | 本局中断、没有胜负；房主可回等待室重新邀请 |

心跳建议每秒一次，连续 3 秒没有有效回应进入重连；最多等待 20 秒。一次比赛允许至多 3 次自动恢复、累计等待不超过 60 秒，超过则中断，防止反复切后台无限拖延。所有阈值通过真机调整。

连接心跳和规则存活分开检测：原生服务即使还能回复网络心跳，也必须携带最近一次 JS 权威活跃标记。长时间没有规则推进 / 活跃标记时进入恢复，不能把“socket 没断”显示成比赛正常。

### 9.3 恢复原则

房主冻结最后一份已经提交的权威状态、活动时长和待处理规则计时；暂停期间不扣比赛时间，不追补后台产生的下压。状态无需得到对方 ACK 才算已提交，ACK 丢失通过序号和快照修复，不能撤销已接受的发射。

非正常挂起后，调度器首先检查原生生命周期标记与过大的时间间隔，进入恢复而非推进时钟。恢复后双方确认快照，发送新的 `RESUME_AT` 并短倒计时；清空旧触控、按键、瞄准缓存和失效动画，避免回来就误发射。

重连需要匹配房间、局、玩家身份和随机恢复令牌；新连接替换旧连接并增加 epoch。恢复令牌仅保存在本次会话内，不进备份、不写日志。首发只恢复仍在同一进程且状态未丢失的会话，WebView 重载或进程重启不假装恢复成功。首发按已知地址重连；若切网导致房主地址改变，恢复失败则明确提示网络已变化并中断本局。后续可增加按房间 ID 的限时重新发现。

终局结果带唯一 `resultId`，客户端按它去重保存。未收到权威结果的一方先标记“结果未确认”，允许在结果保留窗口内重取；不能根据本地倒计时单独宣判胜利。网络中断后已收到的正式结果不撤销。

## 10. 原生平台实现

### 10.1 Windows

新增 `windows/LanService.cs`，承载监听、客户端连接、UDP 发现、网络接口选择、发送队列和关闭清理。由 `Program.cs` 创建并管理其生命周期。

- JS → 原生：沿用 `window.chrome.webview.postMessage`，新增带命名空间的请求，如 `{ type: 'lan', requestId, action, payload }`。
- 原生 → JS：通过 `PostWebMessageAsJson` 发响应和事件；返回 UI 线程后投递，不逐包拼接 `ExecuteScript` 字符串。
- 桥接只接收受信任的本地应用源消息，并校验动作、尺寸与字段；网络包不得直接转成可调用任何宿主能力的消息。[WebView2 安全建议](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/security)。
- 使用 net48 支持的 API 与当前编译器语法；关闭 socket 解除阻塞读 / accept，不能照搬只在新 .NET 可用的取消参数重载。
- 现有打包脚本显式编译 C# 源文件，新文件必须进入编译列表，并扩展原生测试入口。
- 不自动关闭防火墙、开启路由器端口映射或要求管理员常驻。首次建房若被防火墙阻止，说明如何允许该应用在可信专用网络通信，并提供重试。
- 发布测试要覆盖 ZIP 解压到新路径后的网络行为；不能只在开发路径验证放行规则。
- 当前外壳会挂起 WebView；联机时先冻结并通知，再按恢复流程处理。窗口关闭由原生服务直接尽力发送离房及释放连接，不能只依赖 JS `beforeunload`。

### 10.2 Android

新增 `LanMultiplayerPlugin.java` 与网络服务类，在 `MainActivity` 注册。使用 Capacitor 的方法调用和事件回传；设计可参照[官方 Android 插件说明](https://capacitorjs.com/docs/plugins/android)。

- socket 读写、监听和发现放入专用执行器，不阻塞主线程。
- 事件队列有界；WebView 暂停后不无限保留每一个历史事件，恢复以最新快照和明确握手为准。
- 当前 `minSdk=24`、`compileSdk=36`、`targetSdk=36`，清单已有 `INTERNET`。按需增加网络状态查询权限，普通手动局域网连接不要求用户扫描 Wi-Fi 或授予定位。
- 官方当前说明：target 36 及以下仍通过 `INTERNET` 获得局域网访问；升级到 target 37 及以上时，直接局域网通信需处理 `ACCESS_LOCAL_NETWORK` 运行时权限。应封装权限入口并测试拒绝、撤销、重试；不要在当前 target 36 构建中盲加并请求新权限。[Android 局域网权限](https://developer.android.com/privacy-and-security/local-network-permission)（核验于 2026-10-15）。
- 若测试 Android 16 的选择性局域网限制，按同一官方文档单独配置测试环境，不能把测试开关的行为误当所有已发布设备的默认行为。
- `onPause` / `onStop`、网络变更、页面销毁、旋转重建均纳入会话生命周期；退出清理线程、监听器和端口。
- 无外网 Wi-Fi 与蜂窝并存时，不能把系统默认网络等同局域网，也不能以互联网验证成功作为局域网的准入条件。必要时通过选定 `Network` 的 socket 工厂或绑定 API 使用该网络，网络状态查询与回调配套声明 `ACCESS_NETWORK_STATE`。
- 房间和对局前台可使用保持屏幕常亮，离开后恢复；首发无需前台常驻服务，不承诺锁屏后继续比赛。
- 热点地址从有效接口获取，不硬编码某个网关 IP；未验证的热点机型在兼容记录中注明。

联机历史使用新键，如 `orbbound-lan-history-v1`。每条包含 `matchId/resultId`、模式、规则版本、难度、时长、自己与对手的结果摘要、结束原因、是否确认；最近 100 局足够。对手昵称是当局输入，不作为永久账号身份。断线中断记录不算胜败，也不进入任何分数榜。

## 12. 基本防护与诊断

这是局域网休闲游戏，房主权威能阻止普通客户端直接上报假分，但不能防止恶意房主修改程序。首发不设可兑换奖励或可信公开排行。

- 接入默认经过房主允许 / 准备确认；房间只有两个正式席位。握手连接设时限并限制并发，拒绝多余连接。
- 对请求尺寸、频率、JSON 类型、角度、序号、名字长度做校验，不能让异常包使游戏崩溃。
- 只绑定选择的局域网接口，不自动做公网映射；不因实现方便开放通用文件读取或任意执行桥接。
- 不传个人存档、系统路径、设备序列号、账号或密码。随机重连令牌用于会话识别，但明文 TCP 不提供保密或对抗主动窃听的身份认证。
- 首发按可信家庭 / 朋友网络设计；若要支持公共网络和敏感信息，再独立设计基于成熟 TLS 的配对流程，不能把短房间码或自制加密当作安全保证。
- 本地诊断保存有限的连接事件、错误码、协议、RTT 和裁决序号，不保存恢复令牌；导出前展示内容范围。

建议错误码包括 `ROOM_FULL`、`VERSION_MISMATCH`、`PERMISSION_DENIED`、`CONNECT_TIMEOUT`、`NETWORK_CHANGED`、`STALE_STATE`、`HOST_UNAVAILABLE`、`PROTOCOL_ERROR`。界面给具体下一步，不统一显示“网络错误”。

## 13. 开发阶段与交付物

按一名熟悉仓库的开发者估算，P0 约 15～23 个工作日，包含双端实现与实机验证，不包含 P1 新模式；实际以原生链路验证结果调整。它是工作量估计，不是发布日期承诺。

| 阶段 | 工作 | 完成门槛 | 估算 |
| --- | --- | --- | --- |
| S0 原生链路验证 | 两端建房 / 加入、TCP 拆包、UDP 发现、手动地址、热点 | 四种房主 / 客人组合都交换完整快照；记录权限和防火墙行为 | 2～3 天 |
| S1 抽离联机规则 | 控制器、房主裁决、统一时钟与冷却、种子波次 | 无 UI 的完整竞分局可回放；单机测试通过 | 3～5 天 |
| S2 可玩房间 | 等待室、准备、开局、双方棋盘、3 / 5 分钟、结果、再来一局 | 真机可稳定完成两轮比赛，无重复分数或单机记录污染 | 4～6 天 |
| S3 故障恢复 | 重连、后台、拒绝、退出、版本兼容、缓冲限制 | 故障用例产生一致状态与可理解提示 | 3～4 天 |
| S4 发布验收 | 性能、长局、跨端公平观察、回归、打包 | 完成第 14 节并保存证据 | 3～5 天 |

S0 如果发现目标热点普遍不可互通，应先调整支持范围或发现方案；不要在核心链路未打通时先做完整大厅动画。S1 和 S2 合并时也必须保留可独立测试的裁决层。

P1 的连锁对战与协作接力分别估算约 5～8、4～7 个工作日，平衡试玩和新关卡内容可能追加时间。只有 P0 稳定后再安排，不把三个模式绑成一次大版本才交付。

发布时两端一起更新协议与规则，版本号在实施时确定。各自生成 APK、Windows ZIP、校验值、更新说明与兼容表；本方案不预设已经发布的新版本，也不触发上传。

## 14. 验收方案

### 14.1 自动化：验证真实风险

1. **规则复现**：固定种子、角度、活动时间与事件序列，复现清盘换波、自然下压、触底和截止；对比双方完整状态与最终结果。
2. **输入验证**：非法角度、非法落点预测、过期棋盘、冷却中发射、冒用身份、旧局命令、重复命令均不能改分。
3. **边界排序**：截止前一批 / 截止批次、清盘与下压重合、发射与暂停重合、双方触底、同分平局、断线与结果确认相撞。
4. **协议解码**：每个字节边界拆帧、多个消息粘连、中文昵称的 UTF-8 字节长度、超限 / 畸形 / 半包超时、队列压力与资源释放。
5. **恢复**：已提交但 ACK 丢失的发射只执行一次；旧 epoch 消息无效；重连恢复 RNG、冷却、时间和波次；结果去重。
6. **跨语言传输**：C# 与 Java 共享帧测试向量，验证大端长度与 UTF-8；原生测试使用相应平台真实可用 API。
7. **单机回归**：执行现有 `npm test` 与构建，覆盖历史存档、限时、30 关、计分、备份和输入；新增模式不污染任何单机键。

建议增加 `tests/lan-authority.test.ts`、`lan-protocol.test.ts`、`lan-reconnect.test.ts`，配假时钟和模拟传输。模拟器按延迟、断开、重复业务请求和旧消息注入；TCP 内的网络丢包通过真实链路故障测试，不伪装成应用层必然乱序。

### 14.2 原生互联矩阵

| 房主 | 客人 | 必测连接环境 |
| --- | --- | --- |
| Windows | Android | 同一路由器；电脑有线 + 手机 Wi-Fi；Windows 热点 |
| Android | Windows | 同一路由器；Android 热点 |
| Android | Android | 同一路由器；手机热点，至少两种实际可用机型组合 |
| Windows | Windows | 同一路由器；不同电脑与发布目录 |

每个支持组合都验证建房、发现、手动加入、至少两局、重连、结果一致和退出清理。还需覆盖：无互联网但 LAN 正常、Android 无外网 Wi-Fi 与蜂窝同时开启、UDP 被阻断但 TCP 可达、网络隔离、IP 改变、TCP / UDP 端口分别被占用、防火墙拒绝、VPN / 多网卡、版本不匹配、IPv6-only 明确失败提示。

Windows 覆盖最小窗口、全屏切换、最小化 / 锁屏 / 睡眠和 WebView 故障。Android 覆盖后台 / 锁屏 / 返回键 / 输入法 / 旋转 / 杀进程，最低支持版本及至少一台较新系统；当前 target 36 行为与未来 target 37 权限分支分开验证。

### 14.3 建议性能和质量门槛

以下均需在声明过的测试设备与网络下测量：

| 指标 | 首发目标 |
| --- | --- |
| 普通家庭网络发现房间 | 进入列表后 3 秒内出现；失败可手动加入 |
| 手动加入到等待室 | 正常网络下 5 秒内，超时可取消 |
| 发射提交到收到权威确认 | 正常低延迟 LAN 的 p95 ≤ 150 毫秒；本地瞄准持续可响应 |
| 开局与剩余时间显示偏差 | 稳态目标 ≤ 100 毫秒；统计分位和异常值 |
| 联机常态流量 | 每个方向目标 < 30 KiB/s，剥离开发日志后测量 |
| 连续使用 | 30 分钟、至少 10 次重开无持续内存 / 线程增长 |
| 正确性 | 结束时双方结果完全一致；不重复计分、不多发球、不写入单机排行 |
| 恢复 | 连接恢复后拿到完整快照才解锁输入，超时后能够退出与重新建房 |

记录原生真机日志、平台 / 系统 / 网络环境、规则版本和失败复现步骤。浏览器两个模拟客户端通过只能证明共用逻辑，不代替 APK 与 Windows 成品的互联验收。

## 15. 开发启动时的默认决定

为避免实施阶段重新发散，建议采用以下默认值；玩法试玩后调整必须同步规则版本和测试：

- **P0 只发布同图竞分，2 人，默认普通难度、3 分钟，可选 5 分钟。**
- **两端均可建房和加入；原生 TCP + UDP 发现 + 手动地址，先保证 IPv4 可互通网络。**
- **房主裁决全部状态，本地预测只服务操作反馈；规则、时钟、冷却与动画解耦。**
- **明确相同开局，不承诺整局同球序；对手棋盘始终可见，但不挤压自己的操作区域。**
- **前台游玩、短时冻结恢复；房主进程消失则中断，不做首发房主迁移。**
- **独立联机历史，不影响单机记录、存档、关卡与星级。**
- **先通过 S0 的双端互联，再进入完整玩法；实现与验收完成后再决定发布版本号。**
