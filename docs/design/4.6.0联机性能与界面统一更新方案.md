日期：2026-10-18

基线：4.5.0，提交 `ffbeb53`。

状态：**实现完成，进入候选包验收。** 共享棋盘、固定帧率与迁移、连续展示钟与缓存、暂停新规则及地址优先流程已落地，双端版本已调整为 4.6.0。以下保留基线排查及验收标准；最终构建、安装与设备性能结果以[验证记录](../releases/4.6.0-validation.md)为准，完整真机矩阵与同条件性能对比仍待补齐，最终发布另行执行。

## 1. 更新范围与行为约定

| 范围 | 4.6.0 实现行为 |
| --- | --- |

| Android 联机流畅度 | 修复房主动画时间阶梯，减少多人重复绘制，让动态主棋盘按所选目标帧率运行 |

| 双端棋盘 | 联机竞分、对战的主棋盘统一为闯关、无尽、限时使用的视觉样式；共享球体、场地、炮台、瞄准和基础动效 |

“默认 60”指应用的默认活动绘制目标，不承诺硬件、系统或过载情况下每秒必然显示 60 个不同画面。静止页面可以按需绘制，必须与动态掉帧分别统计。画面清晰度的“自动”是独立选项，继续保留。

暂停的“仅保留间隔”针对申请额度：不再有“一人一次”或“累计两分钟后不能申请”。**单次暂停最多 60 秒、投票等待 10 秒及关闭设置/恢复确认超时继续保留**，用于结束一次流程；不因用满一次或多次而耗尽整局资格。掉线恢复规则不属于主动暂停次数限制。

快照并非固定每 50ms 全量广播：当前按棋盘变化、表现事件、结束或约一秒保活触发。性能优化须先测量，不能直接把规则 tick、网络发送和画面 FPS 混为一谈。

## 3. 固定帧率设置及旧数据迁移

### 3.1 运行策略

1. `FrameRateSetting` 仅保留数字 `30 | 60 | 90 | 120`，默认请求值及初始目标均为 60。
2. 单机和联机继续通过统一的 `FrameBudget` 调度，删除 auto → 120、持续负载自动升降帧档的运行分支。不能只隐藏选项后保留自动降至 30 的路径。
3. 原始 rAF 间隔用于诊断，不再把“忙导致回调变慢”的估值反过来当作屏幕上限降档。可信原生显示能力与系统实际限频单独报告；未知能力不能被当成已确认的硬件上限。
4. 保留温度、省电与显示能力信息，用于解释实际限制，以及独立自动画质策略的有界调整；不把用户保存的 60 静默改为 30。系统自身的温控、后台和刷新率限制继续生效。
5. Android 首次和恢复前台请求所选固定刷新率，默认 60；请求失败有界返回，不阻塞游戏。原生后台 `fps=0` 用于释放窗口偏好，必须保留，它不是用户的“自动帧率”。
6. 保留静止按需重绘和后台暂停；输入、发射、收到新状态、动画开始、观战切换应在下一可用帧唤醒，不能等待静止绘制间隔。
7. 性能信息区分请求目标、有效调度目标、实际绘制及静止状态。活动帧率不与静止 5 / 10 FPS 混算，不能再显示过时的“自动适应设备，最高 120 FPS”。

不要给 Phaser 额外叠加固定 `limit:60`，否则保留的 90 / 120 手动档会失效；也不要为了增加绘制次数提高联机规则 tick。

### 3.2 迁移规则

| 输入来源与旧值 | 结果 |
| --- | --- |
| 新安装、默认设置、分类或全部恢复默认 | 数字 60 |
| 本地旧设置 `'auto'`、帧率字段缺省或非法 | 该字段回退 60；其余有效设置及存档保留 |
| 整体设置 JSON 已损坏，无法读取字段 | 按默认设置加载，不删除独立存档和历史；不能宣称仍能恢复损坏文本中的其他字段 |
| 本地合法固定档 30 / 60 / 90 / 120 | 保留原选择，不强制全部重置 |
| 旧备份含设置，其中 frameRate 为 `'auto'` 或缺省 | 兼容导入为 60，规范化后再保存 |
| 备份完全不含设置项 | 继续保留当前设置，遵守部分导入语义 |
| 备份帧率为损坏值或包含其他无效字段 | 保持严格校验并给出错误，不借迁移放宽整个备份格式 |
| `quality:'auto'` | 保留，不进行全局字符串替换 |

统一帧率归一化覆盖 `storage.ts` 的读取/保存、`settings-store.ts` 的实时更新与重载、备份导入/恢复副本、旧 Windows 数据迁移。备份预览只验证和生成规范化结果，不提前写存储；导出不得把磁盘遗留的旧 auto 再次带出。

修改范围：`src/game/frame-rate.ts`、`src/game/runtime.ts`、`src/storage/storage.ts`、`src/storage/settings-store.ts`、`src/storage/backup.ts`、`src/ui/settings-panel.ts`、`src/ui/platform-services.ts`、`src/ui/lan-board.ts`、`src/main.ts`。历史版本说明保留原貌，只更新当前说明与 4.6.0 文档。

## 4. Android 联机流畅度修复

### 4.1 将展示时间与规则时间分开

已新增纯展示时钟 `PresentationClock`，通过 `LanSession.presentationTime()` 每帧采样绝对逻辑时间：

- 房主以最近有效权威进度及其本地采样时刻为锚点，客人以接收快照及其本地时刻为锚点；与事件 `atMs` 统一到同一逻辑时间坐标。
- playing 连续推进，paused / reconnecting / 恢复倒计时冻结；恢复、换局、epoch 改变时重新建锚，不能把后台耗时补成动画或比赛时间。
- 新锚点处理小范围校正，不能在普通快照到达时让同一动画反复倒退；换局和重连属于显式重置。
- finished 的有限尾动画使用独立展示进度，不延长比赛或改变结算时间。
- 应用到本机主画布、对手小图及观察主视图，统一处理表现事件的去重、过期与结束。

**不直接改现有 `displayElapsed()` 的语义。** `lan-board.ts` 的 `canFire()` 也用它检查比赛期限与 `readyAtMs`；连续展示插值不得提前放开发射，不能修改权威快照、计分、下降、攻击、冷却或事件阶段时长。当前规则 50ms 批处理继续保留。

### 4.2 降低无效工作

- 动画忙碌、dirty 和 revision 按玩家/画布管理，任意对手动效不再迫使全部画布同步重绘。
- 球体使用缓存图像；场地与已落位棋盘使用静态缓存，动态层只处理炮台、轨迹、飞行、掉落和反馈。
- 按表现事件缓存消除列表及过渡棋盘，不在每个动画帧复制整盘；缓存随事件结束释放，限制数量。
- 观察弹层纳入统一调度；只读观战不显示本机瞄准角度，也不伪造未同步的对手实时瞄准。
- 主图和缩略图采用统一像素预算策略，按角色设置不同上限；不为三张小图配置完整主画布分辨率。质量或尺寸确实改变时才重建 backing store。
- 控件文案、disabled、音频场景与压力只在相关值改变时更新；将这些开销纳入完整帧采样，保留 4.5.0 已修复的音量修改不重建画布行为。

对手小图仍可约 20 FPS，静态主图仍可按需绘制；动态主图和打开的观察主视图按所选目标调度。只有实际轨迹证实网络解析、序列化或原生队列占主导后，再优化相应链路，不先增加发包频率或重写传输协议。

### 4.3 真机采样与建议目标

在同一 Android 设备、同一画质、种子和棋盘状态下对比 4.5.0 与候选 4.6.0，记录 WebView/系统版本、面板模式、温度、省电及网络条件。

分别记录 rAF、真实绘制、动画逻辑进展、规则 tick、消息频率；分解完整一帧中的权威计算、HUD、编码/解析、主图、小图和观察层。性能轨迹需覆盖双方作为房主/客人及 2 / 3 / 4 人，不能只看 FPS 徽标。

建议验收目标：在设备持续提供至少 60Hz、无系统限频的默认 60 档条件下，连续瞄准与动画区间平均绘制 ≥55 FPS、帧间隔 p95 ≤25ms；主动画不再出现由固定 50ms 展示钟造成的阶梯。大规模同时消除单列长帧与耗时，不用静止帧或简单场景掩盖。以上仍为待测目标，完整同条件真机性能对比尚未完成。

## 5. 主棋盘统一与 Windows 提示删除

### 5.1 以三种单机的现有外观为基准

| 元素 | 统一结果 |
| --- | --- |
| 场地 | 单机圆角内框、顶板、底部暗槽、细横线、顶部圆点、触底说明与危险线 |
| 球体 | 同源颜色、符号、内描边、高光及两个眼点；统一可见尺寸与炮口缩放 |
| 炮台 | 分层底座、圆角炮管、当前颜色带、箭头和有界后坐力 |
| 瞄准 | 同一物理 trace 的等距离圆点、反弹标记与落点双圈；关闭辅助时保持一致的方向提示 |
| 动画 | 共享消除、掉落、下降和得分反馈的视觉参数；联机阶段时长及权威结果不变 |
| 外层画布 | 同平台共享圆角、边框、背景和比例约定，适配不同可用空间 |
| 当前/下一球 | 同平台采用一致预览位置与语义；Windows 不再出现独立当前球副本，不重复放置下一球 |

### 5.2 共享资源，保留两个适配器

已新增以下共享职责，并保留两种渲染适配器：

- `src/render/board-appearance.ts`：单一视觉尺寸、颜色、场地、炮台和瞄准定义。
- `src/render/board-artwork.ts`：共享球体/场地/底座/炮管的绘制与有界缓存；Phaser 注册同源纹理，Canvas2D 使用同源图像。
- `src/render/board-view.ts`：只读显示模型，明确 main / thumbnail / observation 角色，以及压力、rowOffset、目标圈、预览和动画状态。
- 两个渲染适配器消费上述定义：`PlayScene` 保留单机状态机、输入和存档；`LanSession` / `LanPresentation` 保留权威同步与表现事件。

静态缓存可使用普通离屏 HTMLCanvas，不把可选的 OffscreenCanvas 作为 Android 必要条件。不能将 Phaser 现有按格复用退化为每帧重建所有球，也不能每帧重画整盘再上传成纹理。资源在尺寸/质量变化、退出重进时有明确复用和释放规则。

物理 `BOARD_GEOMETRY` 的半径、坐标、边界、下降、匹配和输赢条件保持不变。例如统一危险线外观到单机位置，不等于修改物理触底边界。

对手缩略图复用相同球体与场地，可省略长说明、轨迹、炮台和复杂得分特效。联机昵称、排名、延迟、攻击队列和暂停投票继续存在；主棋盘样式统一不要求这些信息与单机相同。

### 5.3 Windows 黄圈项的精确修改

仅在 Windows 构建下跳过 `createArena()` 的额外“当前球”文字，以及 `renderLauncher()` 中坐标 `(478,698)`、取 `currentColor` 的放大预览。炮口的 `launcherOrb` 与 DOM 的 `nextColor` 预览继续随发射更新。Android 与普通网页原有预览行为保留。

回归时使用 `currentColor != nextColor` 的状态，避免当前球与下一球颜色相同掩盖误删、错用。`tests/windows-platform.test.ts` 中原本要求该副本存在的断言应改为验证其消失，而不是删除整个预览测试。

## 6. 联机暂停：取消额度，保留间隔

### 6.1 新规则

| 项目 | 4.6.0 行为 |
| --- | --- |
| 每人每局成功次数 | 不限制，删除 `pauseUsed` 的判断、记录和重置 |
| 整局累计暂停 120 秒 | 删除预算门禁和累计核算，不再使后续暂停缩短或失去资格 |
| 申请间隔 | 同一选手 15 秒，暂停与“申请暂停以调整设置”共享，房主权威校验 |
| 成功后的间隔起点 | 本次暂停实际恢复到 playing 后开始计 15 秒，不能在暂停中先耗尽冷却 |
| 拒绝、取消、投票过期后的间隔 | 结果确定时开始计 15 秒 |
| 冷却中重复点击 | 返回当前剩余时间，不滑动延长已有截止时间；不能被反复点击无限续期 |
| 重复包 / 相同 requestId | 返回已记录结果，不重复投票、扣时间或重置冷却 |
| 投票与单次时限 | 活跃选手全体同意；投票最多 10 秒；单次暂停最多 60 秒 |
| 恢复流程 | 关闭设置确认、准备、共同倒计时继续保留；封盘/弃权选手的申请资格沿用现有规则 |

冷却绑定房间内稳定选手身份，并使用房主时钟；重连、更换“暂停/设置”入口不能绕过，同局重连也不能清空。新的一局重置该局冷却。不同选手各自计时，不额外增加新的房间总次数上限。

重构 `reportPause()` 当前“所有非 approved 都重设冷却”的行为，区分一次申请结束与仅因冷却/并发被拒，防止重发请求持续推迟冷却。成功申请人需保留到恢复边界，以正确建立成功冷却。

单次到期仍进入既有关闭设置、确认与恢复流程，不在设置未关闭时穿透开局。`recoveryCount`、掉线单次/累计恢复预算是另一套机制，继续保留。

### 6.2 兼容策略

暂停已经改变联机规则，**4.6.0 不能沿用 4.5.0 的 `LAN_RULES_HASH` 并宣称可混用**。

已集中定义 `PAUSE_RULES`，包含不限次数/不限整局累计、15 秒间隔、成功冷却起点、投票和单次时限，并纳入规则指纹、更新算法修订。`LAN_PROTOCOL_VERSION=3` 保持，`LAN_RULES_HASH` 从 `79ab5744` 更新为 **`4e2a4139`**，内容指纹 `f942c2f9` 保持；旧端通过规则哈希握手拒绝，所有选手须更新到同一联机版本。

棋盘视觉、默认帧率和展示插值本身不应改变物理、内容指纹与表现事件阶段。此次规则哈希变化的原因是暂停策略。旧单机存档、历史联机结果继续可读，不迁改旧记录中的哈希；将 `lan-panel.ts` 仅凭协议 v3 就显示“4.4 规则”的历史标签改为正确映射或中性协议标签。

## 7. 房间地址优先显示

### 7.1 创建成功后直接可复制

推荐流程：填写昵称/房名 → 配置规则 → 创建成功 → **大厅首屏地址复制栏 + 玩家列表 + 准备/开始**。

- 只有原生服务绑定成功、返回 `hostInfo.addresses` 和真实端口后才展示可连接地址；创建前不生成虚假“房间地址”。
- 复制栏使用可选中的只读字段及“复制地址”按钮，内容为完整 `IPv4:实际端口`。只读地址不主动唤起 Android 输入法。
- 多网卡时默认展示一个候选地址，并允许切换其他地址；复制当前所选项，不能复制固定端口或过期地址。可保留二级页展示更多网络详情。
- 在用户点击复制后调用统一复制能力，成功才显示“已复制”；失败保留可选字段，提示长按/手动复制。先验证 WebView / WebView2 的现有剪贴板能力，确有缺口再补最小原生接口。
- 没有有效局域网地址时给出明确连接网络提示，禁用无效复制/开始；广播不可用但有有效地址时，仍可复制并通过地址加入。
- 地址栏在玩家就绪、规则变更、重连刷新时保留，不因 50ms 会话通知反复重建、丢失选择或焦点。重新创建房间后更新为新端点。

不自动覆盖系统剪贴板；创建成功显示复制入口，不等于未经点击就执行复制。

### 7.2 加入默认展开地址栏

- 进入“加入房间”默认选中“地址”，直接看到昵称、房主地址和“加入”按钮；不再先切换“附近 → 地址”。
- 沿用已保存的上次输入；没有记录时留空并给出格式示例，不将示例当实际地址。
- `browse()` 的进入浏览状态与广播发现解耦，地址输入和直连不等待广播扫描。附近扫描在选择“附近”或点击检索后启动，扫描失败不阻止地址输入。
- 保留附近、最近、诊断入口及“填入地址”；选择发现或历史端点后填回同一输入字段，继续使用统一解析和连接逻辑。
- 切换加入方式、发现结果更新、键盘开合与连接失败返回后，保留昵称、地址、光标和错误提示；Android 原生 IME 状态链沿用 4.5.0 修复。
- 用户明确点击“加入”才连接；有界等待、防重复提交、取消退出及旧会话隔离继续有效。

此部分主要修改 `src/ui/lan-panel.ts`、`src/ui/lan.css` 和 `src/lan/session.ts` 的浏览入口，复用 `src/lan/transport.ts` 的地址解析；需要补统一复制工具时单独测试，避免把复制失败当房间创建失败。

## 9. 验收矩阵与发布门槛

### 9.1 自动测试

- 帧率：扩展 `frame-rate.test.ts`、`performance-runtime.test.ts`、`platform-refresh.test.ts`，覆盖默认/恢复 60、旧 auto、非法本地值、30/90/120 保留、高刷新回调限帧、后台与连续输入唤醒、没有隐藏负载降档。

- 展示：扩展 `lan-session.test.ts`、`lan-presentation.test.ts`、`lan-controls.test.ts`，用可控时钟证明两次权威 tick 之间动画持续前进，暂停/恢复/epoch 重基正确，规则结果与发射门禁不受插值影响。

- 暂停：同一选手成功暂停至少三次；累计超过旧 120 秒仍可再次申请；成功恢复后及失败后 15 秒边界、重复/乱序包、冷却中重试不续期、切入口/重连不绕过、多人同时申请、单次超时及设置关闭恢复。
- 地址：创建后实际端点直接可见；多地址切换、真实端口、复制成功/失败、无网络、默认地址加入、不依赖发现、输入保留、取消与迟到结果；4.5.0 双向握手应清晰拒绝。

### 9.2 设备与场景

| 维度 | 必测内容 |
| --- | --- |
| Android | 当前实体机作为房主和客人，补较低性能设备；记录 WebView、60/高刷新、省电/升温状态；默认与沉浸操作 |

| 联机 | 竞分/对战 × 2 / 3 / 4 人；Android 与 Windows 双向房主；同时发射、大量消除、下降、封盘、观战切换及退后台恢复 |

视觉验收覆盖六种球、rowOffset、闯关目标圈/天花板、瞄准关闭/反弹、触底、掉落、下降、换波和减少动态效果。观战不出现本机角度，也不具备发射权限。

发布阻断项：Windows 误删炮口/下一球；旧自动设置或备份仍回到 auto / 120；动态主图仍受 50ms 展示钟约束；棋盘仍是两套外观；次数或累计预算仍阻止再次暂停；冷却被绕过或持续续期；地址被藏到二级页/端口错误/复制虚报成功；输入、计时、规则、旧数据或退出生命周期发生回归。

性能改善须给出同条件基线及候选包记录，未测项不能写成通过。完整设备矩阵未完成时按测试版说明缺口，不以浏览器模拟代替原生性能验收。
