# Orbbound 4.3.0 双端联机检索优化与对战模式更新方案

日期：2026-10-16

基线：已发布的 `v4.3.0`，提交 `9389dec`；Android / Windows 共用联机逻辑。

文档状态：已按本方案实现为 4.3.1 测试版；真实服务互通、自动检查及尚未完成的人工/网络矩阵见 [4.3.1 验证记录](../releases/4.3.1-validation.md)。以下为实施依据，数值平衡仍需试玩验证。

## 1. 本次要达到的体验

1. **同一可互通局域网能够稳定找到房间。** 刷新有明确的扫描过程、结果和失败说明；一条网络路径失败，不应让其他路径一起失效。
2. **找到后可以直接加入，也可以只填入地址。** 点击“填入地址”会填入完整的 `IP:实际端口`，随后由玩家决定是否加入。
3. **新增「连锁对战」。** 每累计消除或掉落 12 个球产生一行攻击，先抵消自己收到的攻击，再压向对手；攻击提前预告，防止突然连续下移而无法应对。
4. **补齐联机表现。** 自己棋盘恢复飞行、消除、悬空掉落、下压和得分反馈；BGM 随自己的球群接近底线而加速，消除危险球群后回落。

保留「同图竞分」，两种玩法在创建房间时选择。检索、动画、音乐修复同时覆盖两种模式；对战专属规则不改变单机和竞分的胜负逻辑。

**实施顺序：先修发现与诊断，再补权威表现事件和 BGM，最后接入对战。** 首先保证朋友能找到并进入同一房间，然后确保新增攻击能够被看懂、被正确同步。

## 2. 当前问题核查

以下结论来自现有代码，区分已确认缺口和待设备确认的问题。

| 现象 | 已确认的代码情况 | 处理方向 |
| --- | --- | --- |
| 刷新没有找到同网房间 | Windows 首次全局广播失败会跳过后续定向广播；Android 广播目标共用异常处理，一处失败影响后续目标 | 每个接口、每个目标独立发送、容错和计数 |
| 多网卡或热点下发现不稳定 | Windows 的多个目标仍由同一个未绑定接口的 socket 发送；Android 仅选择一个网络作为发现入口 | 枚举并明确绑定可用 LAN 路径，支持热点接口回退 |
| 刷新后始终像在搜索 | 前端直接调用 `transport.request('discover')`，返回只代表启动；没有扫描完成、取消和空结果状态 | 新增会话级扫描生命周期 |
| 发现服务异常后刷新效果不明确 | 两端接收循环可能异常退出，而服务状态或查询定时器仍存在 | 接收故障清理、有限重建、状态通知 |
| 房间重复、列表跳动 | 当前按 `roomId:address:port` 区分，每次回应会重排；按钮操作依赖数组下标 | 按稳定房间 ID 聚合多地址，稳定排序和绑定操作 |
| 没有快捷填入 | 当前点击房间直接加入，只把地址写入存储，没有填入当前文本框的独立动作 | 增加“填入地址”按钮 |
| 消除直接消失，没有动画 | `authority.applyShot()` 已产生 `events` 和 `trace`，但 `session.acceptShot()` 没有把这些事件交给显示层；`lan-board.ts` 只播放飞行后换最终棋盘 | 传递权威动作结果，建立视觉事件队列 |
| 整盘下移也缺少过渡 | `advanceMatch()` 只输出快照，未输出带原因和时间的下压事件 | 自然下压、攻击下压、换波分别产生事件 |
| 联机 BGM 不随距离加速 | 联机只设置 `setScene('play')`，未更新 `setPressure()`；单机全局状态回调也没有联机音频所有权保护 | 联机使用自己的棋盘压力，隔离旧单机场景回调 |

当前两端的 UDP 42170、发现标识、查询 ID 和 TCP 实际端口字段基本对应，**没有证据支持“双方发现协议字段不兼容”是本次故障原因**。Windows 的 UDP ICMP 10054 处理也已存在，不能把它当作尚未实现的新修复。

仍需用真实 APK 与 EXE 区分：实际选择的接口、广播是否发出、对端是否收到、回复是否回来、是否被字段校验丢弃，以及路由器隔离、防火墙、VPN 和热点策略。现有桌面回环测试不证明手机广播发现已经正常。

## 3. 局域网检索与快捷填入

### 3.1 加入页面

页面顺序：昵称 → 扫描状态与刷新 → 附近房间 → 地址输入与加入 → 最近成功连接 → 连接帮助。

房间卡片至少显示：房间名、房主平台、玩法、人数、可加入状态、兼容状态和最近发现时间。网络信息不足时显示“未知”，不能用猜测值填充。多人网卡对应的多个地址收纳到同一张卡片。

```text
附近房间                         [刷新]
已发现 1 个房间 · 本轮查找完成

朋友的房间          Windows · 连锁对战 · 1/2
192.168.1.8:42171    刚刚发现
[填入地址]                         [加入]

房主地址  [192.168.1.8:42171              ]
已填入「朋友的房间」，点击加入即可连接。
                                 [通过地址加入]
```

交互约定：

- “填入地址”只更新地址输入框、选中房间和辅助提示，不开始连接，不改昵称；这是玩家明确选择后的填入。
- 刷新、收到新回应、房间排序变化均不自动覆盖用户正在编辑的地址。
- “加入”直接连接所选房间；始终使用发现消息中的实际 TCP 端口，不能固定写成 42171。
- 点击绑定稳定的 `roomId + endpointId`，不再绑定易变化的数组下标。
- 点击后连接前再校验兼容性与房间状态；满员或对局中显示原因，版本不兼容引导双方更新。发现状态只是提示，最终以握手为准。
- “最近连接”只保存成功握手的地址，标为历史记录；未经本轮回应不能显示成当前在线房间。
- 手机 320px 宽度下两个动作保持足够触控面积，不使用嵌套按钮。

### 3.2 一次刷新要有开始和结束

新增 `refreshDiscovery()`，不再让界面直接操作原生发现服务。

| 阶段 | 初始建议 | 界面与行为 |
| --- | --- | --- |
| 准备 | 枚举可用 IPv4 LAN 路径 | 没有可用路径立即说明，不无限等待 |
| 扫描 | 8 秒；在约 0、1、2.5、5 秒发出查询，可加少量抖动 | 显示“正在查找 · 已发现 N 个”，按钮变“停止” |
| 完成 | 到期停止本轮 socket / 任务 | 显示发现数量或“本轮未发现”，保留可编辑地址 |
| 失败 | 区分全部路径失败与部分路径失败 | 部分失败继续其他路径；全部失败显示可操作原因 |
| 取消 | 退出、停止、开始加入或被新一轮替换 | 关闭本轮资源，忽略旧回调，不弹过期错误 |

每轮具有 `scanId`，每条原生回调携带该编号。查询 `queryId` 和前端 `scanId` 关联，但各自承担网络应答匹配和 UI 生命周期隔离。快速连续点击不创建并行扫描风暴。

旧房间在刷新时保留并标为“待确认”；新回应更新 `lastSeenAt`。距最后回应 12 秒标“暂未响应”，30 秒或网络身份变化后移出当前房间列表。扫描结束后仍按时间更新标记；不在没有持续扫描的情况下声称“实时在线”。

### 3.3 双端网络实现

**第一层：逐接口广播，属于本次必做。**

1. 枚举处于工作状态、具备 IPv4 的 Wi-Fi、以太网和热点路径；去除回环、无地址和明显不适用的路径。不要仅凭接口名称猜测热点；优先依据系统网络能力、地址和路由。
2. Windows 为各有效本地地址建立明确绑定的 UDP 查询 socket；分别计算实际掩码对应的定向广播，`255.255.255.255` 只作额外尝试。一个目标异常不影响其他目标。
3. Android 优先使用 `Network` 和 `LinkProperties` 确定路径，对适用 socket 使用 `Network.bindSocket()`；热点未暴露为普通 `Network` 时，按有效本地接口地址回退并记录选路方式。不得把整个进程绑定到某个网络来解决单个扫描问题。[Android Network API](https://developer.android.com/reference/android/net/Network#bindSocket(java.net.DatagramSocket))
4. 每个查询 socket 独立收回复；以实际 UDP 来源地址作为候选连接地址，使用应答内的实际 TCP 端口，不直接信任应答内自报的任意地址。
5. 房主端保留单一 UDP 服务端口，按实际入口/路由返回单播回应；需要时明确选择本地回复路径。避免在 Windows 上依赖多个 wildcard socket 争抢 42170 或不一致的端口复用行为。
6. Android 房主来源过滤覆盖所有允许的本地 LAN 路径，不只核对最先选中的一个子网。首版不承诺跨 VLAN 自动发现。

**第二层：少量已知地址的 UDP 单播探测，属于本次兜底。**

广播发送的同时，对当前网络下最多 8 个最近成功地址发送同一发现查询，仍只使用 UDP 42170；有回应才标为“本轮发现”。这样可以覆盖部分广播受限、单播仍可达的网络，不扫描任意公网或所有 TCP 端口。

若实机证明仍有必要，再增加玩家主动触发的“扩大检索”：限定当前直连子网、最多 256 个目标、限速并可取消。它不是本轮主路径，不以默认遍历大网段掩盖选网错误。mDNS/NSD 也暂不加入，避免同时维护两套发现机制和 Windows 新依赖。

**接收与服务恢复：**

- 将主动关闭、超时、可恢复 socket 错误、持续失败分别处理；异常退出必须释放 socket、停止对应定时器并发状态事件。
- 最多按 0.5 / 1 / 2 秒退避重建，超过次数显示失败。保留 Windows 已有 `SIO_UDP_CONNRESET` 处理；UDP 的 ICMP PortUnreachable 可能表现为 `WSAECONNRESET`，不能把所有 socket 错误都静默吞掉。[Microsoft UDP 错误说明](https://learn.microsoft.com/en-us/windows/win32/api/winsock2/nf-winsock2-wsasendto)
- 房主的 `discoveryAvailable` 改为可更新状态，附失败原因；UDP 端口被占用时立即显示“自动发现不可用，可通过地址加入”。
- 浏览页切换网络或回到前台时重新枚举，再开启新一轮扫描。等待室网络地址失效时提示重新建房；进行中的对局继续走已有冻结/重连流程，不在后台偷偷更换房间身份。
- 房主在加入、离开、切换玩法、开始/结束比赛时更新发现元数据。新增 `updateAdvertisement` 动作或等价接口，只更新元数据，不重启 TCP 监听。

Android 当前 `targetSdk=36`，本次不因“搜索不到”就盲目申请定位、附近设备或加入新局域网权限；按官方说明，target 36 与未来 target 37 的要求不同。若之后升级 target 37，再独立接入 `ACCESS_LOCAL_NETWORK` 声明、请求及拒绝处理。`MulticastLock` 也不能被当成已确认的广播故障根因。[Android 局域网权限说明](https://developer.android.com/privacy-and-security/local-network-permission)

### 3.4 能解释失败，但不把猜测写成结论

增加一个默认收起的“连接检查”，给出：可用 LAN 路径数量、本轮发送成功/失败数、收到回应数、有效房间数，以及失败阶段。

内部保留最多 200 条本地诊断，记录扫描编号、接口绑定、查询目标、错误码和拒收原因；不记录重连令牌、玩家完整消息正文。诊断不自动上传。

| 证据 | 面向玩家的说明 |
| --- | --- |
| 无可用 LAN 路径 | 请连接 Wi-Fi、以太网或可互通热点 |
| 所有查询均发送失败 | 当前网络发送失败，可重新选择网络并重试 |
| 查询已发送但无回应 | 未收到房间回应，可尝试地址加入；暂不能确定是房主、网络隔离还是防火墙 |
| 收到回应但版本不兼容 | 已找到房间，双方需要安装兼容版本 |
| UDP 无回应、手动 TCP 加入成功 | 当前网络自动发现受限，已通过地址连接 |
| TCP 也超时 | 检查房主地址、网络隔离和应用通信权限；不把超时单独认定为防火墙问题 |

不自动关闭防火墙或 VPN，不承诺手动 IP 能绕过访客网络/AP 隔离。

## 4. 新玩法：连锁对战

本节替换旧联机总方案中“后续连锁对战”的初拟数值，使用更直接的“累计消除球数 → 攻击行”。旧公式不与本节同时使用。

### 4.1 规则定稿建议

| 项目 | 本次采用的规则 |
| --- | --- |
| 人数与棋盘 | 2 人，各自独立棋盘，相同编号波次使用相同开局 |
| 难度与时长 | 简单/普通/困难；默认普通、3 分钟，可选 5 分钟 |
| 攻击充能 | 同色消除与悬空掉落，每个球都计 1 点；累计 12 点生成 1 行攻击 |
| 单次上限 | 一次合法发射最多生成 2 行，余数继续保留；超出上限的整行直接舍弃，不暗中存为连发 |
| 防御 | 生成的攻击先按先来先抵消自己的待收攻击，再把余下部分发给对手 |
| 同批互抵 | 双方同一裁决批次抵消各自旧待收后，剩余新攻击相互抵消，再入队 |
| 预告 | 每条新来袭攻击独立预告 2 秒，之后在安全操作边界生效 |
| 待收上限 | 每位玩家最多积压 3 行；超出部分丢弃并计入“上限舍弃”统计 |
| 落地频率 | 每次最多压 1 行，两次攻击下压至少间隔 3 秒；自然压力下压对应动作冷却结束后，再留 1 秒操作窗口才可受攻击下压 |
| 自然压力 | 保留按发射次数累积的自然下压；对战关闭额外时间下压，避免三种压力叠加 |
| 清盘换波 | 保留分数、充能余量、待收队列和攻击间隔；不通过换波洗掉攻击，没有额外无敌时间 |
| 单方触底 | 立即判负；对手获胜，与竞分模式“触底后保分”区分 |
| 同批双触底 | 平局；统一提交整批结果后判断，不能先处理房主再宣布胜者 |
| 到时都存活 | 比累计基础分，再比完成波次，仍相同则平局 |
| 掉线与退出 | 沿用冻结和恢复预算；主动退出认输，无法恢复的非主动中断不判胜负 |

消除数以房主规则引擎的 `match.cells ∪ drop.cells` 为准，按同一发的逻辑格子去重。发射出的球如果实际进入消除组，也算 1 个；重复消息、视觉粒子、换波清场和下移本身都不产生充能。

令本次有效消除/掉落数为 `N`、原余量为 `C`：

```text
total = C + N
generatedRows = min(2, floor(total / 12))
nextCharge = total % 12

blockedRows = min(generatedRows, 自己尚未执行的待收行数)
outgoingRows = generatedRows - blockedRows
```

例：原充能 5，本次消除 7、悬空掉落 12，共 19 个球，得到 2 行、余量 0。自己有 1 行待收，则抵消 1 行，向对手发出 1 行；对手看到“来袭 1 行 · 2 秒后可生效”。

例：原充能 0，一次掉落/消除共 38 个球，仍最多产生 2 行，余量 2；多出的完整一行不进入隐藏库存。这样一次大连锁有优势，但不会预存长时间无法应对的连压。

这些数值是第一轮实现与试玩基线，**不是已经证明平衡的结论**。首轮不做连胜加成、随机道具、连击倍率或触控补偿，便于定位数值问题。

### 4.2 攻击队列必须可恢复、可解释

每行攻击是一条独立记录：`attackId`、来源/目标、`createdAtMs`、`notBeforeAtMs`、产生它的事件编号。时间使用房主的比赛活动时钟。

- 抵消按最早入队优先，包括预告中和已到期但尚未落地的行；不重置剩余行的到期时间。
- 每行独立满 2 秒才有资格落地，不能用老攻击带着刚收到的攻击立即连压。
- 暂停、后台与重连冻结预告和攻击间隔；恢复快照必须含充能、队列、上次攻击下压时间、自然下压保护结束时间和随机流状态。
- 攻击下移一整行，顶部补一行合法彩球，更新六角格 `rowOffset`，再检查触底；不只是把画布向下移动几个像素。
- 攻击不清零自然发射压力，不重置计时，不奖励基础分，也不改已经展示的当前球/下一球。
- 超过队列上限的攻击不延后补发、不退款充能；UI 用短提示说明本次有效压入多少行。

### 4.3 原子裁决与安全落地

对战模式新增 50ms 权威批次；竞分保持现有计分、截止和时间下压语义。对战中房主和客人的发射都先入队，使用同一套序号、修订和冷却校验。批次按房主收到命令的时间划分，不信任客户端自报时间；这消除代码路径偏置，但不宣称消除了网络延迟差异。截止以提交时刻为准，可能有最多一个批次的边界等待，双方遵循同一规则。

每批固定顺序：

1. **截止优先。** 到达比赛截止时先结算，截止批次不再接受发射、不再执行待收攻击。截止前已提交的得分保留，即使本地动画还未播放完。
2. 锁定批次开始时双方是否可操作、棋盘修订和到期攻击；在这一份基线上校验双方命令，每人最多接纳 1 发。
3. 各自独立结算合法发射及本次自然压力下压，提取消除数和新充能。双方新发射不能先后修改对方输入所依据的棋盘。
4. 同时进行：抵消自己的旧待收 → 同批新攻击互抵 → 剩余攻击入对方队列。新入队攻击重新拥有完整预告期。
5. 先检查本批自然压力下压：如果这发已触发自然下压，将 `naturalGuardUntilMs` 设为该发 `readyAtMs + 1000`，本批保留攻击而不执行；等待不刷新攻击的原始预告。
6. 对本批未发生自然下压、且批次开始时已可操作的玩家，应用仍到期且满足 3 秒攻击间隔、自然下压保护已结束的最早 1 行攻击。即使该玩家本批普通发射新设了冷却，也不能据此无限推迟本批到期攻击；批次开始时仍在上一次飞行/结算冷却中的玩家暂不执行攻击。
7. 双方一起提交快照、事件、修订和新的 `readyAtMs`，最后统一判断触底与胜负。

显示顺序固定为“原棋盘上的弹道 → 消除/掉落与抵消 → 必要的下移”。因此不会在飞行展示中途改变目标。没有本批发射时，到期攻击直接播放 360ms 下压；有发射时冷却包含本次全部阶段，视觉快慢不会改变规则窗口。

这比在现有 `acceptShot()` 后立即调用对手 `forceDescent()` 更复杂，但能避免房主先处理、攻击重复、无限拖延和飞行中突然错位。

### 4.4 随机数与现有核心边界

当前 `forceDescent()` 会把 `danger` 清零，并消耗 `state.rngState`。不能直接循环调用它实现攻击，否则攻击会意外减轻自然压力并改变后续供球。

建议提取更底层的纯下压原语，允许传入补行颜色和原因：现有单机/竞分包装仍保留原行为；对战攻击包装保留 `danger`，使用独立的攻击补行随机流。

攻击随机流由比赛种子、固定命名空间和**实际已应用的攻击行序号**推导，同一序号双方使用相同算法；抵消或上限丢弃不消耗序号。随机流不依赖谁先收到网络包、不读取 `Date.now()`，也不额外消耗供球 RNG。规则指纹包含算法与常量。

## 5. 联机消除动画与反馈

### 5.1 从“只发最终棋盘”改为“快照 + 权威事件”

保留当前 Canvas 联机显示，不把单机 `PlayScene` 整体搬进联机。单机场景带有存档、结算和排行榜副作用，应复用表现参数与纯动画计算，而不是复用整套单机生命周期。

新增同一权威提交内的事件集合，例如：

```ts
type LanCommit = {
  matchId: string;
  epoch: number;
  serverSeq: number;
  snapshot: MatchSnapshot;
  events: PresentationEvent[];
};
// 每条事件包含 eventSeq、playerId、commandSeq（若由发射产生）、
// before/afterRevision、活动时间、类型和该类型的最小表现数据。
```

事件类型至少区分 `shot-resolved`、`board-descended`、`wave-started`、`attack-queued`、`attack-cancelled`、`attack-applied` 和 `match-ended`。`board-descended` 还应区分自然压力、竞分计时和攻击来源；不能继续把换波伪装成普通下压。

`shot-resolved` 包含落点、压缩后的弹道拐点、消除/掉落格子与颜色、得分增量和逻辑阶段时长。颜色从移除前状态提取，落地的新球单独补上；最终快照里已没有这些球，不能收到后再猜它们原来的颜色。

房主本地和客人都消费同一份提交事件。定时下压也必须从 `advanceMatch` 的后续接口输出事件。限制事件数量和字节数，保持单帧不超过原生 65536 字节限制；不传每帧像素或完整飞行采样点。

### 5.2 具体表现

| 阶段 | 表现与时长原则 |
| --- | --- |
| 飞行 | 沿原棋盘弹道；沿用 220–920ms 的逻辑时长范围 |
| 同色消除 | 缩小、淡出和轻微亮环；视觉约 170ms，适配现有 190ms 逻辑预算 |
| 悬空掉落 | 分批下落、轻微旋转、淡出；全部落在现有 656ms 逻辑预算内 |
| 得分 | 一次动作一条汇总浮字，区分同色消除和悬空掉落；不为每个球创建文字 |
| 自然/攻击下压 | 360ms 插值到下一行；攻击使用清晰的红色边框和“来袭下压”标识 |
| 换波 | 短淡出/淡入及“第 N 波”；不会出现从上一波错误插值的大面积飞球 |
| 对手棋盘 | 简化的消除闪烁和下移插值；省略大量粒子和连续音效 |
| 减少动态效果 | 用短淡变和数字提示替代掉落/旋转；规则冷却、攻击预告和最终结果保持一致 |

补回 `match`、`drop`、`danger` 音效及本地消除触感，沿用已有音量和震动设置。对手动作以视觉为主，避免两侧消除音效叠加成噪声。

### 5.3 延迟、暂停和重连不能重播旧消除

- 区分权威 `modelState` 与仅用于展示的 `presentationState`。缓存旧球与短时视觉层，最终一定收敛到权威快照，不让显示层回写规则。
- 本地立即预测飞行，收到拒绝时取消预测并对齐；收到确认只接续同一 `commandSeq`，不再发射第二颗球。消除和攻击提示由确认后的事件触发。
- 以 `matchId + eventSeq` 去重；事件序号在同一对局重连后不归零，`epoch` 用于拒绝旧命令，不充当重新播放历史事件的理由。
- 动画相位按同步的比赛活动时间计算，暂停时冻结；重连时以快照和事件水位重新建立基线，不补播断线前几秒的音效、掉落和攻击。
- 事件缺失或修订不连续时申请重同步，跳过无法可靠重建的效果；不只靠两个棋盘作差猜测“消除”还是“换波”。
- 最后一击确认胜负后立即禁止输入，但表现层可以完成已确认的最后一次消除/下压，再打开结果面板，最多等待 2 秒。此时比赛活动时间已经停止，剩余转场改由独立的终局展示时钟推进，绝不推进权威比赛时间、冷却或攻击；转后台则直接收敛到结果，回来不补播。不能让 `finished` 页面立即销毁画布而吞掉最后一击；超时直接对齐结果，不能用动画拖延权威结算。
- 展示队列建议上限 32 条，落后超过 2 秒直接收敛到新快照。帧率较低时允许缩短/省略装饰动画，不能把逻辑发射许可交给动画完成回调。
- 动画结束释放对象和旧棋盘引用；静止时沿用低频绘制，连续动画结束后回到空闲节奏。

## 6. BGM 随接近底线而加速

### 6.1 使用已有距离指标

联机每次本地棋盘权威修订后，调用现有 `boardMusicPressure(localPlayer.state.board)`，再交给 `gameAudio.setPressure()`。

**音乐危险程度不是 `state.danger`。** 后者是发射下压的累计压力；用户要求的是球群距离底线越来越近时加速。复用现有最低占用行计算，避免单机与联机听感不同：

```text
pressure = clamp((最低占用行 - 6) / 11, 0, 1)
speed = adaptiveMusic ? 1 + pressure × 1.2 : 1
```

例如最低球在第 6 行时为 1.0 倍，第 12 行约 1.65 倍，第 16 行约 2.09 倍。这里只改变音符播放节奏，沿用已有音高与旋律，不直接提高音量或让音高失真。

### 6.2 音频所有权和状态

| 状态 | BGM 行为 |
| --- | --- |
| 等待室、倒计时 | 常速背景音乐，清除上一局残留压力 |
| 正在比赛 | `play`；依据自己的权威棋盘更新压力；对手接近底线不改变自己的速度 |
| 消除底部球群/清盘 | 下次状态提交后降低压力，不遗留之前的紧张速度 |
| 暂停、等待重连 | 回到常速等待状态，停止过期局内音效；比赛时钟仍冻结 |
| 后台 | 沿用现有 `setForeground(false)` 静音/挂起逻辑 |
| 恢复比赛 | 用最新棋盘重算压力，再恢复比赛音乐 |
| 本人封盘或结算/退出 | 清零压力并回到常速，避免危险值带回首页 |

尊重“音乐随局势加速”开关和音乐音量；关闭时始终 1.0 倍，音量为 0 时不强行出声。音频不可用也不能影响对局。

`main.ts` 的单机状态更新在联机激活时，不得覆写全局 `gameAudio` 的场景和压力。建议由一个轻量音频上下文统一决定当前来源，或先增加明确的联机所有权判断；不要同时让两个场景各自创建 BGM 播放器。

## 8. 验收标准

### 8.1 检索必须用实际安装包验证

| 场景 | 通过条件 |
| --- | --- |
| Windows 建房 → Android 加入，交换房主再测 | 正常互通网络下连续 10 轮扫描，每轮 8 秒内出现正确房间，且能成功握手 |
| Windows—Windows、Android—Android | 同样覆盖双方房主；设备不足时记录未验收，不用回环替代 |
| 普通路由器、无外网 Wi-Fi + 蜂窝、Android 热点 | 各方向记录真实网络与接口，热点广播受限时能明确说明并尝试单播/手动地址 |
| 多网卡、VPN/虚拟网卡同时存在 | 证明有效 LAN 路径实际发包，不能只确认枚举到了名称 |
| 某个广播目标发送异常 | 其他路径继续发现，不出现整轮静默失败 |
| UDP 接收异常、前后台、网络切换 | 服务状态准确、有限恢复、旧 scanId 不污染新结果 |
| 连续刷新/取消/退出 20 次 | 不遗留查询任务、监听 socket 或旧房间回调 |
| 默认 TCP 端口占用 | 发现和快捷填入均使用动态实际端口，能够连接 |
| UDP 42170 被占用或广播被阻断 | 明确显示发现不可用或无回应；TCP 可达时手动加入仍可用 |
| 快捷填入 | 不自动连接、不改昵称；刷新不覆盖手工编辑；多地址只显示一张房间卡 |

### 8.2 对战纯规则与会话

必须覆盖：11/12/24/38 个球的阈值和余量；同色/悬空去重；单发上限；先抵消再发送；同批互抵；队列满；独立预告；3 秒间隔；自然下压与攻击撞期；防御发射不能无限延后到期攻击；清盘不清攻击；同批双触底；截止与攻击同刻；认输和中断；攻击 RNG 不改变供球 RNG。

网络回归覆盖：重复/延迟命令不重复充能，旧 epoch 和旧对局消息无效；双方交换房主仍得到同一批输入的等价结果；暂停/重连保留充能、攻击队列与剩余预告；结算和历史只写一次。

### 8.3 动画与 BGM

- 在竞分和对战中分别完成一次三连消除、一次悬空大掉落、一次自然下压、一次清盘换波；对战再验证攻击预告、抵消和攻击落地。
- 房主自己的动作、客人自己的动作都显示同样的阶段；不能只修房主动画。
- 模拟 50/150/300ms 延迟、事件重复、断线重连与页面暂停，检查无重复发射、重复消除音、旧特效补播和永久错位。
- 30/60/120 FPS 与减少动态效果下，逻辑发射窗口、攻击生效与最终结果一致；低帧率只能减少表现，不能增加或减少攻击。
- 音乐测试使用最低占用行 6/12/16 的棋盘，分别验证约 1.0/1.65/2.09 倍节奏；消除底部球群后确实回落，对手棋盘不干扰本地速度。
- 加速开关关闭、音乐静音、后台恢复、从单机切换到联机及返回首页均正常；旧单机场景事件不能抢走联机音频状态。
- Android 真机录屏检查掉落/触控，实际听测 BGM；Windows EXE 检查键鼠与音频。截图和函数测试不能代替听测。
- 检查 320×568、390×844 和桌面布局；增加攻击条后仍能看到主棋盘、来袭预告与发射入口。

### 8.4 数值试玩与发布门槛

先做至少 20 局跨端试玩，双方交换房主和设备，记录对局时长、首个攻击时间、最大待收行数、抵消次数、连续被压次数及触底来源。样本只用于发现明显问题，不声称统计上证明公平。

若攻击几乎看不到，优先观察消除计数和阈值；若一轮大掉落经常让对方毫无反应机会，优先降低单发/积压上限或延长预告，再考虑调整阈值。调整后更新规则指纹并重跑边界测试，不在 UI 中偷偷改时间。

发布前必须有实际 APK ↔ EXE 的两个房主方向验收、动画录屏/听测、自动回归、签名和成品哈希。未取得这些结果时只能标注为测试构建，不再把 Java/C# 桌面 TCP 回环或浏览器模拟作为整套联机功能已经验收的依据。

## 9. 分阶段交付

| 阶段 | 可检查的交付物 | 进入下一阶段的条件 |
| --- | --- | --- |
| A：检索修复 | 双端扫描生命周期、逐路径容错、多接口选路、快捷填入、最小诊断 | 真实跨端双方建房均能发现并加入；故障可定位到阶段 |
| B：表现补齐 | 权威提交事件、消除/掉落/下压动画、BGM 压力和音频隔离 | 两端事件不重播、低帧率不改变规则、加速开关与后台正常 |
| C：连锁对战 | 12 球充能、预告/抵消/限流、原子胜负、对战 HUD 与记录 | 攻击边界、暂停重连、同批裁决测试通过 |
| D：试玩与发布 | 成对设备记录、数值调整结果、安装包、更新说明与验证记录 | 满足第 8 节的实机和构建门槛 |

本次范围不加入公网中继、账号好友、多人混战或协作接力。先把“找得到、进得去、攻击看得懂、动画和音乐跟得上”做成可重复验证的完整体验。
