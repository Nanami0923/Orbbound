# Orbbound Android 玩法、UI 与性能优化方案

整理日期：2026-10-14。基线：当前工作区 4.1.0，代码提交 `e886bba`。本文为实施方案；其中的目标值不是当前实测成绩。

Android 应优先改善**短屏棋盘辨认、触控反馈、存档可迁移性**，再通过真机测量推进**最高 120 FPS 的自适应帧率与画质**。保留现有深蓝、薄荷绿、暖黄、珊瑚红的视觉语言，以及 30 个高难关的定位。

配套文档：[Windows 优化方案](Windows玩法UI与性能优化方案.md)。共用规则与存档格式应由两端共同实施，避免分别改出两套玩法。

## 1. 审查范围与现有基础

本次检查了玩法、Phaser 场景、DOM/CSS、Capacitor 原生入口、存档及 4.1.0 发布验证记录，并在浏览器查看当前共享源码的 390×844、320×568 普通操作布局。本次没有完成 Android 真机性能或触控验收。

建议使用三类标记：**明确缺口**表示源码或浏览器观察已确认；**体验建议**表示产品改进；**待实测**表示有优化线索，但尚未证明存在性能问题。P1 为下一轮重点，P2 为后续完善。真机验收是发布前置条件。

以下功能已经存在，后续应保留并回归验证：

- 三种玩法：闯关、无尽、5/10 分钟限时；各有独立存档，闯关支持继续，30 关有真实弹道通关回放。
- 首页机制动画、继续游戏并入模式卡、手机选关滚动及结算关闭返回选关。
- 双滑条、双指发射、左右布局交换、沉浸模式按住瞄准松手发射；中断、失焦和后台会停止转向。
- 原生系统栏、开孔及手势区域 Insets，CSS 四边安全区与横屏布局。
- 首页/弹窗休眠游戏循环，后台暂停计时、存档及音频；运行时模块已经动态导入。
- 每帧合并瞄准更新、弹道缓存、球纹理共享、棋盘对象复用及部分动画分组。
- 当前帧率配置为 60 FPS 上限；正式构建已开启 R8 和资源裁剪。

依据：`src/main.ts`、`src/game/PlayScene.ts`、`src/game/immersive-control.ts`、`src/ui/android-insets.ts`、`android/app/build.gradle:22-26`。旧设计文档中的“开启裁剪”“首页延迟加载”“接入安全区”等不能继续当作未完成任务。

## 3. 玩法方案

### 3.1 统一有效颜色供球（A07 / P1，明确行为差异）

闯关会检查下一球颜色是否仍在棋盘上；无尽、限时直接让下一球晋级。已只读复现：清掉全部颜色 0 后，棋盘只剩颜色 2，但当前球仍是 0。这是当前规则行为，是否保留应明确决定。

建议采用“只从当前有效颜色供球”的一致规则，复用闯关的检查；说明下压补色、清盘补盘和已经显示的下一球如何处理。若改变既有规则，处理 `rulesVersion`、旧存档及历史成绩口径，避免用新规则静默解释旧对局。

验收：消除、悬空掉落清除最后一种颜色以及补盘后，供球符合选定规则；固定种子、保存恢复和相同发射序列得到一致结果。

依据：`src/core/engine.ts:195-197,232-234`。

### 3.2 加可操作短练习，保留高难闯关（A08 / P1，体验建议）

首页动画和文字帮助已经有了，下一步增加 3–4 个可跳过的短练习：同色消除、切断支撑、一次反弹、当前选择的操控方式。练习每次只教一件事，成功后直接进入正式模式；帮助页可重新进入。

双滑条练习让用户体验“另一只手发射”；沉浸练习明确移出取消、系统中断与待发射行为。练习使用独立状态，不覆盖三种主模式存档，也不进入排行榜。

验收：初次玩家不看长文也能独立完成消除、掉落和一次反弹；跳过后能直接开局。依据：`src/ui/home.ts:11-22`、`src/main.ts:359-371`。

### 3.3 用真人与角度容差校准难度（A08 / P1，待验证）

30 关已经证明可解；固定角度回放尚不能证明手指误差、手指遮挡和三星时间合理。优先检查章首、新机制首次出现、限时关和必须精确反弹的关。

对关键发射测量仍能落在正确格子的角度区间，记录普通/沉浸两种操作的成功率、重试次数和实际操作时间。极窄容差优先通过布局、支撑点和预算改善，保留具有策略意义的难度。

验收：每种机制有真实玩家记录；时间预算有人工操作依据；调整后 30 条通关参考路线继续通过。依据：`tests/campaign.test.ts`、`docs/releases/4.1.0-validation.md:4,9`。

### 3.4 把星级目标和进步反馈说清楚（A09 / P2）

- 局内显示“距三星还可用 X 发 / X 秒”；过线后切为二星预算。手机优先展示目标剩余与资源预算，避免同时铺满说明。
- 失败按发数耗尽、时间耗尽、触底、目标残留给一条具体建议，提示逐级展开。
- 首页存档、局内分数标为“基础分”；结算和榜单标为“结算分”。结算可增加新纪录、当前榜排名和距个人最佳差值。
- 闯关“最高星级、最少发数、最快操作时间”分别展示。目前三个字段独立取最优，不能拼成一局从未发生过的“最佳”。
- 选关预览加入与局内一致的六种符号；已有颜色加符号辨识基础，重点补预览及小尺寸清晰度。

验收：星级边界正确；动画和菜单不消耗闯关操作时间；不同页面同一局分数标签一致；分项最佳不会暗示来自同一局。

依据：`src/main.ts:217,228-248,410,432-433`、`src/ui/home.ts:48-54`、`src/storage/campaign.ts:31-33`、`src/ui/campaign-panel.ts:27-28`。

## 4. UI 与触控方案

### 4.1 优先解决短屏棋盘过小（A02 / P1，浏览器已确认）

普通双滑条模式当前按高度预留约 324 CSSpx 的其他空间，短屏下棋盘明显缩小。此次测量：

| 浏览器视口 | Canvas 显示尺寸 | 小球可见圆直径约值 | 观察 |
| --- | --- | --- | --- |
| 390×844 | 358×425 CSSpx | 19.58 CSSpx | 常规尺寸可辨认，仍需真机确认 |
| 320×568 | 205.47×243.99 CSSpx | 11.24 CSSpx | 控件未遮挡，但符号和目标圈过小 |

圆直径按纹理中约 35 个逻辑像素乘显示缩放估算，不是触摸命中区域；CSSpx 不能直接等同 Android dp。Canvas 内部分辨率均为 1280×1520。

方案：短屏合并次要状态行，压缩控件装饰和间距，主要触控目标保持约 44–48 CSSpx 的布局目标并真机验证；给沉浸模式一次可跳过的介绍。关键文字可移至 DOM，避免随棋盘一起缩到难读。保持 14 列规则与输入映射。

验收：320×568、360×640、390×844 及横屏，球符号、白圈目标、落点与发射控件均可辨；系统栏和手势区变化后仍能操作。依据：`src/style.css:741-756,955-969`、`src/game/PlayScene.ts:437-457`。

### 4.2 沉浸模式显示“待发射”（A04 / P1，明确缺口）

当前在上一发动画未结束时松手，会缓存最多一发，最多等待 1600ms；但界面与帮助只表达“松手发射”。增加轻量待发射标记及取消方式，并明确超时、进入菜单、后台、新手势和旋转时的处理。

建议随后以场景阶段变化通知取代每 16ms 轮询。阶段通知需要可取消、只执行一次，保留现有 Pointer Capture 和中断防护。

验收：快速连续松手不会产生无法解释的延后发射；系统取消、菜单、后台和过期请求不会在恢复后突然开火；标记与实际发射次数一致。依据：`src/game/immersive-control.ts:45-53`、`src/main.ts:366`。

### 4.3 增加 Android 本地备份入口（A05 / P1，明确缺口）

通用 JSON 备份、校验和导入前恢复副本已经存在，但 mobile 设置隐藏了入口。增加系统文档选择器导入/导出，复用现有格式；可选分享备份文件，保持离线使用。

导入先展示版本、关卡进度、历史数量和覆盖范围；用户取消时不修改数据。保留 Windows 专属旧 Electron 迁移入口的桌面边界。

验收：两台 Android 设备间往返导入三种模式存档、历史和设置；损坏/过大文件、空间不足和取消选择均不破坏原数据；导入前备份可恢复。

依据：`src/ui/settings-panel.ts:13,34`、`src/storage/backup.ts:6-11,47-55`。系统 `allowBackup` 不替代用户主动备份。

### 4.4 减少动态效果与安全区诊断（A10 / P2）

系统减少动态偏好目前主要覆盖首页动画。将其延伸到局内闪光、跳分、位移和下压装饰，并提供手动选择。命中与结果反馈保留；视觉动画、发射锁定和限时计时的关系必须先定义，避免减动画使某档玩法更容易。

安全区本身已经实现；补原生桥接失败诊断、有限重试和最近有效值。在手势/三键切换、分屏、旋转及密度变化时复核四边区域。诊断信息供开发使用，正常界面只在操作受影响时给简短提示。

验收：系统偏好与局内一致，安全区失败可诊断且页面可操作。依据：`src/style.css:759-761`、`src/ui/android-insets.ts:9-14`、`MainActivity.java:38-46`。

## 5. 性能方案：最高 120 FPS 自适应

### 5.1 帧率设置与自动策略（A03 / P1，用户指定）

将当前固定 `target: 60, limit: 60` 改为可管理的帧率策略。**自动档默认，实际游戏渲染上限最高 120 FPS**。

| 选项 | 建议行为 |
| --- | --- |
| 自动，最高 120 | 结合显示刷新率、WebView 可用回调节奏、持续帧耗时及设备状态选择档位 |
| 60 FPS | 稳定档；普通设备、兼容回退及注重续航时使用 |
| 90 FPS | 提供给节奏相容的显示模式，不能假定每台 120Hz 手机都支持独立 90Hz 模式 |
| 120 FPS | 请求最高流畅度；系统限制或持续性能不足时允许降档 |
| 30 FPS 省电 | 降低渲染负载，计时与玩法速度保持原定义 |

自动档逻辑上限为 `min(120, 当前显示/宿主允许的刷新能力, 可持续性能档位)`。支持的候选档从实际设备能力选择，未知时先回退 60；屏幕标称 120Hz 不等于 WebView 一定给出 120 FPS。

实施步骤：

1. Android 原生桥报告当前刷新率、可用显示模式及显示变化；前端短时采样可用回调节奏作为补充。刷新率请求按 Android/WebView 的实际承载方式验证，不能直接套用原生 SurfaceView 代码。
2. Phaser 采用 RAF 驱动，帧率控制集中到共用适配层；迁移设置增加枚举与默认值。画质和帧率分别设置，避免降帧必然降清晰度。
3. 首次进入测量后逐级试升至 90/120；以数秒窗口判断持续负载，连续超预算或系统省电/热状态触发降档。恢复余量持续更久再试升，加入冷却时间，避免频繁来回切档。
4. 瞄准、飞行和消除阶段使用当前活动档；完全静止阶段再评估降低渲染频率。首页/弹窗保留现有休眠，后台先保存和暂停，不持续跑 120。
5. 返回前台、刷新率变化和横竖屏切换后重新评估；不通过重建整局来切帧率。

Android 的刷新率请求可能被系统省电或其他约束限制，必须按实际可用节奏回退。[Android 官方帧率说明](https://developer.android.com/media/optimize/performance/frame-rate)。

### 5.2 不能只改 `target` 或限帧数字

已检查项目安装的 Phaser 3.90：`target` 是时间步参考值，`limit` 才参与限帧；目前限帧器累积时间超过阈值后归零，且 FPS 计数发生在渲染回调之前。

因此，144Hz 等不整除的回调节奏可能产生低于目标的实际渲染频率；在理想固定 144Hz 回调、120 上限的简化情况下，每两次回调才跨过阈值，会落到约 72 次游戏步进/秒。此为源码推导，不是本次设备实测。

实现时验证保留时间余量的节流方案、显示节奏相容的档位或合适的引擎接口，避免只写 `target: 120`、只修改 `loop.fpsLimit` 或直接修改依赖目录。**统计实际游戏更新/渲染次数和帧间隔，不能将 RAF 回调数或 `loop.actualFps` 直接当成游戏渲染 FPS。**

依据：`src/game/PlayScene.ts:783-800`、本地 `node_modules/phaser/src/core/TimeStep.js` 的 `stepLimitFPS()`；[Phaser FPSConfig 官方说明](https://docs.phaser.io/api-documentation/typedef/types-core#fpsconfig)。

### 5.3 高帧率下保持玩法一致

- 转向、微调、后坐和动画按时间推进，不能按帧数翻倍加速。
- 30/60/90/120 档同一角度、棋盘和供球状态，得到相同落点、消除、得分与下压规则。
- 核对闯关 READY 操作计时、限时模式时钟、帧停顿与后台恢复；异常大 delta 的处理不能造成瞬间转满角度或补扣后台时间。
- 动画开关、渲染分档及缓存发射与输入锁定分别验收，避免高帧设备获得额外时间优势。

现有 `tests/mobile-controls.test.ts` 已有部分 30/60/120 模拟；应补 90、动态切档、非整除刷新率与真实渲染测试。这些模拟不代替真机高刷验收。

## 6. 真机矩阵与验收指标（A01）

至少覆盖一台入门/中档 60Hz 手机、一台 90/120Hz 手机；记录机型、Android、WebView、系统刷新率设置、导航模式、构建号和电量/温度条件。可用设备不足时明确尚未覆盖的范围。

场景：冷启动和热启动各至少 5 次；首次开局；满盘连续瞄准；大面积掉落与下压；普通/沉浸模式；双指操作；菜单/后台/锁屏恢复；连续游玩至少 15 分钟。系统层用 Perfetto，网页层检查主线程及实际渲染。[Android 系统跟踪说明](https://developer.android.com/topic/performance/tracing)。

| 指标 | 拟定验收目标 / 记录方式 |
| --- | --- |
| 帧率正确性 | 60Hz 实际不超可用能力；120Hz 且能力充足时能实际接近 120；降档及恢复可解释 |
| 活动帧节奏 | 记录实际渲染间隔 p50/p95/p99；档位 N 的预算为 1000/N ms，120 为 8.33ms，90 为 11.11ms，60 为 16.67ms |
| 持续性 | 记录超过 1.5 倍预算及 >50ms 的帧比例；初拟前者 ≤1%，排除加载/后台后再校准 |
| 输入反馈 | 记录触控到下一次可见变化；初拟 p95 ≤50ms，高刷相对 60 档应有可测改善 |
| 操作可靠性 | 双指/连续松手各 100 次，无漏发、重发、后台补发或残留转向 |
| 功耗和温升 | 同亮度、同路线、同时间比较 60 与自动/120；持续掉帧或过热时降档，不靠平均 FPS 掩盖问题 |
| 内存 | 测应用及相关 WebView 内存；连续重试/切页后达到平台，不持续线性增长 |
| 规则和存档 | 不同帧率切换后结果一致，后台暂停准确，备份往返成功 |

## 7. 分阶段交付

1. **可靠性与可读性**：真机基线、短屏布局、待发射反馈、加载出口、备份入口。
2. **高刷与功耗**：120 自适应策略、真实渲染统计、节流适配、各档规则回归；根据测量再做画质分档。
3. **玩法与进步感**：供球规则、短练习、难度校准、星级预算与纪录口径。共用逻辑和 Windows 同步。
4. **后续完善**：减少动态、安全区诊断、HUD 增量更新和静止功耗。

每阶段附设备与前后数据。默认不扩展账号、联网排行、体力或签到；先提升现有三种玩法的操作、理解与稳定性。
