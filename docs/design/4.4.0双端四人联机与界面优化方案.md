## 3. 暂停申请与联机设置

### 3.1 玩家看到的完整流程

1. 对局内固定显示「暂停 / 设置」，Windows 也支持已绑定的设置快捷键。
2. 比赛进行中点击设置，立即显示「正在申请暂停以调整设置」，本局继续运行；收到房主的暂停确认前不打开设置。
3. 其他仍在操作的选手看到首屏内的申请条：申请人、原因、剩余表决时间、同意进度，以及「同意暂停 / 继续比赛」。申请人默认同意，可以取消申请。
4. 所有需要投票的人同意后，房主在统一规则批次边界冻结比赛，并广播暂停快照。设置申请者自动进入设置，其他人进入暂停面板，也可调整自己的设置。
5. 设置自动保存。「完成设置」只回到暂停面板；点击「准备继续」才提交恢复意愿。
6. 所有仍在操作的选手关闭设置并准备后，统一倒计时 3 秒，再重新接受输入。

申请条占用预留的状态区域，不放在棋盘下方，不依赖滚动，不遮挡发射区域。表决期间不弹出强制夺走焦点的模态框；键盘或指针点选投票按钮不能顺带触发发射。拒绝、取消、超时、网络异常都要有可见结果，不能只让提示消失。

### 3.2 请求、投票和预算

| 项目 | 规则 |
| --- | --- |
| 同时进行的请求 | 全房间最多一个；房主按收到的合法请求顺序接受，其他申请明确提示已有请求 |
| 请求身份 | `requestId + matchId + epoch + requesterId`；由认证连接确认申请人，禁止冒用 |
| 请求状态 | 发送中 → 等待投票 → 已批准 / 已拒绝 / 已取消 / 已超时；结果按请求编号保留并去重 |
| 发送反馈 | 点击后立即显示本地状态；2 秒未收到房主确认，显示尚未确认并查询状态；重复发送使用相同编号，不能生成新投票 |
| 确认超时 | 本地最多等待 10 秒确认，之后显示连接异常并取消本次打开设置意图；迟到的权威暂停仍应执行，但不自动打开已取消的设置页 |
| 表决时间 | 从房主创建有效请求开始 10 秒；任意一人拒绝即结束，未表态按超时处理，不能自动视为同意 |
| 投票成员 | 请求创建时仍可操作的选手；竞分已封盘、对战已淘汰者不参与，也不能发起暂停 |
| 成员变化 | 表决期间有人出局、退出、断线或退后台，取消当前请求并说明原因；根据新状态重新申请 |
| 成功次数 | 每人每局最多成功申请一次；拒绝、取消或超时不消耗成功次数，失败后本人冷却 15 秒 |
| 暂停长度 | 全房间每局共享 120 秒暂停预算；批准时本次上限取 60 秒与剩余预算的较小值，预算为零则明确拒绝；提前恢复只消耗实际暂停时间 |
| 观战者的设置 | 只能在房间已暂停、已结束或大厅中打开，不拥有干预在赛选手的投票权 |

申请编号的终态不能被迟到消息改写。房主拒绝不匹配的比赛、阶段、请求或投票成员；同一成员重复投票不重复计数。房主自己申请与客人申请使用同一套请求对象和结果通知。

### 3.3 冻结和恢复必须覆盖全部玩法时钟

- 房主在批次边界确认已经裁定的动作，发布唯一暂停快照；尚未裁定的命令取消并明确反馈，不能在恢复后补发。
- 冻结有效比赛时间、球的动作冷却、自然下压、攻击预告、攻击间隔和换波。心跳、表决超时、暂停预算及断线恢复期限继续使用真实经过时间。
- 冻结、重连与恢复切换使用新的 `epoch`，隔离旧发射和旧表决；客户端重新对齐表现事件水位，避免重放消除音效。
- 本地清除按键长按、触控捕获、待发射、转向与动画插值遗留状态。关闭设置后的第一下点击不得误发射。
- 准备后再次进入设置会撤销本人准备；进入恢复倒计时后不能重新打开设置。倒计时中任何必要成员退后台或断线，取消本轮倒计时，转入恢复流程。
- 正常恢复也会关闭观战者的设置页；观战者不参与继续投票，也不阻塞恢复确认。仍承担服务的房主必须在线并完成同步，即使房主已经出局。
- 达到暂停时间上限，先通知并自动保存、关闭各端设置，进入「恢复准备」；每端确认设置已关、输入已清空、快照已装载，再倒计时。关闭确认 3 秒未齐则转断线恢复，不能让比赛在设置背后运行。
- 暂停截止时间不会因为重连而重置；恢复成功但暂停已到期时，执行上述关闭及恢复准备流程。

### 3.4 本地设置与房间规则分开

音量、BGM 加速、画质、帧率、动态效果、瞄准辅助、快捷键和触控布局只影响本机。声音可实时预览，控制变化立即应用，但都不改随机种子、棋盘、分数或网络冷却。

模式、难度、时长、容量属于房间规则，只能由房主在大厅修改；每次修改撤销所有玩家准备。暂停中不得更改攻击阈值或其他比赛规则。数据与维护操作（含备份导出、导入、恢复和旧版迁移）只在主页设置开放；对局内保留分类说明并提示返回主页操作，避免文件选择器或数据替换干扰活动会话。

统一返回顺序：输入法 → 设置子页 → 设置分类页 → 暂停面板 → 离房确认。Windows Esc、Android 返回键和界面返回按钮一致，一次操作只退出一层。

## 4. 两种模式支持 2–4 人

### 4.1 房间、身份与开局

- 使用房主加最多 3 名客人的星形连接。Android 和 Windows 房主能力相同，不要求客户端之间建立连接。
- 房间容量可选 2 / 3 / 4，默认 4；至少 2 人且所有已加入选手都准备后即可开始，不必等到满员。
- 四个固定席位以 2×2 展示：昵称、平台、房主标识、连接和准备状态。未使用席位显示空位或未开放，不把它算作未准备玩家。
- 房主分配稳定 `playerId`；房主身份是角色，不再依赖固定的 `host / guest` 两个玩家 ID。重连必须回到原席位，不能按昵称认人。
- 开局固定参赛名单、顺序、规则、种子和比赛 ID。对局中不允许新玩家插入；只有原选手可以凭恢复令牌重连。
- 房主逐人确认装载完成，再统一 3 秒倒计时。有人未装载则说明是谁并取消开局，不能让已就绪的人先玩。
- 发现广告展示 `当前人数 / 容量`、玩法和可加入阶段。保留按地址检索与快捷填入，加入最终以房主握手结果为准。

### 4.2 同图竞分

所有人使用相同难度、波次种子和对局时长，各自在独立棋盘上操作。继续支持 3 / 5 分钟；同一波初始布局相同，后续供球仍随各自棋盘确定。

- 触底者封盘、保留分数和完成波次并进入观战；其他人继续，不因一个人触底结束整局。
- 所有人封盘或有效时间到期时结算。按总分降序，再按完成波次降序；两项完全相同则并列，不用房主身份、收包顺序或玩家 ID 打破平局。
- 排名采用比赛排名，例如 `1、2、2、4`。触底保分属于正常完赛；主动退出或恢复超时标为弃权，不凭保留的高分获得第一。
- 全部参与者的姓名、分数和状态可见；桌面右栏展示对手，手机使用固定摘要区。

### 4.3 连锁对战：按其他选手的消除总量累计压力

**本版采用按目标累计的全员对战，不指定单个攻击对象。** 每位玩家都接收其余存活选手的贡献，人数越多，每生成一行所需球数越高。

设某个 50ms 规则批次开始时有 `N` 名存活选手，目标为 `j`，本批选手 `i` 的真实去重消除量为 `rᵢ`：

```text
每行阈值 T(N) = 12 × (N − 1)
目标 j 的本批来袭贡献 = 所有 i≠j 的 rᵢ 之和
累计值 Cⱼ = 上批来袭余量 + 本批来袭贡献
本批生成行数 = min(2, floor(Cⱼ / T(N)))
新来袭余量 = Cⱼ mod T(N)
```

| 当前存活人数 | 其他选手数 | 下压一行所需累计消除数 | 示例：A 的来袭如何累计 |
| --- | --- | --- | --- |
| 2 | 1 | 12 | B 消除 12 球，A 生成 1 行来袭 |
| 3 | 2 | 24 | B 消除 10 球、C 消除 14 球，合计使 A 生成 1 行 |
| 4 | 3 | 36 | B 消除 10 球、C 消除 14 球、D 消除 12 球，合计使 A 生成 1 行 |

例子假设此前余量为 0，且目标没有防御。累计的是实际消除球数，不是分数、发射次数或已经生成的攻击行数。同色消除与悬空掉落都算，按 `match.cells ∪ drop.cells` 去重；参与匹配消除的发射球也计入。清盘额外分数不增加球数，因下移越界丢失的球不算消除。

### 4.4 防御、上限与统一结算顺序

保留消除抵消来袭的能力，但将 4.3.1 的双方互抵明确改成每人独立防御：

- 每人保存 `defenseRemainder`。自己的消除每满 12 球产生 1 行防御，每次发射最多产生 2 行，只保留不足 12 球的余数。
- **同一次消除攻防双用**：真实消除量全部贡献给其他存活选手，同时用于本人防御。防御不会撤回已经贡献给别人的压力。
- 防御先抵消自己最早的旧来袭队列，包括还在预告中的行，再抵消本批新生成的来袭。没有目标可抵消的整行防御立即作废，不能攒无限护盾；不足 12 的余数保留。
- 每个目标每批最多生成 2 行，超额完整行丢弃；入队后最多积压 3 行，超出队列上限的行丢弃，不作为隐藏债务以后补发。
- 每行至少预告 2 秒；每位玩家两次攻击下压至少间隔 3 秒，每次安全边界至多实际下压 1 行。自然压力下压对应动作结束后仍保留 1 秒保护窗口。
- 保留发射导致的自然压力下压；对战不启用额外时间下压。攻击不清零自然压力，不改变当前球、下一球或供球随机流。
- 清盘换波保留来袭余量、防御余量与待下压队列。整盘下移、攻击闪光、消除和掉落沿用权威事件表现，减少动态效果不改变时序。

每个批次按下列唯一顺序处理，不能按收包先后逐个攻击：

1. 若有效比赛时间已经截止，直接按到时规则结算，不执行本批新发射和下压。
2. 固定本批存活集合及阈值；从每个选手的命令队列最多接受一次合法发射。
3. 结算所有发射，统计各自去重消除数及自然下压；得到每个目标的其他人贡献总和。
4. 分别计算新来袭行和本人防御，先抵旧队列，再抵同批新行；将剩余新行入队。
5. 根据动作冷却、预告、间隔和自然保护条件执行待下压；是否到达安全边界以本批开始的资格判断，不能靠连续发射无限拖延攻击。
6. 统一判断所有人的触底结果，再产生排名和下一批的存活集合。不能先判某个人输就跳过同批其他人的合法动作。

取消原来的全体最小攻击数互抵逻辑，避免一名零输出玩家让其他人无法抵消，也避免只攻击数组中的第一个对手。

防御示例：四人局中，B/C/D 合计给 A 贡献 36 球；A 同批消除 12 球且没有旧队列，则 A 的 1 行防御抵消新来袭。A 的 12 球仍分别计入 B、C、D 的来袭余量。若 A 已有 1 行旧来袭，则先抵消旧行，本批新行正常预告。

### 4.5 人数变化与多来源记录

当前存活人数发生变化，从下一批开始更新阈值，保留已完成进度的比例：

```text
newRemainder = floor(oldRemainder × newThreshold / oldThreshold)
```

例如四人剩两人，`18/36` 转为 `6/12`；不会因阈值降低突然补发攻击。已经入队的行和预告时间保留，防御余量不变。只剩一人时先结算胜利，不计算 `T(1)`。

本批末才淘汰的选手，其本批已接受发射的贡献仍有效；后续批次不再贡献。已生成的攻击不因来源淘汰而撤回。

一行可能由多位选手共同贡献，事件记录贡献者集合，不能把它硬归给最后一人。来袭余量另存至多四名参赛者的贡献明细；跨批累计后按固定席位顺序消耗贡献，仅用于稳定记账。先提取实际生成行的贡献，再消耗超出生成上限而丢弃的完整行，最终账本只保留 `C mod T` 对应的余量；防御抵消或队列满导致行被丢弃时也不退回贡献。阈值变化时各贡献按比例缩放，用最大余数法补齐整数尾差，同余数时按固定席位排序，保证明细之和等于新的总余量。已经淘汰的来源可保留历史贡献，但不再增加新贡献；4.4.0 不增加击杀榜。

### 4.6 胜负、退出与重连

| 情况 | 处理 |
| --- | --- |
| 对战只剩一名存活选手 | 该选手获胜，立即结算 |
| 同批多名选手触底 | 同批并列；排名按淘汰后剩余人数加一计算，例如剩 2 人时另两人同批出局，二者并列第 3 |
| 最后所有存活选手同批触底 | 最后这组选手并列第 1，显示平局，无唯一胜者；之前出局者保留原排名 |
| 对战时间到仍有多人存活 | 存活者排在已淘汰者前；存活者比分、再比完成波次，完全相同并列；已淘汰者按淘汰批次从晚到早，同批并列 |
| 仍可操作的客人主动退出或恢复超时 | 只将该选手标为弃权，其余人继续；竞分弃权者列在正常完赛者之后且不获胜，对战按控制批次处理出局 |
| 非房主已封盘/已淘汰后退出、掉线或退后台 | 只离开观战，不改已确定的分数/名次、不改成弃权、不冻结其他人；重连也不能恢复比赛资格 |
| 房主已经触底或主动认输 | 可继续观战并保留权威服务；不因房主角色给其额外比赛机会 |
| 房主真正退出应用、关闭房间或恢复超时 | 全局中断，保留中断记录，不判其他人自动获胜；界面提前区分「认输并观战」与「关闭房间」 |

退出和恢复超时在游戏批次前的控制边界处理；若时间已截止则截止优先。对战处理后只剩一个正常存活选手时立即判胜。竞分已封盘者仍有排名资格，只有未弃权参赛者仅剩一人时可以提前结算；仅剩一人能操作而其他人已封盘时，仍等待全体封盘或时间结束。若全部弃权则无胜者，不能把弃权者排为第一。

每个玩家独立维护连接、恢复令牌、心跳、前台状态、恢复次数和累计等待时间。仍可操作的选手或房主掉线、退后台时先全局冻结，单次最多等待 20 秒；每位选手最多恢复 3 次，全房间累计恢复等待最多 60 秒，避免多人轮流拖住比赛。多个掉线者共用同一段全局等待，不把同一秒重复扣多次。仍可操作的客人超时弃权后移出投票和准备集合，剩余选手重新装载快照并倒计时恢复。非房主观战者离线不消耗这份等待预算。

已封盘/已淘汰者离开观战后，本机保存最后确认状态。没有收到终局结果时标为最终结果未同步，不能自行推算最终排名；恢复观战时获取房主保留的权威结果。

房主中断不能靠三位客户端各自判定结果。房主仍需保持游戏在前台；本版不增加后台持续游戏服务。结果结构改为 `ranking[] / winnerIds[] / terminationReason`，完整区分触底、到时、弃权和网络中断。

## 5. 首页与全界面无纵向滚动

### 5.1 首页固定四入口

```text
ORBBOUND                         设置

       闯关模式       无尽模式
       进度与星级     开始 / 有存档

       限时模式       局域网联机
       5 / 10 分钟    2–4 人 · 两种玩法

玩法与练习                          记录
```

Windows 使用左侧品牌/简短机制演示、右侧 2×2 模式入口；手机采用顶部品牌、居中 2×2 入口、底部工具。四个入口高度和层级一致，局域网作为正式模式参与构建，不再由模块在最后追加一张不同尺寸的卡片。

卡片只保留名称、一句简介和必要进度。「继续 / 新游戏」、难度和时长进入模式准备页后选择；主页不因存在多个存档而增加按钮行。短屏优先缩减留白及隐藏装饰演示，不压缩关键按钮或把入口推到屏外。

### 5.2 页面约束

统一 `ViewportShell`：固定标题、可分配内容、固定主要操作。以实际可用视口和安全区计算尺寸，容器使用可收缩网格及 `min-height: 0`。

**除设置详情外，不允许页面、列表、卡片或弹层纵向滚动。** 设置页也只允许中间内容区滚动，标题、返回、完成和联机暂停剩余时间固定可见。禁止仅用 `overflow: hidden` 截掉内容来通过检查。

长内容按以下方式处理：

| 页面 | 无滚动处理方式 |
| --- | --- |
| 单机开局、难度、限时选择 | 紧凑选项页；长说明切到独立帮助页，主要按钮固定 |
| 30 关选关 | 章节切换 + 按可用高度计算每页 4 / 6 / 8 个关卡；上一页、下一页和页码固定 |
| 关卡详情 | 目标、星级、预览固定；长提示使用目标 / 提示标签页 |
| 历史与排行榜 | 均有分页，条数随实际可用高度变化；手机通常 3–5 条、桌面 5–8 条，不能只分页却保留内滚动 |
| 教程与实操练习 | 一屏一步；说明、练习棋盘和下一步按高度分配，保留跳过和返回 |
| 联机入口 | 创建 / 加入并列，详细规则另开分页说明 |
| 创建房间 | 基本信息、规则两步；容量、玩法、难度、时长不与长帮助堆叠 |
| 加入房间 | 附近 / 地址 / 最近三个标签；附近列表分页，保留刷新、停止、快捷填入和按地址检索 |
| 连接诊断和多网卡地址 | 独立分页详情，可复制或导出日志；不出现内嵌滚动日志框 |
| 大厅 | 固定四席位、规则摘要、准备/开始；房主修改规则和查看地址进入独立页 |
| 五种玩法界面 | 棋盘按剩余高度等比缩放；状态、操作和暂停始终在屏内 |
| 单机结果 | 结果摘要、奖励、主要操作一屏；详细统计切页 |
| 四人联机结果 | 固定四行排名，个人详情按选手切换；不纵向堆四张大结果卡 |
| 普通确认、错误、断线状态 | 简短正文和固定操作；长细节分页，不能继承设置的可滚动弹窗样式 |

分页保持稳定条目 ID 和焦点；刷新房间不把用户带回第一页，不覆盖手动输入。结果更新不让正在点击的条目跳位；页数减少时才将当前页限制到最后有效页。

### 5.3 小屏、输入法和字体

- 棋盘以 640:760 逻辑比例等比适配，碰撞、危险线和触控坐标仍使用同一逻辑空间。不能拉伸棋盘或通过减小逻辑球间距塞进屏幕。
- 本机棋盘优先于装饰、长说明和对手大预览。触控目标至少 44 CSSpx，关键状态不能只靠颜色，也不能为了无滚动缩成难读文字。
- Android 昵称、房间名、IP 编辑时，进入单字段编辑层并依据 `visualViewport` / 原生可见区域处理输入法；键盘上方保留当前字段、必要校验及取消/完成。键盘收起后恢复原页和输入内容。
- 横屏、刘海、手势条、三键导航和字体放大都重新分配可用高度。内容放不下时减少一页条数、增加步骤或切换紧凑布局，不能裁掉最后一个按钮。
- Windows 紧凑窗口只调整信息布局，不因此切成手机操作；同时验证显示缩放后的真实 WebView 客户区。现有原生最小外窗 780×500 不能直接当成 CSS 视口尺寸。

## 6. 五种玩法共用界面结构与操作

### 6.1 共用内容与平台布局

三种单机（闯关、无尽、限时）和两种联机（竞分、对战）使用共同的 `GameShell`、`GameHudModel` 和输入动作接口：

- 模式与阶段、得分/目标、剩余时间、自然压力和攻击预警采用一致的信息顺序、单位、颜色与状态文本。
- 当前球、下一球、炮台、危险线、瞄准路线采用相同视觉参数和相对位置；不能出现单机在侧栏、联机漏掉下一球等差异。
- 暂停、设置、返回/退出的位置及语义一致；联机暂停走投票，单机暂停由本地立即执行。联机不展示单机的存档退出承诺。
- 飞行、消除、悬空掉落、得分反馈和整盘下移共享时长及样式规范；规则来源仍分别是单机引擎和联机权威事件。

| 平台/尺寸 | 本机棋盘及信息 | 对手/任务区 | 操作区 |
| --- | --- | --- | --- |
| Windows 常规窗口 | 中央棋盘，左侧本人数据和模式信息 | 右侧任务或最多三个对手缩略图、分数、状态 | 鼠标键盘为主，显示简短快捷键提示，无手机双滑杆 |
| Windows 紧凑窗口 | 保留桌面输入，缩减边距和辅助说明 | 三个固定摘要 + 一个可切换预览 | 固定暂停/设置入口；不把所有侧栏依次堆到棋盘下方 |
| Android 按钮模式 | 紧凑顶栏、模式状态、本机棋盘 | 联机显示最多三个固定摘要；详细预览切换而非拉长页面 | 双滑杆 + 发射，遵循左右调换、按键大小和偏移设置 |
| Android 沉浸模式 | 增大棋盘有效区域，保留相同 HUD | 同上，允许缩略但不遗漏在赛者状态 | 完全隐藏底部按钮栏，棋盘按住瞄准、松开发射 |

手机横屏采用侧置辅助信息与控制区，仍保持一屏。查看对手大预览时明确进入本地观察层、阻止穿透发射，并提示比赛仍在继续；关闭观察层回到原瞄准方向，不自动发射。观战者可切换被观察玩家，不再保留自己的可操作发射栏。

### 6.2 统一输入语义

Windows 以现有单机习惯为基准：鼠标左右键都支持发射，按住瞄准、松开且仍满足棋盘边界条件时发射一次；屏蔽棋盘内右键菜单。键盘发射、长按转向、快转 30° 和自定义快捷键在五种玩法与练习中一致。

Android 两种操作方式沿用现有偏好。按钮模式支持一手微调、另一手发射；沉浸模式移出取消、系统中断取消，禁止设置切换或失焦后补发。平台和输入设备能力与尺寸布局分别管理，Windows 构建始终采用桌面输入配置。

将 `aim / fire / turn / quickTurn / pause / settings` 映射到统一输入控制器；场景只提供动作执行和当前可操作状态。菜单、设置、暂停、断线、失焦、模式切换均先释放旧输入；任何弹层存在时只允许该弹层需要的操作，不能让快捷键穿透。

## 7. 设置层级与实时生效

设置最多两层：分类列表 → 分类详情。Windows 使用左侧分类、右侧内容；Android 使用分类页和详情页。只有详情内容可纵向滚动，不同时出现外层和内层两个滚动区域。

| 分类 | 项目 | 依赖和展示规则 |
| --- | --- | --- |
| 声音与音乐 | 音效音量、音乐音量、局内音乐加速、菜单/紧张节奏/音效试听 | 音乐为 0 时保留加速偏好并说明静音；试听不改比赛压力 |
| 操作与辅助 | 瞄准辅助；Windows 键鼠说明和快捷键；Android 控制方式、微调灵敏度、布局与震动 | 瞄准辅助不再独占一个分类；快捷键也不游离在分类导航之外 |
| 画面与性能 | 清晰度、帧率上限、减少动态效果、帧率显示 | 显示实际运行能力；自动帧率与清晰度独立，不把它们合并为含糊档位 |
| 数据与维护 | 导出、导入、恢复备份、旧版迁移、恢复默认 | 对局内仅提供说明，返回主页后操作；各类恢复按钮说明影响范围 |

Android 选择按钮模式时才显示双滑杆灵敏度、左右调换、发射宽度与控制区偏移；沉浸模式下收起这些无效项，保留原值，切回按钮模式时恢复。没有震动能力时说明不支持，不显示看似可用却无效的开关。Windows 不展示触控布局选项。各分类提供「恢复此分类默认」，全局恢复仍放在数据与维护中。

新增共享 `SettingsStore`，兼容现有 `orbbound-settings-v1` 的有效值，单机、联机、练习和音频订阅同一个已应用版本。分类重排本身不清空偏好；遗留的 `independentLaunch` 不重新暴露为有效选项。

应用设置时分别处理：

- 音量与自适应 BGM 立即更新；设置试听拥有临时音频控制权，退出试听恢复暂停场景，恢复比赛后再根据自己的棋盘计算危险速度。联机每帧更新不能覆盖试听。
- 清晰度变更主动重新计算画布像素尺寸；帧率变更刷新当前渲染器预算，帧率标识跟随当前玩法，而非绑定单机页面。
- 控制方式、布局、灵敏度或快捷键变化先释放旧手势和按键，再重新布局/绑定；保持当前棋盘、比赛时钟和随机状态。
- 减少动态效果只影响表现；当前事件收敛到对应快照，不重复播放消除或提前解除规则冷却。
- 弹层统一做焦点约束与背景隔离，包含联机页面；设置关闭后将焦点还给暂停面板，不直接落到发射按钮。

### 8.2 连接与消息体积

原生已经有按连接 ID 发送的能力：Windows 当前上限 8 个连接，Android 当前上限 4 个连接；四人房不需要改为全互连。应用层限制为 3 个已认证客人加最多 1 个临时候选，候选 5 秒未完成握手即回收；房间已满且无恢复需求时直接拒绝额外连接。重连替换旧连接前核验原令牌，并关闭失效连接，避免耗尽恢复通道。

每个连接分别维护发送队列、序号、限流和超时。房主从连接映射确定发射者，不能相信消息自报身份。一个慢客人不能阻塞其他人的命令确认或暂停消息；必要时按慢连接故障处理。断线通知只改变对应选手。

单条原生消息硬上限保持 65,536 字节。前端使用 `TextEncoder` 计算完整信封的 UTF-8 字节数，目标不超过 60 KiB；不能再用 `JSON.stringify(...).length` 当字节预算。

四人同步使用完整权威状态与分层表现：本人事件完整，其他三人可简化粒子、得分浮字和弹道密度，但保留消除/下压提示。需要拆分时，状态快照与按玩家的表现事件分包，带同一快照修订号及每玩家事件水位。客户端只有在对应状态到齐后播放；缺失或超期则收敛到快照，不回滚规则。禁止直接丢弃整个事件列表尾部，使后两个席位长期没有动画。

命令结果、暂停投票、冻结和结束消息不可按视觉事件策略丢弃；积压快照可合并为最新一份。对手预览建议独立限制到 15–30 FPS，本机沿用用户帧率偏好；减少对手渲染负担不减少规则计算频率。

### 8.3 版本与历史兼容

- 产品版本：Android / Windows 同步 `4.4.0`；Android `versionCode=40400`，Windows 文件版本 `4.4.0.0`。
- LAN 协议及联机快照升至 3，升级规则指纹，纳入人数、动态阈值、防御及并列规则。4.3.x 发现条目明确标为不兼容，不能握手后才悄悄丢包。
- 保留原签名、包名和数据目录，支持覆盖安装。单机旧存档、旧设置及 4.3.x 双人记录继续读取；新旧对战规则的记录显示版本和人数。
- 新结果的 `winnerIds` 可多项；全局中断或全部弃权为空。记录完整的参赛名单和终止原因，不把并列、观战、断线和正常失败混在一起。

## 9. 实施顺序

1. **P0：暂停故障复现和状态机。** 先在现有双人链路完成请求反馈、投票超时、取消、冻结与恢复，日志覆盖发送、接收、校验、渲染和点击；定位用户报告的实际原因。
2. **P0：共享设置及输入隔离。** 接入设置订阅、音频优先级、返回层级和恢复关闭握手，确保暂停调整后当前局立即生效。
3. **P1：多人协议和会话。** 将身份、连接、装载、恢复和结果从双方抽象为集合，先完成 2–4 人竞分，再接入多人暂停。
4. **P1：多人对战。** 落实唯一公式和批次顺序，覆盖所有阈值、抵消、淘汰、弃权及动态人数边界，再接入多人表现。
5. **P1：共享玩法界面和桌面操作。** 三种单机与两种联机逐一适配 GameShell 和输入控制器；桌面恢复完整键鼠语义，手机沉浸与按钮模式一致。
6. **P1：首页及全页面无滚动。** 按页面清单改为固定布局、分页或分步，清理历史 CSS 覆盖；同时完成设置分类重排。
7. **P2：真实双端与四机验收、平衡试玩、签名打包。** 版本字段和发布资料在验收阶段统一更新，不能在四人链路未完成时仅凭界面变化发布正式版。

12 / 24 / 36 是本方案默认数值。后续试玩若确需修改基础值，应同步更新规则指纹、说明、示例与测试；不能在某个平台单独调整。

## 10. 验收与发布条件

### 10.1 暂停和设置

- 2 / 3 / 4 人分别覆盖房主、每个客人申请；Android 与 Windows 互换房主。申请后本机即时反馈，其他人无需滚动即可同意或拒绝。
- 验证拒绝、超时、取消、同时申请、重复投票、迟到投票、额度不足、申请者出局和成员变化；每次都获得明确终态。
- 暂停期间所有端的有效时间、攻击预告、自然下压和冷却均停止；心跳继续。设置中不接受棋盘点击、键盘发射或旧待发输入。
- 音量、加速开关、清晰度、帧率、瞄准辅助、快捷键和触控方式在当前联机局立即生效；试听不被游戏音频覆盖。
- 关闭设置不立即开局；正常恢复和暂停到期均先关闭设置、对齐快照，再共同倒计时。设置中断线/退后台按恢复规则处理。
- Android 返回、Windows Esc、返回按钮只退出一层；退出设置不会同时退出房间，也不误发射。

### 10.2 多人规则与网络

- 两种模式均覆盖 2 / 3 / 4 人开局、少于容量开局、满员拒绝、规则修改撤销准备、开局装载超时与重连身份隔离。
- 阈值边界：11/12、23/24、35/36；三人分别贡献 10+14，四人分别贡献 10+14+12；只贡献零球的选手也必须正常收到其他人合计压力。
- 大消除、同色/掉落去重、来袭余量跨批、每目标生成上限、队列满、防御攻防双用、旧队列优先、无目标防御作废和阈值比例换算；超额行清账后，贡献明细必须仍等于余量，抵消不能返还贡献。
- 四人同批发射交换输入数组顺序，结果和事件语义一致；覆盖同批多人触底、最后全员同批触底、超时优先、退出与到时交错。
- 4→3→2 的进度转换不瞬间补发攻击，不撤销历史排队行；退出者和淘汰者之后不能继续贡献。
- 四人最大棋盘、同批大消除、长中文/emoji 昵称及补帧消息均以实际 UTF-8 字节测量，不超过原生上限；各席位都有正确表现事件。
- 单客人慢连接、丢线、退后台和恢复不会串改其他玩家；房主中断不产生假胜利；恢复等待不能通过轮流掉线无限延长。
- 竞分只剩一名可操作玩家时，不遗漏其他封盘者的排名资格；非房主观战者离开不冻结比赛、不抹去成绩；未收到终局时不生成虚构排名。
- 原有广播扫描、按地址检索、快捷填入和端口冲突回退继续回归；没有广播回应时明确显示结果，不把手动地址连通写成自动发现通过。

### 10.3 全界面和一致性

Windows 覆盖原生最小窗口的实际 WebView 客户区，以及 800×600、1280×720、1366×768、1920×1080；检查 100% / 125% / 150% / 200% 显示缩放、窗口调整和全屏切换。Android 覆盖 320×568、360×640、393×851、412×915、568×320，并覆盖系统字体 100% / 130%、安全区和输入法出现/收起。

对第 5 节清单中的每一页、每一种正常/空/错误/最后一页状态检查：

1. 除设置详情外，所有可见容器满足 `scrollHeight <= clientHeight + 1`；隐藏页面不参与计算，也不能借不可见裁切掩盖超出内容。
2. 关键按钮、焦点控件和完整主要信息处于可用视口内；触控目标不低于 44 CSSpx，Tab 不会把焦点移到屏外隐藏内容。
3. 分页能访问全部关卡、记录、房间和诊断内容；检查最长昵称、四人结果、多地址和放大字体，保证没有信息永久丢失。
4. Windows 五种模式均支持相同的左右键、长按转向、快转、键盘发射和快捷键；紧凑窗口也不出现手机双滑杆。
5. Android 五种模式的按钮/沉浸、双指操作、移出取消、系统中断和设置切换一致；动画、危险线和下一球表达一致。

### 10.4 实机与发布门槛

自动规则测试、浏览器模拟、原生服务互通和真实游戏界面对局分别记录，互不替代。至少完成 Android—Windows 双向房主的完整竞分与对战，并完成四个真实终端参与的混合平台四人局；推荐 2 台 Android + 2 台 Windows。只有两个真实设备加模拟客户端时，应明确标注该范围，不能当作真实四机验收。

覆盖普通路由器与手机热点；每种人数和玩法都执行暂停调整、恢复、淘汰、退出及到时结算。对战另做至少 20 局平衡试玩，覆盖不同人数及水平差异，记录首次攻击时间、平均来袭/抵消、队列溢出、触底原因和暂停使用。观察卡顿与实际 BGM 变化，不只看测试用例通过。

满足上述关键验收后再将 4.4.0 标为正式版。未完成真实四人对局、暂停设置恢复、无滚动页面检查或键鼠一致性时，只发布明确标注缺口的测试版。发布资料包含双端成品、SHA-256、更新说明、验证矩阵、已知问题及本方案链接；保留既有发布，避免覆盖 4.3.x 文件。

验收完成的玩家体验应当是：能在首屏找到四种模式；2–4 人顺利进入同一房间；暂停申请看得见且有结果；调整设置后共同恢复；对战压力随所有其他选手的消除而变化；无论单机还是联机，Windows 和 Android 都使用各自一致、可预期的操作方式。
