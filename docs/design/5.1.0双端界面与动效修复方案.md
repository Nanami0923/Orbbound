## 3. Android：章节、关卡与详情统一包装

### 3.1 保留三个清楚的导航层级

```text
首页 · 闯关模式
  → 章节选择
    → 当前章节的关卡列表
      → 单关详情
        → 开始 / 继续实际对局
```

章节选择采用应用内面板，替换该入口的系统原生下拉菜单。各层使用相同的深色面板、标题栏、圆角、字号和返回按钮。Windows 的关卡展示方式保持独立，Android 列表改造通过明确的布局参数或平台类启用，避免直接改动共享模板而影响桌面布局。

### 3.2 章节选择层

- 标题为“选择章节”，右侧保留关闭入口。
- 每章一行：章节编号、名称、已通关数量；当前章用小面积薄荷色标记。
- 五章按原顺序展示，长屏可完整显示，短屏在内容区滚动。
- 总关卡/星级进度放在标题下方的一行摘要中。
- 有进行中存档时提供独立的“继续存档 · 第 X 关”入口；存档所属章节与当前浏览章节可以不同，文字必须明确。
- 打开、选择、返回均由现有模态导航系统管理，同一时刻只有一个活动面板和焦点范围。

```text
选择章节                              关闭
已通关 0 / 30 · 已获 0 / 90 星

1   进阶起点                       0 / 6  ›
2   路径拆解                       0 / 6  ›
3   多色迷阵                       0 / 6  ›
4   高压棋盘                       0 / 6  ›
5   终极考验                       0 / 6  ›

继续存档 · 第 1 关                       →
```

### 3.3 具体关卡改为单列列表

每行建议以 64–76 CSS px 为普通字号下的起始高度，随大字体和内容自然增加；主要点击目标至少 48 CSS px，并在真机上核对实际触控区域。列表行不使用 `1fr` 拉满剩余高度。

```text
‹ 章节                路径拆解         关闭
第 2 章 · 已通关 0 / 6

07  交错阵列                     待解锁
08  逐层剥离                     待解锁
09  高处星点                     待解锁
10  折返长廊                     待解锁
11  支撑迷阵                     待解锁
12  步步紧逼                     待解锁
```

行结构采用“编号 / 名称与必要状态 / 星级或锁定状态”。已通关行显示实际星级，可开始行有轻量方向提示，锁定行明确显示“待解锁”。不依赖颜色单独表达状态。

- 普通竖屏以当前章节的六行列表为主，空间不足时滚动；取消 Android 关卡网格专用的页码和空白占位。
- 点击已解锁行进入详情，不直接开局；保留 `data-level` 和实际解锁校验。
- 返回列表恢复原章节和滚动位置；切换章节后从新章节顶部开始。
- 返回键按“详情 → 关卡列表 → 章节选择 → 首页”逐层返回；关闭按钮保留清楚的关闭语义。
- 列表采用普通导航按钮与列表语义；章节当前项、焦点和锁定态提供读屏文本。

### 3.4 单关详情保持信息完整

统一标题栏、背景、按钮与列表页的视觉语言，继续保留真实棋盘预览、目标、发数/限时、不下压或下压规则、提示、星级条件、个人纪录和存档替换提示。

详情保留“开始第 X 关”“返回选关”。首次开局的互动练习、旧解锁继承、已有星级与最优纪录继续生效。棋盘预览复用共用球面矢量图案，保持原有白圈目标标记含义。

## 4. Android：首页模式卡片与透明演示

### 4.1 图标和文字组的排布

常规竖屏继续采用 2×2 模式卡，极窄屏沿用单列滚动。卡片以 116–130 CSS px 为初始高度，内容较多或字体放大时自然增高。

- 左侧图标列建议 28–32px，图标约 24–28px；跨越整个文字组的行高并垂直居中。
- 图标与文字的列间距由当前约 8px 增至 12–16px，结合实际卡片宽度确定。
- 右侧标题、关键状态、必要 action 组成一个整体，整体垂直居中；图标与该文字组的中心线对齐。
- action 继续放在独立行或明确的独立位置，不与正文共享重叠区域。
- 四张卡统一内边距和重心，保留左右相同的安全留白。

```text
┌──────────────────────────────┐
│                              │
│   ◇       闯关模式            │
│           0 / 30 关 · 0 ★     │
│           选关 →              │
│                              │
└──────────────────────────────┘
```

### 4.2 文案精简规则

| 模式 | 保留的关键信息 | 精简方式 |
| --- | --- | --- |
| 闯关 | 模式名、实际通关/星级进度、存档所属关卡 | 移除“固定棋盘 · 逐关解锁 · 星级挑战”等常驻说明；有存档时简洁显示“存档 · 第 X 关” |
| 无尽 | 模式名、进行中存档分数、实际最高纪录 | 有存档显示“继续 · 670 分”等实际值；无存档保留最高纪录摘要，去掉“自由节奏 · 自动存档”长说明 |
| 限时 | 模式名、5 / 10 分钟、存档剩余时间 | 移除“争分夺秒”；存在存档时优先显示实际剩余时间，时长选择仍可在模式设置进入 |
| 联机 | 模式名、2–4 人、联机入口 | 首页保留“2–4 人”即可，竞分/对战规则在联机页选择 |

所有数字来自真实进度、纪录和存档。精简文案不删除继续游戏、最高纪录、5/10 分钟选择或联机功能；暂无纪录时避免在多处重复展示没有区分度的 0 分。

### 4.3 字重层次

- 主标题及四个模式名称：系统无衬线字族，约 700 字重；当前设备支持时使用真实粗体。
- 存档分数、关卡/星级等关键数字：约 600–700，数字采用等宽数值特性。
- 正文摘要约 12–13px、常规字重；辅助说明约 11–12px。短屏通过滚动和排版适配，不继续压小文字。
- 辅助信息保留较低对比度，关键按钮使用明确的粗体层级，避免整页所有文字同样粗重。

### 4.4 演示背景透明

Android 首页 `.mechanism-demo` 的背景改为透明，并清除该演示容器的独立渐变、底板、边框与面板阴影。首页整体的淡背景装饰可以继续保留。

保留 SVG 中的轨迹、球体、发射位置标记、简短机制文字和约 10 秒自动循环。发射位置标记属于演示内容，不视为整块背景。离开首页、打开面板或进入后台时继续暂停；减少动态效果时保持静态机制说明。维持没有重播按钮的首页行为。

## 5. Android：联机“下一球”边界修复

### 5.1 修复尺寸来源

当前 HUD 为球体预留 28px 网格列，内部 `.next-preview` 却仍可能继承 `--orb-preview-box-size:44px` 对应的固定宽高和 flex-basis。`min-width:28px` 只设置下限，无法把 44px 实际盒子改成 28px；SVG 的 `overflow:visible` 也需要一并核对。

实施时由 HUD 预览组件统一决定以下尺寸，不再让列宽、盒宽、球宽分别来自不同规则：

| 元素 | 建议初值 | 约束 |
| --- | --- | --- |
| 下一球卡片 | 依 HUD 可用宽度自适应 | `min-width:0`、`box-sizing:border-box`，完整容纳文字和预览盒 |
| 图案所在网格列 | 32px | 与实际预览盒宽度一致 |
| `.next-preview` | 明确宽高 32×32px | 重置继承的 width、height、flex-basis 和不必要外边距 |
| 球体 | 28×28px | 在预览盒内居中，四周保留安全空间 |
| SVG | 球体盒内 100%×100% | 保留正确 viewBox、圆形外轮廓、原图案和两个小圆点 |

卡片内边距以 6–8px 为起点，左右文字/球体间距约 6px。先修正真实几何尺寸，再约束外溢阴影；完整球体与图案必须可见。

### 5.2 保留同步与自适应

- “下一球”继续采用文字在左、球体在右的排布，与单机提示语言一致。
- 保留共享 `nextOrbPreviewMarkup()` / `updateOrbPreview()`、唯一 DOM ID 和现有发射、飞行、装填的颜色切换时机。
- 窄屏、大字体或长昵称时，增加 HUD 高度或将辅助操作移到下一行，保持球体完整。
- 核对普通操作、沉浸操作、横竖切换、2–4 人、观战与返回自己；同一组件的单机预览同步检查。
- DOM 边界验收应覆盖“球体 ⊆ 预览盒 ⊆ 卡片内边界”，并以真机画面核对实际 SVG 和阴影范围。

## 6. Windows：左侧下压/计时条留白

本项按用户截图中的贴边问题处理，同时检查“本局用时”模块的上下间距。保留真实倒计时、剩余次数和进度比例。

### 6.1 布局调整

- 收拢 `.game-header`、`.danger-stat` 和两条 `.danger-meter` 的桌面覆盖规则，解决旧 `.desktop-ui .game-screen …` 选择器压过新 padding 的问题。
- 在左侧信息内容与右侧分隔线之间保留明确 gutter，常规窗口建议 16–20 CSS px，最小窗口至少 12px。
- 为进度轨道明确可用宽度、`max-width:100%`、`min-width:0` 和盒模型；轨道在模块内部完整显示。
- 下压次数条与限时模式时间条共用相同的水平边界；标签、数值和轨道左侧对齐。
- 轨道与上方数值建议保留 6–8px；与下一信息模块建议保留 14–20px，具体随小窗口复核。
- 窄窗口若进入横向信息栏布局，按对应布局重新分配 gutter，保证棋盘仍保持 640:760 比例。

### 6.2 数据与视觉分开验证

轨道宽度由布局决定，填充比例继续由实际状态和 `scaleX(progress)` 决定。合法的 100% 状态仍应填满**轨道内部**；不可为制造留白而把真实进度强制限制在 90% 或 95%。

实施前后对比无尽、限时和闯关三类状态，记录 `aria-valuenow`、提示文字及填充比例，确认变化仅影响模块几何与留白。

## 7. 双端：直接消除与连带掉落同步

### 7.1 根因与同步目标

当前 V5 视觉轨迹中，直接消除球的起始延迟为 0；连带掉落球使用：

```text
起始等待 = 85ms + min(index, 6) × 24ms
         = 85–229ms
```

`index` 来自“直接消除 + 连带掉落”的合并数组，批量掉落通常很快达到等待上限。掉落又使用从静止起步的平方加速曲线，最初的位移较小，进一步增加迟启动的观感。

5.1.0 将同一发命中的直接消除和连带球统一登记在命中时刻 `t0`，在同一展示帧开始运动。两种轨迹继续分别体现“散开消除”和“失去支撑后下落”。

### 7.2 视觉时序调整

| 项目 | 当前行为 | 5.1.0 目标 |
| --- | --- | --- |
| 直接消除球起动 | 命中后 0ms | 保持 0ms |
| 连带球起动 | 命中后 85–229ms，依 index 排队 | 所有连带球为 0ms，取消该类视觉延迟 |
| 直接消除轨迹 | 约 520ms，向外散开后淡出 | 保留同源轨迹，确认命中帧连续 |
| 连带球轨迹 | 约 1050ms，另加等待 | 从命中起立即下落，约 900–1050ms 收尾 |
| 连带球初始运动 | 纯平方曲线，前段位移弱 | 增加适度初速度，随后加速下坠 |
| 粒子与加分 | 由同一次清除触发 | 使用同一个命中时钟，保留实际加分与粒子预算 |

掉落位移可先采用 `distance × (0.25p + 0.75p²)` 作为调参起点，`p` 为从命中开始的归一化进度。以录屏确认起动清楚、下坠自然；不为制造同步感把所有球压成相同轨迹或瞬间消失。

### 7.3 同时覆盖 Phaser 与 Canvas

- 修改共享 `clear-motion.ts` 的 V5 视觉起始时间，清理不再使用的视觉 delay/stagger 参数。
- 同步更新 Phaser 视觉尾迹总时长的计算，并核对 LAN 尾迹保留期限，避免移除等待参数后仍沿用旧结束时间或提前销毁球体。
- Phaser 单机继续用脱离棋盘容器的球体克隆，完整保留球面图案；原棋盘重绘后视觉尾迹仍可继续。
- LAN Canvas 的主棋盘和观战使用同一轨迹与同一逻辑展示时间，事件晚到时两类球一起按同一 elapsed 追帧。
- 当前旧主题回退还有独立的延迟公式。5.1.0 的两端 V5 发布路径必须全部覆盖；若验收仍会进入该回退路径，也统一其视觉起点并单独回归。
- 大量掉落不再按数组下标等待。粒子仍受桌面 54、Android 30 的现有预算限制。
- 低动态模式在同一次命中反馈中处理两类清除，跳过粒子和大幅位移，保留文字与计分反馈。

### 7.4 发射锁、联机时序与生命周期约束

视觉起始时间和输入解锁时间分别维护：

```text
视觉：match.startAt = drop.startAt = 命中时刻 t0
输入：继续采用当前单机结算锁 / LAN 权威 readyAtMs
```

PlayScene 的原 source-orb 分组和旧等待公式仍控制实际发射锁；其中的旧 delay 用于保持既有节奏，不再作为 V5 球体克隆的启动等待。缺少 sourceOrb 的刚发射球可以参加清除动画，但不单独增加锁定时间。

LAN 的 `resolutionMs`、`readyAtMs`、冷却和协议校验保持原值。视觉尾迹在 READY 后继续播放，下一次合法发射仍可正常接受。暂停、后台、切局、重开和终局按既有时钟暂停或清理，避免恢复后补播、旧球残留、重复粒子与重复加分。
