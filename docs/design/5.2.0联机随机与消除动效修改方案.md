# ORBBOUND 5.2.0 联机界面统一、随机与消除动效修改方案

日期：2026-10-21。基线：5.1.0。已纳入后续“散开和下落添加加速度”“下落曲线符合抛物线”及“双端联机基础界面与其他模式统一”的反馈。
状态：已接入双端 5.2.0，并完成本轮自动回归、Windows 原生交互、Android 实机、两组实体联机及正式包保留数据覆盖升级验收。三组实际联机 UI 样例已于 2026-10-22 获用户确认；实际范围及未覆盖矩阵见 [5.2.0 验收记录](../releases/5.2.0-validation.md)，文件信息见[产物清单](../releases/5.2.0-artifacts.json)。

本轮沿用深海军蓝、低高光、简约面板与六种原球面图案。联机以各自平台已确认的其他模式局内界面为基准，复用基础布局与样式，仅增加联机专属信息和必要操作；首页和选关延续现有方案。

最新约束：保留当前 demo 的抛物线角度和轨迹参数，本次界面方案补充不再调整抛物线。

## 1. 本次修改范围

| 编号 | 要求 | 5.2.0 目标 |
| --- | --- | --- |
| R1 | 联机各玩家棋盘和出球不再相同 | 两种联机模式均改为每人独立随机；初局、后续波次和供球都覆盖 |
| R2 | 连带掉落与直接消除同步 | 同一次命中的两类球使用相同起点、时长、淡出及运动模型，同步完成 |

| R4 | 粒子更多、更柔和，双端都保留 | 增加细粒及短尾层次，Android 使用明确预算，普通效果下不直接省略粒子 |
| R5 | 减少效果也要有基础过渡 | 关闭粒子、散落和旋转，保留两类球原位淡出；恢复正常可见的发射与装填 |

动效改动同时覆盖双端单机、联机主棋盘和观战。联机随机改动限制在联机建局路径，单机与固定关卡的生成及旧存档保持原规则。

## 2. 实施前现状与原因（5.1.0）

### 2.1 联机同棋盘、同球序

当前 [`createMatch()`](../../src/lan/authority.ts) 对所有玩家调用同一个 `deriveWaveSeed(matchSeed, 0)`；[`resolvePlayerShot()`](../../src/lan/match-helpers.ts) 清盘后的同编号波次也使用同一个派生种子。因此初始棋盘、当前球、下一球和 RNG 状态一致。

仅换成不同种子还不够直观：[`fillOpeningRow()`](../../src/core/engine.ts) 保留固定 opening 模板，每格只有 27% 概率尝试改色，仍有约 78% 的位置保留模板色。5.2.0 应同时取消联机开局的固定位置骨架，避免“种子不同但棋盘看着还是类似”。

### 2.2 同时开始，仍不同步消失

[`clearOrbPose()`](../../src/render/clear-motion.ts) 虽已取消掉落的额外起动等待，但直接消除使用 520ms，连带掉落使用 1050ms；透明度在各自进度的最后 32% 才下降。两类球分别约在 354ms、714ms 开始淡出，并在 520ms、1050ms 消失，缩放终值也分别为 0.65、0.88。单机 Phaser 和联机 Canvas 都使用这套模型。

现有粒子每个采样球只发 3 个，总量上限 Windows 54、Android 30；单机纯匹配的 520ms 驱动还会提前截断设定为 560ms 的粒子。减少效果路径则跳过清除克隆或把源球直接置透明，缺少基础淡出。

## 3. 联机独立随机方案

### 3.1 房主生成，每人独立，可复现

房主在新一局生成一个随机根种子，按稳定玩家身份、波次和用途派生个人种子：

```text
deriveLanSeed(matchSeed, playerId, waveIndex, domain)

domain:
  board-v1   → 本人的初始棋盘 / 新波次棋盘
  supply-v1  → 本人的当前球 / 下一球 / 后续供球
  attack-v1  → 对战来袭行，另加入目标应用序号
```

- 派生算法采用固定整数运算和明确编码，不依赖窗口大小、时间、客户端性能或本地 `Math.random()`。
- 棋盘建盘 RNG 与供球 RNG 分离，建盘消耗多少随机数不会改变开局球序。球色仍从当前棋盘有效颜色中抽取，避免抽到已不存在的颜色。
- 供球继续使用每名玩家快照中的个人 `rngState`；自然压力下压可沿用该个人流，与其他玩家互不影响。本轮不要求同一玩家的供球永远不受自身棋盘变化影响。
- 对战攻击行继续与个人供球流隔离，并把目标 `playerId` 加入攻击种子的派生，避免不同目标的相同攻击序号必然得到同一行。
- guest 只提交操作、接收房主快照，不在本地另抽棋盘或下一球。所有客户端看到的同一玩家棋盘必须一致。

派生规范以 demo 的 `deriveSeed()` 为参考：按 UTF-16 code unit 遍历 `playerId + NUL + waveIndex十进制 + NUL + domain`，执行固定 FNV-1a 与 32 位混合。玩家 ID 使用房主生成的稳定 UUID，不能用可改昵称代替。参考向量：

| 根种子 | 玩家 | 波次 | 用途 | 派生值 |
| --- | --- | --- | --- | --- |
| 520 | p1 | 0 | board-v1 | 603175877 |
| 520 | p1 | 0 | supply-v1 | 3636614665 |
| 520 | p2 | 0 | board-v1 | 2466274389 |
| 520 | p1 | 1 | board-v1 | 3356980069 |

攻击行单独定式为 `deriveLanSeed(matchSeed, targetPlayerId, 0, "attack-v1/" + appliedRows十进制)`；波次位固定为 0，`appliedRows` 为目标已有的全局累计应用序号，跨波次不重置，重连不清零。

### 3.2 初始盘位置随机，难度约束一致

同一难度保持相同球数、行数、颜色种类和颜色配额；对每名玩家的完整开局球池独立执行 Fisher–Yates 洗牌，再填入六角网格。每个位置均参与洗牌，不保留原模板的大部分固定色位。

5.2 联机明确改用整盘均衡配额，不沿用旧 opening 模板的颜色计数：

| 难度 | 行数 × 列数 | 按颜色 ID 升序的固定配额 |
| --- | --- | --- |
| 简单 | 5 × 14 | `[18, 18, 17, 17]` |
| 普通 | 7 × 14 | `[20, 20, 20, 19, 19]` |
| 困难 | 8 × 14 | `[19, 19, 19, 19, 18, 18]` |

Demo 实现其中普通难度样本，每人配额相同、位置独立。正式接入须核对所有难度的开局可操作性、色团分布和难度波动；不宣称随机棋盘天然具有完全相同的通关难度。

独立随机不等于每颗球必须不同。允许首球或一小段序列偶然相同，不为追求表面差异而强制换色，也不让某位玩家根据对手抽球结果重新抽取。

### 3.3 后续波次、重连及再来一局

- 清盘后按本人的 `playerId + waveIndex` 生成新棋盘和供球种子，不回到所有人共用的编号棋盘。
- 断线恢复、前后台切换、暂停/恢复及 RESYNC 直接恢复房主现有 board、current/next、rngState、waveIndex 等状态，不能调用重新建盘或重新抽球。
- “再来一局”由房主生成新的 matchId/root seed；普通重连保留原局。
- 上述恢复保证针对房主会话仍存活的情况，本轮不增加房主进程退出后的持久化续局。

### 3.4 模式文案与兼容

“同图竞分”改为“随机竞分”，说明为“相同难度，各自随机棋盘与出球；按得分、完成波次排名”。“连锁对战”保留名称，补充独立开局说明；攻击累计、防御和胜负规则沿用现行规则。

房间创建、规则摘要、局内标题、帮助页、联机记录统一用词，清理“同图”“相同开局”的旧承诺。历史 5.1 记录仍按原含义展示。

随机策略是规则变更，必须更新 `LAN_RULES_HASH`，不能沿用 5.1 的 `4e2a4139`。保持消息字段不变时可继续使用协议 v3；若实施时增加快照字段，则同步更新 schema 与严格校验。5.2 与旧 5.1 在握手阶段明确拒绝混连，并提示双方更新，不能静默套用旧随机策略。新指纹由最终代码计算，不在方案中预填一个假值。

## 4. 双端统一清除动效

### 4.1 同一时间轴，不再按球类分时长

| 项目 | 直接消除球 | 连带掉落球 |
| --- | --- | --- |
| 起点 | 同次命中 t₀ | 同次命中 t₀ |
| 完整效果时长 | 720ms | 720ms |
| 透明度 | `(1 - p)^1.15`，从 t₀ 开始淡出 | 完全相同 |
| 球体尺寸 | `scale = 1` | `scale = 1` |
| 运动 | 向两侧由慢到快散开，先轻抛再沿抛物线下落，少量旋转 | 同一运动函数 |
| 完成 | t₀ + 720ms | t₀ + 720ms |

`p = clamp((now - t₀) / 720ms)`。不按 `falling` 选择不同分母，不再使用逐球起动延迟，也不延长连带掉落的淡出尾巴。球体连同图案一起等大渐隐，禁止通过缩小、骤降 alpha 或最后一帧直接隐藏来代替过渡。

根据后续反馈，Demo 同时满足“散开有加速度”和“空间轨迹为抛物线”。采用加速的水平距离推进一条明确的抛物线，而不是把 X、Y 分别套用不一致的缓动。以下数值以 640×760 逻辑棋盘为单位，`t` 为命中后经过的秒数：

```text
d(t) = vx₀ × t + ½ ax × t²
L = d(0.72)
u = d(t) / L

x = x₀ + direction × L × u
y = y₀ + 420u² - 144u

vx₀ = 60～72 px/s
ax  = 140～230 px/s²
```

消去 u 后，Y 是水平位移的二次函数，空间路径严格为抛物线。小球先向两侧轻微上扬，再沿弧线加速落下；水平距离仍按正加速度增加，不退回水平 ease-out 的减速散开。此设计是加速推进的抛物线路径，不把它误称为“水平加速且恒定竖直重力”的物理模拟。

两类球使用相同参数规则、时钟和淡出曲线，保留不超过约 0.28 弧度的旋转；位置差异只来自起点及散开方向。路径修改不改变球体尺寸、720ms 淡出或粒子预算。“减少效果”仍原位淡出，不施加运动或加速度。

720ms 是本轮演示候选参数。后续如调整，须整体调整两类球，不能重新拆为两个时长；以用户确认的 demo 作为实机接入基准。

### 4.2 粒子更丰富，但不提高高光

| 项目 | Windows 主棋盘 | Android 主棋盘 |
| --- | --- | --- |
| 每球目标粒子数 | 14 | 10 |
| 同次清除总量上限 | 192 | 144 |
| 本 demo 12 球样本 | 168 | 120 |
| 起点 / 生命周期 | t₀ / 720ms | t₀ / 720ms |
| 材质 | 原球色细粒 + 少量短尾，无大光团 | 相同风格 |

- 采用圆周扩散、速度衰减和轻微重力，避免几条固定射线的机械感；以低透明度叠加，保留暗色背景的干净层次。
- 粒子半径保持不变，以透明度渐隐，不把球体或粒子不断缩小作为主要消失方式。
- 预算按所有被消除球轮流分配，直接消除和连带掉落都能产生粒子，避免前几颗耗尽预算。
- 动效采样使用独立的确定性随机源，不消耗游戏 RNG，不影响后续出球。
- Demo 为重复对比使用固定外观采样；正式版按 `playerId + eventSeq/commandSeq` 派生外观种子，使不同次消除具有自然变化，仍不占用供球 RNG。
- 正式版采用对象池及单棋盘总预算，多次清除重叠时控制总量。联机缩略棋盘使用更小的共享预算和较低刷新率；完整效果下仍保留可辨识的粒子，不因平台是 Android 就全部关闭。
- 粒子按自身生命周期更新与回收，不再被纯匹配球的旧 520ms 驱动提前截断，也不因加分文字尾巴仍在而保留不可见对象。

## 5. “减少效果”的明确含义

建议界面文案为“减少消除效果”，说明为“关闭粒子和散落，保留基础淡出”。

| 表现 | 完整效果 | 减少效果 |
| --- | --- | --- |
| 基础清除淡出 | 两类球同步 720ms | 两类球原位同步 320ms |
| 球体缩放 | 不缩小 | 不缩小 |
| 粒子 / 短尾 | 保留 | 关闭 |
| 散开 / 下落 / 旋转 | 保留 | 关闭 |
| 额外加分上浮 / 强调波纹 | 保留克制反馈 | 去掉额外运动，数值仍更新 |
| 正常发射 / 装填 / 瞄准 | 正常可见 | 正常可见 |
| 基本界面过渡、音效、触觉、规则计时 | 原有设置决定 | 不被本开关额外关闭 |

这不是“把球直接隐藏”。320ms 过程中必须能看到半透明中间帧，直接消除和连带球同时淡出完毕。基础清除层始终存在，开关只决定是否叠加额外运动和粒子。

实施时保留现有 `reducedMotion` 存储键的读取兼容，但收窄用户开关作用域，梳理发射隐藏、后坐、界面 CSS 和首页演示等旧调用，避免继续把它当全局关动画开关。系统 `prefers-reduced-motion` 另行处理：单机、联机使用同一判定，减少非必要运动时也保留可见的基础淡出，不通过隐藏发射物或清除球实现。

## 6. 双端联机与其他模式的基础界面统一

### 6.1 统一原则

联机不再单独设计一套局内界面。Windows 的联机与本平台无尽、限时、闯关共用基础界面；Android 同样对齐本平台其他模式。双端遵循同一视觉规范，同时保留 Windows 横屏和 Android 竖屏各自的排布，不能把两端强制排成同一版面。

联机相较其他模式，主要增加房间、选手、连接、对手和比赛状态等专属信息。基础区域的背景、材质、字体、字号、字重、数值模块、球体、按钮、间距和边框沿用本平台共用样式，不因为进入联机而切换另一套皮肤。

| 基础区域 | 统一要求 |
| --- | --- |
| 局内整体框架 | 共用背景、面板层级、圆角、描边、留白、安全区和响应式断点 |
| 主棋盘 | 共用棋盘底板、边框、网格、触底线、尺寸比例及危险提示样式；按可用空间等比排布 |
| 小球与发射器 | 共用六种原图案、颜色、半径规范、发射器材质、瞄准线、发射和装填表现 |
| 分数与计时 | 共用标题、标签、数值字体和进度条组件；名称、单位与读数对应当前真实模式 |
| 下一球 | 共用预览卡、球体与图案的尺寸、对齐和安全边界，不再保留联机专用的另一套预览布局 |
| 基础操作 | 暂停、设置、玩法等共用按钮外观、尺寸、字重、间距、按下反馈与快捷键提示规范 |
| 弹窗与反馈 | 共用标题栏、按钮、关闭/返回、设置详情、结果面板及本方案清除动效；联机状态通过内容和专属信息补充 |

界面一致不代表显示相同数据。联机的剩余比赛时间、定时下压、波次或来袭压力必须按真实规则显示，不能为了模仿其他模式而误写成本局用时或“再发射 N 次”。

### 6.2 联机专属增量信息

以下内容在基础界面之外增加，使用同一套文字、数值和面板样式：

- 房间/玩法、自身昵称、房主或客人身份，以及比赛准备、倒计时、对局中等状态。
- 延迟、连接、重连和同步状态；有异常时强化提示，平时保持轻量。
- 当前波次、对战来袭/防御及联机压力等当前玩法实际需要的信息。
- 其他玩家的昵称、分数、波次、缩略棋盘与淘汰状态；保留点击观察、返回自己的入口。
- 全员准备、暂停投票、恢复准备、认输/离开房间、观战和最终排名所需的内容与操作。

这些是联机功能增量，不用于重新包装基础棋盘或替换基础操作区。联机暂停仍按全员投票规则处理，退出仍按认输/离房规则确认；共用样式时不能错误沿用单机“本机暂停”或“存档并返回”的行为和文案。

### 6.3 Windows 排布

- 保留其他模式的左侧信息、中间主棋盘、右侧操作框架；分数、计时、下一球及主要操作沿用相同组件和所在区域。
- 波次、连接与压力等专属信息放入既有信息区域的增量分组；对手列表、缩略棋盘及观察操作放入附加区域，使用共用面板样式。
- 2～4 人局按实际对手数量展示；窗口较矮时允许对手区折叠或独立滚动，不通过压窄基础数值、裁切按钮或拉伸棋盘容纳信息。
- 保留既有进度条与分隔线的留白，避免联机再引入贴边、额外描边或另一套按钮风格。

### 6.4 Android 竖屏排布

- 保留其他模式的顶部信息栏、主棋盘、发射/方向控件层次；普通模式和沉浸模式分别沿用本平台已经确认的排布。
- 分数、下压/计时和下一球使用共用信息栏模块。联机状态增加在紧邻信息栏的轻量区域，不把原有基础模块改成另一套尺寸、文字位置或纵向挤压的布局。
- 对手信息采用紧凑的横向条或可收起区域，保留观察入口；展开详情按共用面板规范呈现，避免默认堆叠大卡片把主棋盘和操作区整体推低。
- 短屏、大字体、状态栏/手势安全区下仍需保证主要操作可达。新增信息需要空间时，优先收起或滚动专属区域，保持基础模块上下留白和棋盘等比显示。
- 单机、联机与观战的下一球均按同一尺寸规则核对，球面图案必须完整位于预览卡内部。

### 6.5 共用实现与样例确认

实施时将局内框架、HUD、下一球、按钮与面板的基础样式归入共用组件/样式层；联机只传入实际数据、模式语义及专属信息。需要使用不同渲染器时，也复用同一套棋盘、小球、发射器和动效参数，避免复制整份单机 CSS 后再单独演化。

重点梳理 `lan-match-layout.ts`、`lan-panel.ts`、`lan-board.ts` 与 `android-v5.css` / `windows-v5.css` 的联机覆盖规则，清除仅由模式不同造成的基础样式差异；保留因平台、视口和真实信息内容产生的合理排布差异。

现有 demo 继续作为动效与随机策略基准。本次仅补充联机界面统一方案；正式接入前，给出 Windows 和 Android 普通/沉浸模式的联机与其他模式对照样例，按既有要求确认 UI。抛物线沿用当前角度与参数。

## 7. 共享实现与规则时钟

1. 在共享清除模块提供 `clearOrbPose`、`clearParticlePose` 和统一配置；直接消除、连带掉落均调用同一模型。Phaser/Canvas 只做渲染适配，不复制两套参数。
2. 单机在命中后记录 t₀，创建源球外观一致的临时清除层；减少效果也创建基础淡出层，不能跳过克隆后直接置透明。
3. LAN 以 `event.atMs + flightMs` 为同一次命中起点，主视图、观战与缩略图使用同一事件时钟。网络快照更新不能把正在淡出的球突然删掉或重新画回去。
4. 动效时间与权威规则阶段分开。保留当前 match/drop 的发射就绪、readyAt、计分和结算规则；720ms 展示尾巴可跨 READY 独立收尾，不增加隐藏等待。快速下一发时，对象引用按事件隔离。
5. 暂停时冻结动画相位，继续后接着播放；退出、换局、断线结束和减少效果切换时清理临时层，避免旧粒子或掉落球混入新局。
6. 延续原球面图案与低高光材质，加分、连击和通关/失败反馈不改成大光团或满屏闪烁。

主要落点：[`src/lan/authority.ts`](../../src/lan/authority.ts)、[`match-helpers.ts`](../../src/lan/match-helpers.ts)、[`battle.ts`](../../src/lan/battle.ts)、[`protocol.ts`](../../src/lan/protocol.ts)、[`PlayScene.ts`](../../src/game/PlayScene.ts)、[`clear-motion.ts`](../../src/render/clear-motion.ts)、[`lan-presentation.ts`](../../src/ui/lan-presentation.ts)、[`lan-board.ts`](../../src/ui/lan-board.ts) 及设置/样式调用点。
