# Orbbound Windows 玩法、UI 与性能优化方案

整理日期：2026-10-14。基线：当前工作区 4.1.0，代码提交 `e886bba`。本文为实施方案；其中的目标值不是当前实测成绩。

Windows 应优先改善**弹窗键盘焦点、防误重开、外壳异常恢复和高 DPI 可读性**，加入**最高 120 FPS 的自适应帧率**，再按原生测量优化画质、空闲负载和启动。

配套文档：[Android 优化方案](Android玩法UI与性能优化方案.md)。供球、计分、练习和存档格式属于共用任务，两端只调整输入与展示重点。

## 1. 审查范围与现有基础

检查了共用规则、Windows 专用样式、键鼠、WebView2 外壳和打包配置，并在浏览器查看 Windows 模式的 1280×720、780×500 布局；打开模式弹窗时，焦点仍停留背景启动按钮的现象已经观察到。本次没有完成 Windows 原生外壳全流程或性能测试。

**明确缺口**表示源码或浏览器观察已确认；**体验建议**表示产品改进；**待实测**表示线索而非已证实故障。P1 为下一轮重点，P2 为后续完善。原生验收是发布前置条件。

当前已经完成：

- Windows 为 .NET Framework 4.8 / WinForms + 共享 WebView2 Evergreen，发布 x64 轻量 ZIP。历史 `electron/` 不是当前成品外壳。
- 窗口位置、大小、最大化状态保存与工作区校正；PerMonitorV2 DPI、单实例、F11 全屏及恢复。
- 桌面布局与鼠标左右键、键盘发射、长按转向、30° 快转、自定义快捷键及冲突校验。

- 弹道缓存、瞄准合并、纹理共享、棋盘对象复用、部分动画分组及当前 60 FPS 上限。
- 30 个高难闯关、独立模式存档、本地历史与按模式/时长分榜。

依据：`windows/Program.cs`、`windows/app.manifest`、`scripts/package-win.cjs`、`src/game/PlayScene.ts`、`src/main.ts`。旧 3.0 设计文档中的“迁移 WebView2”“保存窗口”“加入备份”等不再列为新任务。

## 3. 玩法方案

### 3.1 Windows 有进度时确认重开（W03 / P1，明确缺口）

侧栏“重新开始”和对应快捷键直接执行 `restartGame()`，清理该模式进行中存档。有进度时应先暂停，显示“放弃当前局并重开？”；默认焦点放“继续游戏”，Escape 取消。尚未发射的局和结束后的重试可直接执行，保持挑战节奏。

READY、FLYING、RESOLVING 都应先获得一致的可恢复状态，取消时保留棋盘、供球/RNG、分数与计时预算，确认只新建一次。Android 菜单已有放弃确认，可复用文案语义。

验收：鼠标、重开快捷键、长按 repeat 都不误清存档；取消回原局，确认后仅重开一次。**F 结算已经有确认，应保留。**

依据：`src/main.ts:570-572,624-627`、`src/game/PlayScene.ts:220-224`、`src/main.ts:515-516,526-529`。

### 3.2 统一有效颜色供球（W07 / P1，明确行为差异）

闯关会替换已经从棋盘消失的下一球颜色；无尽和限时仍可能将该色直接晋级。已只读复现棋盘仅剩颜色 2、当前球却为已清除颜色 0 的情况。

建议统一为从有效颜色供球，明确清盘、下压补色和已经显示的下一球处理；修改时兼顾规则版本、旧存档及旧榜单语义。若决定保留旧行为，也应明确它是预览供球的规则。

验收：同一棋盘、种子与操作在两端得到同一结果；消除和掉落清除末色后符合选定规则；旧数据可继续按原语义解释。依据：`src/core/engine.ts:195-197,232-234`。

### 3.3 实操练习与高难关校准（W07 / P1，体验建议 / 待验证）

保留 30 个高难关，另加可跳过的短练习，分别教消除、支撑与反弹；桌面练习包含鼠标瞄准、独立发射、方向键与快转。帮助页可重进，练习状态不覆盖正式存档、不入榜。

使用真人测试和关键发射角度容差校准关卡，尤其章首、新机制和限时关；分别看鼠标与键盘的操作时间和误差。已有通关路线只证明可解，不能直接作为三星操作时间合理的证据。

验收：新玩家能独立完成三个机制；键鼠各完成代表关的人工测试；改关后 30 条参考路线仍通过。依据：`src/ui/home.ts`、`src/main.ts:359-371`、`tests/campaign.test.ts`、`docs/releases/4.1.0-validation.md:4,9`。

### 3.4 星级预算、成绩和排行（W10 / P2）

- 保留并强化已有本关目标、剩余目标数和下移提示，增加三星/二星发数或时间预算，次要解释可展开。
- 分清“基础分”和“结算分”。局内显示基础分，结算沿用现有系数并显示新纪录、当前榜排名及距个人最佳差值。
- 当前关卡星级、最少发数、最快操作时间各自取最优；分项展示，避免拼出不存在的最佳一局。
- Windows 排行表高亮最近一局，增加难度筛选及可选近期趋势；保留综合加权榜与现有同分规则。倍率是否公平需要实际成绩分布，不能只靠公式判断。
- 失败提示按发数、时间、触底和目标残留给对应建议；残局复盘和逐级提示可后续加入。

验收：分数和星级边界准确；最高纪录以对应模式/时长榜为准；筛选不覆盖原始历史；最近记录可快速找到。

依据：`src/main.ts:217,228-248,410,432-433`、`src/ui/home.ts:48-54`、`src/storage/campaign.ts:31-33`、`src/ui/history-panel.ts:11-13`。

## 4. UI、键鼠与窗口方案

### 4.1 完整弹窗焦点管理（W02 / P1，已确认）

现有 `role="dialog" aria-modal="true"` 没有配套初始焦点、Tab 圈定、背景隔离和关闭恢复。浏览器打开模式弹窗时，焦点仍在背景模式按钮。

打开时保存触发元素，将焦点移到标题或合适控件，背景设 `inert`，处理 Tab / Shift+Tab；关闭时恢复到合理入口。绑定标题和 `aria-labelledby`。切换设置子页及结算转选关时，恢复目标应按新页面决定。

验收：仅用 Tab、Shift+Tab、Enter、Escape 能完成首页→模式→游戏→设置→结算流程；焦点不进入背景，无丢失或不可见焦点。依据：`src/main.ts:310-348`。

### 4.2 关闭浏览器专属快捷键（W06 / P1，待原生复核）

外壳已关闭默认菜单、开发工具和缩放，但未设置 `AreBrowserAcceleratorKeysEnabled`。官方默认值为 true，据此推测 F5/Ctrl+R 重载、Ctrl+P 打印等可能仍干扰游戏，需原生确认。

正式外壳禁用浏览器专属加速键，必要时在 controller 层处理；保留游戏 F11 和文本编辑快捷键。

验收：原生 F5、Ctrl+R、Ctrl+P、Ctrl+F 不打开浏览器功能或丢局；F11、自定义游戏键、文件对话框复制粘贴正常。依据：`windows/Program.cs:69-72`、[WebView2 Settings 官方说明](https://learn.microsoft.com/en-us/microsoft-edge/webview2/reference/winrt/microsoft_web_webview2_core/corewebview2settings?view=webview2-winrt-1.0.3800.47)。

### 4.3 多显示器、高 DPI 与小窗口（W08 / P2）

已有 PerMonitorV2 和窗口恢复。继续覆盖 100/150/200/300% DPI、低 DPI 屏拖到高 DPI 屏、拔副屏、窗口恢复和 F11 往返。浏览器 780×500 检查只能说明网页布局，不能代替带标题栏和缩放的原生客户区验收。

低高度布局优先保证棋盘、剩余发数/时间和下一球；次要侧栏可折叠，不继续把关键字缩小。选关预览补球符号；增加明显的“全屏 F11”入口可后续实施。

验收：所有主要动作可见，球符号与白圈目标可辨，弹窗关闭按钮不滚出屏幕，窗口不离屏，全屏退出恢复原状态。

依据：`windows/Program.cs:50,157-179`、`windows/app.manifest`、`src/style.css:850-927`、`src/ui/campaign-panel.ts:27`。

### 4.4 方向键组合与异常停顿（W09 / P2，明确状态边界）

当前只保存一个转向方向：按住左、再按右、先松右时会停转，即使左仍按住也不会自动恢复。维护按下方向键集合，约定最后按下优先或双键抵消；释放时恢复另一键，失焦/弹窗/鼠标接管时清状态。

对异常大 delta 的转向积分设合理上限或在恢复时重置，避免卡帧后突然转到 ±78°。单键加速曲线和快转语义保持一致。

验收：双键各释放顺序、鼠标接管、长按时 Alt+Tab、模拟停顿和弹窗恢复均无粘键或大角度跳变。依据：`src/game/PlayScene.ts:130-143,293-305,550-577`。

## 5. 原生稳定性与后台行为

### 5.1 按 WebView2 故障类型恢复（W04 / P1，明确代码缺口）

当前所有 `ProcessFailed` 都隐藏游戏并要求关闭重开。部分 GPU/Utility 故障可由运行环境自动恢复，因此这条统一处理可能把可恢复故障变成长期不可用页面。

| 故障 | 建议行为 |
| --- | --- |
| GPU / Utility 退出 | 记录诊断，允许宿主自行恢复；持续失败才显示恢复入口 |
| 主 renderer 退出 | 显示简短提示及重载入口，从最后成功存档恢复 |
| Browser 退出 | 按实际生命周期重建 WebView 控件/环境连接 |
| 不响应或加载超时 | 提供等待、重试和退出，设置有限重试，避免无限循环 |

恢复不得重复记历史、重复创建音频和输入监听，不承诺还原尚未成功持久化的内存状态。已有存档备份机制应保留。

验收：使用隔离测试数据注入各类故障；GPU 自恢复后可玩；renderer/browser 可重试；连续失败有明确出口。依据：`windows/Program.cs:78,82-85`、[WebView2 进程事件与恢复](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/process-related-events)。

### 5.2 明确失焦、锁屏与睡眠策略（W06 / P1，待原生验证）

外壳目前主要通过 Resize 的最小化状态通知后台；页面 blur 会停止转向，但窗口仍可见的 Alt+Tab 不一定触发 `document.hidden`。先验证音频和限时行为，再明确“失焦暂停”的默认策略或设置。

区分普通 resize、Deactivate、最小化、系统锁屏/睡眠；后台依次暂停、存档、音频静音。回前台提供可理解的继续状态，避免恢复时直接补扣时间或发射。

真正不可见时再评估 WebView2 挂起：先保存，再满足 `IsVisible=false`，调用 `TrySuspendAsync`；处理失败返回值和恢复。失焦本身不等于满足挂起条件。[TrySuspendAsync 官方条件](https://learn.microsoft.com/en-us/dotnet/api/microsoft.web.webview2.core.corewebview2.trysuspendasync)。

验收：Alt+Tab、Win+D、锁屏、睡眠和原生文件对话框均不丢局、不粘键，暂停预算正确，恢复后只有一个音频调度器。依据：`windows/Program.cs:53,115-117`、`src/main.ts:561-562,594-613,646-647`。

## 6. 性能方案：最高 120 FPS 自适应

### 6.1 档位和自动策略（W05 / P1，用户指定）

当前固定 `target: 60, limit: 60`。新增默认**自动，最高 120 FPS**，以及 30 省电、60、90、120 上限选项。用户选择的是目标上限，显示能力或持续性能不足时可自动回退。

| 显示与运行情况 | 自动行为 |
| --- | --- |
| 60Hz / 可用回调仅 60 | 使用 60 或更低稳定档 |
| 90Hz 且性能足够 | 可使用 90 |
| 120Hz 且性能足够 | 最高 120 |
| 144/165/240Hz | 最高仍为 120；验证非整除节奏及 VRR 情况，不直接宣称匀速 120 |
| 性能不足、笔记本省电 | 降到稳定档，恢复余量持续满足后再试升 |
| 首页、弹窗、最小化 | 保留休眠/暂停，避免持续高帧空转 |

自动上限为 `min(120, 当前显示/宿主可用刷新能力, 可持续性能档位)`。按窗口所在显示器和实际 WebView2 回调节奏评估，跨屏、刷新率变化及恢复前台时重算；不修改用户系统显示设置。

适配层以几秒窗口统计负载，降档较快、升档较慢，加入冷却时间。静止棋盘、鼠标连续瞄准、飞行/掉落分别测量，避免一轮掉落使档位反复跳变。设置与画质分开，正常 UI 只展示选择和必要状态。

### 6.2 Phaser 限帧与实际渲染测量

Phaser `target` 是时间步参考值，`limit` 才参与限帧；不能只把 target 改成 120。[Phaser FPSConfig 官方说明](https://docs.phaser.io/api-documentation/typedef/types-core#fpsconfig)。

本地 Phaser 3.90 的 `stepLimitFPS()` 累积时间跨过阈值后归零。在理想 144Hz 回调配 120 上限的简化模型下，需要两个回调才渲染一次，可落到约 72 次游戏步进/秒；这是源码推导，尚未作为实际机器结果测量。

高刷实现先验证保留时间余量的节流适配、显示节奏相容的档位或合适引擎接口；避免简单更改单个运行时字段或每次切档重建游戏。非整除刷新率下需看帧间隔分布，平均数接近 120 也不代表均匀显示。

引擎的 FPS 计数位于渲染限流之前，因此**RAF 回调数与 `game.loop.actualFps` 都不能直接证明实际游戏渲染 FPS**。单独统计游戏更新/POST_RENDER 事件、帧间隔及输入到可见变化，并配合 GPU/宿主记录检查。

依据：`src/game/PlayScene.ts:783-805`、本地 `node_modules/phaser/src/core/TimeStep.js`。

### 6.3 30/60/90/120 下保持规则与操作一致

转向、快转、后坐及 Tween 均按时间推进；核对长按加速、动态切档和异常 delta。固定棋盘、种子和发射角度序列，在各档得到相同落点、消除、得分及下压。

限时的真实预算、闯关 READY 操作计时和菜单/后台暂停准确；视觉动画开关不能让某一档多出操作时间。分别记录鼠标和键盘输入反馈，不能把绘制更快理解为玩法速度更快。

验收覆盖 60/90/120Hz，至少再加一个 144Hz 或 165Hz 非整除场景；同机比较 60 与自动/120 的实际帧节奏、输入和 CPU/GPU 成本。现有模拟测试只能证明部分逻辑，不能替代原生高刷测试。

## 7. 原生矩阵与拟定验收指标（W01）

至少一台低配核显笔记本、一台常规办公机；高刷可用时加入 120Hz 和非整除刷新率显示器。记录 Windows、WebView2 Runtime、GPU/驱动、DPI、显示刷新率、电源模式、构建号和客户区尺寸。

场景：冷/热启动各至少 5 次、首局与二次进入、满盘快速瞄准、大掉落、连续游玩 30 分钟、反复菜单/重试、最小化和睡眠恢复；全屏、跨屏、旧存档迁移与离线启动也需回归。

| 指标 | 拟定验收目标 / 记录方式 |
| --- | --- |
| 实际渲染 FPS | 目标最高 120；60Hz 正常回退；高刷不被错误限帧锁到较低档 |
| 帧节奏 | 记录真实渲染间隔 p50/p95/p99；预算 120/90/60/30 分别为 8.33/11.11/16.67/33.33ms |
| 卡顿 | 超过 1.5 倍当前预算的活动帧比例初拟 ≤1%；另记 >50ms 帧，排除加载/后台后校准 |
| 输入 | 记录鼠标/键盘到下一次可见变化，初拟 p95 ≤50ms；同机高刷改善需实测 |
| CPU / 内存 | 首页、局内、最小化分别测；应用及相关 WebView2 进程树合计，JS 堆单列 |
| 持续稳定性 | 30 分钟内帧率可持续，切页/重试后内存达到平台；降档没有抖动或输入跳变 |
| 外壳恢复 | 分类故障、失焦、睡眠、高 DPI、全屏和跨屏行为符合定义 |
| 存档与规则 | 档位切换不丢局，异常恢复不重复成绩，备份和旧版迁移成功 |

## 8. 分阶段交付

1. **桌面可靠性**：原生基线、弹窗焦点、防误重开、故障分类、宿主快捷键与失焦策略。
2. **最高 120 自适应**：共用帧率设置和适配层、真实渲染统计、高刷/非整除测试、切档和计时回归。
3. **玩法与界面**：共用供球、短练习、关卡人工校准、星级/分数/纪录，高 DPI 与方向键组合。
4. **按实测完善**：画质、HUD、静止和最小化负载、备份迁移反馈。

每阶段提交原生结果和前后数据。保留轻量离线游戏定位，先把三种玩法和键鼠/窗口体验做好，再决定是否增加联网或大型新模式。
