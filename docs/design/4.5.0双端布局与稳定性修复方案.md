# Orbbound 4.5.0 双端布局与稳定性修复方案

日期：2026-10-18

适用平台：Android、Windows

排查基线：当前工作区 `eb77e3f`，产品版本 `4.4.0`

文档状态：**已按 4.5.0 实施并生成双端安装包，作为 prerelease 测试版交付。** 下文保留排查基线和设计目标，实际完成范围、实机记录及未完成矩阵见 [4.5.0 验证记录](../releases/4.5.0-validation.md)，不将目标清单等同于全部验收通过。

## 1. 更新目标与排查结论

4.5.0 以修复布局回归和界面无响应为主：恢复 Android 首页演示，缩短不必要的菜单高度，修复 Windows 模式卡裁切，并消除分页和异步操作造成的阻塞风险。

当前问题有共同来源：4.4.0 在旧样式之上增加固定视口、统一弹窗高度和通用分页，但没有完整清除旧容器裁切，也没有按页面内容区分高度策略。

| 用户反馈 | 本轮结论 | 证据等级 |
| --- | --- | --- |
| Android 首页演示动画消失 | 移动端被 CSS 无条件隐藏，SVG 和动画实现仍在 | 代码确认、浏览器复现 |
| 各级菜单异常长 | 普通短弹窗同样被强制设为最高 720px，内部正文填满剩余空白 | 代码确认、浏览器复现 |
| Windows 选择区域圆角过大、按钮显示不全 | 无内边距的新布局仍继承旧父容器 `28px` 圆角与 `overflow:hidden`，对子卡片二次裁切 | 代码确认、浏览器几何和命中检查复现 |
| 个别界面卡死 | 已发现逐字同步分页、破坏式拆段、联机等待无上界及无关设置触发重绘等缺陷；尚未取得用户故障时的真机调用栈 | 缺陷已确认；具体卡死归因待真机抓证 |
| Android 安全区、键盘异常风险 | 项目自研 Insets 与 Capacitor 内置 SystemBars 同时处理窗口边界 | 双重处理链已确认；设备影响待验证 |

本版保留原有模式、关卡、存档、签名和操作习惯。延续 4.4.0 的页面约束：**普通页面使用一屏布局、分页或分步；设置详情允许单一纵向滚动。** 不以隐藏溢出、缩小到不可读或隐藏动画来满足这一约束。

## 3. 已定位问题与修复决策

### 3.1 P0：恢复 Android 首页演示，并重新分配高度

**证据：** [style.css](../../src/style.css) 第 1088 行直接写有 `.mobile-ui .mechanism-demo { display:none; }`；[home.ts](../../src/ui/home.ts) 第 35–36 行仍将演示 SVG 放入 `.hero-copy`。较早的显示规则已被后面的隐藏规则覆盖。第 1156 行还在短屏隐藏演示。

实施要求：

1. 清除无条件隐藏及冲突覆盖，让首页组件只有一套可追踪的最终规则。
2. 为品牌、标题/演示、四模式 2×2 区域、底部工具明确分配高度；安全区单独计入。
3. 常规竖屏保留完整演示；短竖屏压缩标题、装饰和次要文案，为演示分配紧凑区域；横屏采用左演示、右模式的布局。
4. 极低可用高度采用明确的紧凑/分步展示，演示仍可访问，四个模式和返回入口始终可达。不得把不可见裁切作为降级方案。
5. 减少动态效果或系统减少动画时显示清晰静态机制图；正常模式保留播放和轻触重播。进后台、弹层打开时暂停，返回后恢复。

**完成标准：** 320×568、360×640、393×851、412×915 竖屏可见演示；普通动画状态下 SVG 有非零尺寸、实际播放并可重播；四个模式及底部三个入口完整可点击。

### 3.2 P0：修复 Windows 父圆角二次裁切

**证据链：** [style.css](../../src/style.css) 第 96–108 行的旧 `.home-card` 有 `overflow:hidden` 和 `border-radius:28px`；第 1069 行将其改成零内边距、无背景的布局层，却未清掉这两项。第 1070 行按钮网格紧贴父边缘，第 730 行子模式卡仍有自己的 `16px` 圆角。

实施要求：

- `.home-card` 仅承担排版，显式复位 `border-radius:0; overflow:visible`，清理残留的尺寸限制。
- 模式卡独立承担背景、强调边和圆角，建议统一为 12px；按钮与卡片的边界一致。
- 校验文字、箭头、描边、悬停/按下态、键盘焦点环全部可见。仅减小父圆角不算完成修复。
- 将外壳剩余高度传到模式区域；在具备确定高度后使用两行有界网格。取消冲突的按钮固定最小高度时，必须同步提供可读、可点击的紧凑布局。

当前常规外壳固定占用约 128 CSSpx，两行 120px 模式卡加间距还需约 252px；这是未计安全区和左侧内容的最低预算。不能依靠没有确定块高度的 `1fr` 自动解决溢出。

Windows 原生 `780×500` 最小值是外窗尺寸，见 [Program.cs](../../windows/Program.cs) 第 92 行。断点和验收必须记录真实 WebView CSS 客户区，窗口变窄也继续使用桌面输入。

### 3.3 P0：按内容类型定义菜单高度

**证据：** [style.css](../../src/style.css) 第 1095 行将所有弹窗统一设为 `height:min(720px,100%)`；第 1102 行正文再以 `flex:1` 填满剩余空间；设置卡第 1130 行为最高 800px。[main.ts](../../src/main.ts) 第 373–391 行将各类普通弹窗送入同一套外壳和分页器。

| 页面类型 | 4.5.0 高度与内容策略 |
| --- | --- |
| 确认、错误、退出、简短提示 | 内容自然高度 + 可用视口 `max-block-size`；按钮紧接正文，不设全屏固定高度 |
| 无尽/限时配置、关卡详情、教程、结果 | 按语义分步或有界分页；标题和操作区固定可达；单页内容少时自然收紧 |
| 选关、记录、房间列表、联机帮助/诊断 | 保留数据分页；按真实正文区域及文字高度决定容量 |
| Android 设置分类首页 | 四分类紧凑呈现，按内容决定高度 |
| 设置分类详情 | 有界工作区；标题、返回/完成固定，仅详情正文纵向滚动 |
| 练习、游戏、联机对局 | 专用布局保留棋盘与操作区，不交给通用弹窗拆分 |

菜单类型应由创建者显式声明，避免继续通过类名排除名单推断。短弹窗不应因为挂载了空的分页容器而自动膨胀。

### 3.4 P0：替换逐字符、破坏式通用分页

**证据：** [viewport-shell.ts](../../src/ui/viewport-shell.ts) 第 50–60 行逐字符更新 `textContent` 并读取 `scrollHeight`；第 64 行将碎片回写 `units`。第 67 行仅在当前页已有多个子元素时换页，无法处理单个超高表单或预览。

浏览器已经复现缩屏后步骤结构永久丢失。循环的文本偏移会前进，**没有证据证明是无限循环**；但它在同一帧中反复触发布局，且可能生成大量页面。

实施要求：

1. 教程按完整步骤、配置按字段组、结果按摘要/详情分页；先取消普通短对话框的自动分页。
2. 保留不可破坏的原始内容模型和稳定条目 ID。展示分页只管理分组，不能将 DOM 文本碎片作为下一轮数据源。
3. 确需拆长说明时，保留语义和强调；采用有次数上限的测量或二分策略，禁止逐字符写入并读取布局。
4. 正文高度为 0 或不足最低行高时延后排版或进入专门紧凑步骤，不能继续生成字符页。
5. 单个超高交互单元改为专用分步表单/预览；不把它塞进隐藏溢出的卡片。
6. 合并 `window.resize`、`visualViewport.resize` 和安全区变化，一帧最多进行一次当前页面重排；读尺寸与写样式分开。
7. 重排保留当前步骤/条目、字段值和焦点；缩屏再恢复时，内容结构与首次以该尺寸打开一致。关闭页面后取消待执行测量。

实施时补充了两项容错：文本分段 API 缺失或抛错时使用 Unicode 安全回退；重排发生意外异常时恢复原内容及关闭按钮，并临时启用有界正文滚动恢复区。这个异常恢复态优先保证内容和退出可达，恢复正常布局后重新分页；普通页面的正常状态仍使用分页/分步。

**完成标准：** 教程的 3 个步骤及语义结构在 568→240→568 高度切换后保持完整；不存在无法访问的表单项或末页；不出现分页导致的持续无响应。

### 3.5 P0：统一 Android 安全区和键盘处理责任

**代码事实：** [MainActivity.java](../../android/app/src/main/java/com/orbbound/game/MainActivity.java) 第 39–45 行在 content 上处理 Insets 并返回 `CONSUMED`；[android-insets.ts](../../src/ui/android-insets.ts) 第 13 行再写入项目 CSS 安全区。与此同时，[capacitor.config.ts](../../capacitor.config.ts) 没有禁用内置 SystemBars。

本地 Capacitor 8.5.2 的 `SystemBars.java` 第 56、125、191–238 行表明：默认使用 `css` 处理、在 DecorView 上监听，并根据 WebView 版本处理系统栏与 IME。第 229–231 行说明消费 Insets 会破坏安全区重算。这是源码依据，尚不能直接推导某台手机一定被重复扣除多少高度。

**本版推荐决策：** 统一采用已安装的 SystemBars CSS 处理机制，移除项目额外消费 Insets 的链路，保留必要的系统栏配色和原生能力查询。

- 将项目 `--safe-area-*` 映射至内置 `--safe-area-inset-*`，并保留 `env()` 回退；停止另一套代码持续覆盖它们。
- 视口高度使用当前可见的 WebView/`visualViewport`；已经由原生缩减的键盘空间不再重复扣除。IME 高度与导航安全边距分开处理。
- 建立系统栏/刘海 Insets、可见视口、键盘状态的统一采样；变化合并后通知当前页面。
- 昵称、房间名、IP 编辑沿用单字段编辑层，键盘上方保留当前字段、校验和完成/取消；收起后恢复原页和输入值。
- 同步替换 [lan-panel.ts](../../src/ui/lan-panel.ts) 第 361–364 行仅凭 `innerHeight - visualViewport.height > 120` 判断键盘的逻辑：原生调整窗口时两者可能同时缩小。以统一的原生 IME 可见状态和当前字段编辑状态为主，视口变化作为兜底；原生状态通道只读，不再次消费或改写 Insets。补测“两个高度相等但键盘仍可见”，避免编辑层不出现或被立即关闭。
- 若实机验证必须保留自研链路，则显式禁用内置 Insets 处理并补全 IME；两套机制不能同时作为布局权威。不要修改 `node_modules` 作为正式修复。

当前实体机 WebView 为 143，正处于依赖源码中键盘处理存在版本分支的范围，因此应优先验证真实输入法与三键/手势导航；不以升级系统 WebView 代替应用修复。

### 3.6 P1：为联机操作提供有上界的等待和退出

**证据：** [transport.ts](../../src/lan/transport.ts) 第 63–66 行直接等待 Android 插件 Promise；Windows 第 70–75 行已有 10 秒超时。[lan-panel.ts](../../src/ui/lan-panel.ts) 第 53–57 行仅在操作结束后解除 `busy`，退出清理期间还会锁住首页联机入口。

原生 TCP 连接已有 5 秒超时，不能将普通连接失败一概描述为永久卡死。缺口在于插件初始化、桥接失联、不回调或串行队列阻塞时，前端没有统一退出上界。

实施要求：

- 为初始化、创建、加入、检索、关闭分别定义期限和取消语义，统一双端反馈；普通桥接请求可沿用现有 10 秒期限作为默认值。
- 用户退出后先恢复本地可操作界面；原生清理以有界流程完成，必要时提示重试。
- 所有请求关联操作编号及会话 generation，超时/取消后的迟到成功不能创建幽灵房间或覆盖新会话；必要时向原生发送补偿关闭。
- `finally` 保证清理 `busy`、禁用状态和加载提示。不能只加 `Promise.race` 而保留迟到副作用。

### 3.7 P1：减少设置拖动和尺寸变化的无关工作

**证据：** [main.ts](../../src/main.ts) 第 475–478 行每次设置变化都会刷新原生性能配置；[platform-services.ts](../../src/ui/platform-services.ts) 第 40–48 行请求原生刷新率。[lan-board.ts](../../src/ui/lan-board.ts) 第 155–184 行每次设置变化都重设画布尺寸，尺寸相同也会写 `canvas.width/height`。

实施要求：

- 按实际变更项分派副作用：音量只更新音频；帧率变化才请求刷新率；清晰度或实际尺寸变化才重分配画布；控制项变化才重绑输入。
- 设置仓库使用同一个可变对象，差异判断应保存上次已应用的字段快照，不能仅比较对象引用。
- 相同画布像素尺寸不重复写属性；原生刷新率请求去重和合并，能力信息未变化不再触发整组重排。
- 单机和联机的 ResizeObserver 回调统一进行尺寸差异检查、一帧合并和必要的 `scale.refresh()`，避免观察与写入互相驱动。

完成标准：拖动音量 5 秒且画质/帧率/尺寸不变时，原生刷新率请求为 0，画布尺寸重建为 0；设置仍实时生效。

### 3.8 P1：补齐加载中断和弹层恢复保护

[main.ts](../../src/main.ts) 第 219–225 行在等待 `scene.ready` 时已经显示游戏页；返回和后台路径可能调用 `pauseGame()`。[PlayScene.ts](../../src/game/PlayScene.ts) 第 270–286 行没有 ready 防护。这是需通过慢启动注入验证的竞态候选，尚未复现为本次卡死。

- 明确 `loading → ready / cancelled / failed`；未 ready 时先取消启动，不访问未创建的场景对象。
- 快速返回、退后台、加载失败与超时都要清除 loading，旧启动完成后不得抢回页面。
- 当前弹层已有 inert 和焦点释放机制，未发现常驻 inert 的确定缺陷；继续回归替换弹窗、返回一层、关闭设置和退出练习，确保遮罩及输入状态恢复。
- 页面退出时成组清理 rAF、计时器、观察器、订阅和待执行异步结果，避免往返后重复绑定。

## 5. 验收矩阵和发布阻断项

### 5.1 布局与交互

| 维度 | 必测范围 |
| --- | --- |
| Android CSS 视口 | 320×568、360×640、393×851、412×915；568×320、851×393；320×240 仅作压力测试 |
| Android 实机 | 当前 Android 16 实体机 + Android 15 模拟器；补一台较低性能实体设备；记录各自 WebView、字体与导航方式 |
| 系统变化 | 字体 100%/130%，三键/手势导航，刘海/打孔安全区，横竖屏，真实键盘展开/收起，退后台恢复 |
| Windows CSS 视口 | 800×600、1280×720、1366×768、1920×1080；640×360 紧凑压力检查 |
| Windows 原生 | 默认窗口与 780×500 最小外窗；100%/125%/150%/200% DPI；最大化/恢复、不同 DPI 显示器之间移动、恢复旧窗口位置 |
| 页面清单 | 首页；无尽/限时配置；选关及详情；教程与练习；设置四分类及详情；记录筛选/解释/末页；联机创建/加入/帮助/诊断/大厅；暂停/退出/错误/结果；五种玩法界面 |
| 内容状态 | 空数据、长中文/emoji 昵称、长错误、多地址、最大条目、最后一页、旧存档及可继续游戏状态 |

每项同时检查：

1. 全部关键按钮和文本位于可见安全区域；触控目标至少 44 CSSpx，无遮挡和圆角裁切。
2. 使用实际边界、祖先裁切和命中检测；模式卡有效边角、按钮中心及正文实际点击有正确结果。
3. 普通页面无纵向滚动且全部内容可由分页/分步访问；设置详情只有一个滚动区域；不能只凭 `scrollHeight <= clientHeight` 判定成功。
4. 焦点不会进入隐藏页；Android 返回、Windows Esc 与页面返回按钮只退一层，不穿透发射。
5. 首页演示正常/减少动画两种状态均可见，播放与重播可验证；对动画截图使用固定阶段，避免随机时刻误判。

### 5.2 无响应专项

- 教程和菜单执行视口缩放、键盘开合、旋转、关闭重开各 20 次，原内容、字段值、当前条目可恢复。
- 首页→菜单→返回、设置→返回、练习→退出、创建/加入→退出各往返 50 次；监听器、rAF、ResizeObserver、遮罩和 inert 不随次数累积。
- 对 Android 桥接注入永不返回、超时后成功、超时后失败、初始化失败和清理失败；UI 均可退出重试，迟到结果不污染新会话。
- 注入慢场景初始化，立即返回、切后台、重试；无未捕获异常和永久 loading。
- 在真机记录菜单打开/重排耗时、长任务、连续帧间隔和 resize 次数；若发生冻结，关联 WebView 调用栈、原生主线程/ANR 信息与当时页面状态。
- 建议性能目标：交互在 100ms 内提供反馈；基准设备普通菜单打开/分页可操作耗时 p95 ≤200ms；超过 50ms 的测量任务记录来源，不允许出现由分页或重排引起的持续 1 秒无响应。这些是 4.5.0 验收目标，尚未取得实测通过数据。

### 5.3 测试补齐与发布门槛

现有 Node 测试继续保留，新增实际浏览器布局/交互用例；分页算法、超时状态机和设置差异分派分别做针对性测试。原生 Insets 和 IME 必须在安装版验证，浏览器截图不能替代。

以下任一项未通过，阻断 4.5.0 正式版发布：

- Android 首页演示仍不可见、入口或主要操作被裁切。
- Windows 模式卡边角、文字、焦点环不完整。
- 短菜单仍被无意义撑成大空白，教程缩屏后结构被破坏。
- 已复现的卡死仍未定位，或退出/取消后界面不能恢复。
- 键盘、系统栏或 DPI 改变后确认/关闭按钮不可达。
- 覆盖安装造成旧存档、设置或历史记录丢失。

局域网保持原协议 v3、规则和内容指纹不变是本版目标；是否与 4.4.0 混用须通过双向房主回归确认后写入说明。至少验证双端完整一局、暂停设置恢复及退出重连；四人界面和画布修改还需四终端回归，不以单机布局修复替代联机验收。
